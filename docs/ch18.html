Chapter 18

Agent to UI

The host cannot see inside your frame, so an agent that wants to act on your interface has to be given a vocabulary. Registering tools is that vocabulary, and it turns out to be the same mechanism accessibility and testing need.

The reverse direction is harder than it looks, and the reason is a security property rather than an oversight. Your view is in a sandboxed iframe. The host cannot read its DOM, and should not be able to. So an agent that wants to highlight a row, open a panel, or propose a value has no way to reach in.

The draft specification’s answer is that the view reaches out: it registers tools, and the host calls them. That single mechanism covers everything in this chapter, and it has three uses that are worth noticing are the same thing.

A view declares tools in appCapabilities during initialisation. The host then sends tools/list to the view, which answers with tool descriptors in the standard MCP shape, and tools/call to invoke one. When the set changes, the view sends notifications/tools/list_changed.

Extracted from from apps/labs/lab-apptools/index.html

bridge.registerTool({
  name: "highlight_line_item",
  description: "Draw the user's attention to one line item by index",
  inputSchema: { type: "object",
    properties: { index: { type: "integer", minimum: 0, maximum: 3 } },
    required: ["index"] },
  annotations: { readOnlyHint: true },
}, async ({ index }) => {
  tab = "b";
  draw(index);
  return { content: [{ type: "text", text: `Highlighted ${ITEMS[index][0]}.` }],
           structuredContent: { item: ITEMS[index][0], amount: ITEMS[index][1] } };
});

Three properties of app tools distinguish them from server tools, and all three follow from where the code lives.

They are ephemeral. They exist while the frame does. Hosts must not persist the registrations across sessions, and calling a tool from a closed app returns an error.

They are untrusted. The code came from a server and runs in a sandbox. Descriptions may not describe side effects honestly, names may collide with server tools, and results should be validated. The specification recommends clear attribution in the host’s UI, per-app or per-server approval, name prefixes, resource limits, and an audit trail.

They are the only introspection route. The host has no DOM access, and a view may nest cross-origin frames of its own. If the model is to know anything about the view’s state, the view has to say so, either by pushing with ui/update-model-context or by answering a pull through a tool.

Annotate honestly. readOnlyHint: true is the one claim a host will act on, by auto-approving. Marking a mutating tool read-only is the single most consequential lie available in this system.

“Draw attention to this thing”, where the thing is a row, a node, a line, or a region. It is the lightest agent action and the one that makes a conversation about a view feel connected to it.

Application behaviour. Implement it as a tool that takes a stable identifier, not a coordinate or a CSS selector. highlight_line_item(index) survives a re-render; highlight("#row-3 > td:nth-child(2)") does not, and hands the agent a way to poke at your internals.

Make the highlight obviously temporary and obviously the agent’s. Recipe 7 puts a glow on the node and says “agent: highlighted Classify” in the corner, so a user who looks away and back knows who moved what.

Accessibility. A highlight that is only visual is invisible to a screen reader user, and this is a change they did not cause. Announce it, once, into the live region from Chapter 13.

“Open the panel you are talking about.” The agent changes view state: switches a tab, expands a section, scrolls to a result, selects a row.

The rule that keeps this safe is that every agent-initiated navigation must be something the user could have done themselves with the mouse, and must be visible when it happens. An agent that silently changes what the user is looking at while they are reading is worse than one that does nothing.

Design the tool around the user’s vocabulary, not your component tree. show_panel("items") is a tool the model can use correctly from a description. set_state({activeTabIndex: 1}) is one it will use wrongly, and one that breaks when you reorder the tabs.

Prefill

ui.prefillCoreLevel 4Yours to build

The agent proposes values into inputs. It never submits.

That distinction is the whole entry. Prefilling a form is enormously useful: the agent has read the ticket, the invoice, the previous three messages, and can fill in six fields the user would have typed. Submitting the form is taking an action in the user’s name, and the signature on it has to be theirs.

Application behaviour. Fill the field, mark it visibly as proposed, focus it so the user’s next keystroke is in the right place, and leave the submit button alone. The demonstration shows “Proposed by the agent. Review before submitting.” next to the field until a human presses the button.

Extracted from from apps/labs/lab-apptools/index.html

bridge.registerTool({
  name: "propose_reason",
  description: "Propose wording for the adjustment reason, for human review",
  inputSchema: { type: "object", properties: { text: { type: "string" } },
    required: ["text"] },
  annotations: { readOnlyHint: false },
}, async ({ text }) => {
  $("#reason").value = text;
  $("#proposed").hidden = false;
  $("#reason").focus();
  return { content: [{ type: "text",
    text: "Proposed. The user has not submitted it." }] };
});

Note the return value. The tool tells the agent what actually happened, including the part the agent might otherwise assume: the user has not submitted it. An agent that receives “done” will report to the user that it has been done.

In a document rather than a form, the same rule produces a diff or a proposal card rather than a silent replacement. Recipe 4 shows the rewrite as a proposal with Accept and Decline, and accepting is one undo transaction.

Reading the view

The fourth thing to register is not an action at all. get_state lets the agent ask what is currently on screen.

Extracted from from apps/labs/lab-apptools/index.html

bridge.registerTool({
  name: "get_state",
  description: "Read the view's current state",
  annotations: { readOnlyHint: true },
  inputSchema: { type: "object" },
}, async () => ({
  content: [{ type: "text", text: `Panel ${tab}, reason ${
    $("#reason").value ? "drafted" : "empty"}.` }],
  structuredContent: { panel: tab === "a" ? "summary" : "items",
                       reason: $("#reason").value,
                       submitted: false },
}));

This is the pull half of the pair whose push half is ui/update-model-context. Push keeps the model current on the things that always matter; pull lets it ask about the things that occasionally do. Most views want both, and the deciding question is whether a fact is worth spending context on every turn.

The three uses that are one mechanism

Worth stating plainly, because it justifies the effort.

Agent action. The subject of this chapter.

Accessibility and voice. A user who cannot point still needs to open the panel. An agent driving show_panel on their behalf is doing exactly what the mouse would have done, through an interface designed for it.

Testing. A sandboxed frame cannot be driven from outside by a test harness, because the harness cannot reach its DOM either. It can be driven through the same tools. The conformance harness in Part VI drives views this way, and the golden transcripts for this chapter’s demonstration are recordings of a test doing exactly what an agent would do.

Three requirements, one mechanism, one set of tools to write. That is unusual enough to be worth designing around: if you are choosing which parts of your view to expose, choose the ones that would make all three easier.

Designing the tool surface

A view with twenty registered tools is a view whose tools the model will choose between badly. Four to six is the range the recipes here settle on, and the way to get there is to design the surface as a vocabulary rather than as an API.

Name operations, not implementation. show_panel("items") reads from a description; set_state({activeTabIndex: 1}) does not, and breaks when the tabs are reordered.

Take stable identifiers. Names and ids that survive a re-render. Never selectors, never coordinates, never array positions that depend on the current sort.

Return what happened, not what was asked. “Held. The user is editing” and “Proposed. The user has not submitted it” are both outcomes an agent needs, and both are outcomes a naive implementation would report as success. This is the single highest-value habit in the chapter: an agent that receives “done” will tell the user it is done.

Include one read tool. get_state costs almost nothing and removes the need to publish everything through ui/update-model-context every turn.

Annotate honestly. readOnlyHint: true is the claim that earns automatic approval, so it is the claim that must be true.

Failure modes across the group

Unsupported. The view declares tools and the host never sends tools/list. Everything still works by pointer; nothing works by agent. Do not build a view whose only route to a function is a tool.

Unknown tool. Return an error naming the tool, so the agent can correct rather than retry.

Invalid arguments. Validate before acting. The SDK does this from the schema; the bridge in this repository does not, which is a real difference between a teaching implementation and a production one.

Called after teardown. The frame is gone and the host must return an error. Tools are tied to the render, and hosts must not persist registrations.

Conformance checks

  1. A view declaring tools receives tools/list and answers with descriptors.
  2. tools/call for a registered tool runs it and returns its result.
  3. tools/call for an unknown name returns an error rather than hanging.
  4. Registering or removing a tool sends notifications/tools/list_changed when the view declared listChanged.
  5. App tools disappear when the frame is torn down.
  6. A prefill tool changes an input and does not submit it.
  7. Every agent-initiated change is visible and reversible.

What to remember

The agent cannot see your interface, and giving it a set of named, stable, honestly annotated operations is both the safest and the most useful thing you can do about that. Every one of them should be something a user could have done, should be visible when it happens, and should be reversible. Chapter 20 is what happens when it is not.
