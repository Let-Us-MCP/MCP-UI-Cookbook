Appendix C

Conformance Checklists

What a host is claiming when it claims a level, phrased as things a test can assert.

Levels are cumulative: a host claiming Level 3 passes the checks for Levels 1, 2 and 3. Extended capabilities are not on these lists, because they are optional at any level and their absence must be handled by applications.

Items marked not standardised are Core capabilities with no mechanism. A host cannot be asked to implement them until the gap in Appendix B is closed, and they are listed so that the shape of the missing work is visible.

Level 1: Embedded

Render, size, theme, link out, and know what you are running inside. A host claiming level 1 passes every check below, and the checks for every level under it. 1 further capabilities at this level are extended and may be absent.

  • host.capabilities — Enumerate what this host supports before using any of it.
  • surface.resize — Report content size so the host can size the frame around it.
  • surface.viewport — Read the space actually available: fixed, flexible, or unbounded.
  • input.pointer — Click, hover, drag, and capture across mouse, touch, and pen.
  • link.open — Delegate external navigation instead of attempting it.
  • env.theme — Take the host's tokens and follow them when they change.
  • env.locale — Format numbers, dates, and text for the user's region.
  • env.timezone — Render instants in the timezone the user is actually in.

Level 2: Interactive

Focus, keyboard, selection, clipboard, files, dialogs, and errors that recover. A host claiming level 2 passes every check below, and the checks for every level under it. 9 further capabilities at this level are extended and may be absent.

  • surface.close — Ask the host to dismiss this view.
  • surface.focus — Move, trap, and restore focus inside the view.
  • surface.focusHandoff — Hand focus across the host boundary in either direction. not standardised
  • surface.scroll — Scroll to a position or bring an element into view inside the frame.
  • surface.reveal — Ask the host to scroll the conversation until this view is visible. not standardised
  • dialog.alert — Block on an acknowledgement the user cannot miss.
  • dialog.confirm — Take an explicit binary decision before acting.
  • dialog.prompt — Collect one small value without leaving the surface.
  • notify.toast — Say saved, copied, failed, and get out of the way.
  • input.keyboard — Keys, modifiers, and the platform conventions users already have.
  • input.shortcut — Own an accelerator without fighting the host for it. not standardised
  • input.longpress — Touch equivalent of a right click.
  • input.contextmenu — Contextual actions on right click or long press.
  • input.selection — Single, additive, range, and select-all over text and objects.
  • input.dragdrop — Drag and drop inside the view, with structured transfer data.
  • clipboard.write — Copy text or structured content, with a fallback when denied.
  • file.open — Open the system file picker and read what comes back.
  • file.dropzone — Accept dropped files with validation, preview, and progress.
  • file.export — Hand a generated artifact to the host to save.
  • file.save — Persist app-generated content through the host.
  • env.inputMode — Size targets for the modality actually in use.
  • env.safeArea — Keep content out of regions the host has spoken for.
  • env.reducedMotion — Respect a stated preference for less movement.
  • env.contrast — Survive forced colours and high contrast.
  • env.textScale — Stay usable when text is two sizes larger than you designed for.
  • a11y.announce — Tell assistive technology that something changed.
  • lifecycle.dirty — Track uncommitted local state and say so.
  • lifecycle.beforeClose — Get one chance to finish before the frame goes away.
  • op.progress — Determinate and indeterminate progress with a phase name.
  • op.cancel — Interrupt work that is still running.
  • op.retry — Retry without making the user rebuild the interaction.
  • op.error — Structured errors: what failed, whether to retry, what to do.

Level 3: Native-Like

Display modes, spatial interaction, lifecycle, persistence, history, media. A host claiming level 3 passes every check below, and the checks for every level under it. 7 further capabilities at this level are extended and may be absent.

  • surface.displayMode — Move between inline, fullscreen, and picture-in-picture.
  • input.zoompan — Wheel and pinch zoom, pan, reset, fit to content.
  • lifecycle.visibility — Know when the view is on screen and when it is not.
  • lifecycle.suspend — Stop doing work nobody is looking at.
  • lifecycle.connectivity — Show online, offline, and reconnecting honestly.
  • state.save — Persist view state keyed to the view's identity. not standardised
  • state.restore — Come back up where the user left off. not standardised
  • history.transaction — Group mutations into one undoable unit.
  • history.undo — Revert the last transaction, including the agent's.
  • history.redo — Reapply what was reverted.

Level 4: Agentic

Tools, streaming, context, approval, and shared ownership of state. A host claiming level 4 passes every check below, and the checks for every level under it. 1 further capabilities at this level are extended and may be absent.

  • agent.escalate — Put the current selection into the conversation as a request.
  • agent.contextUpdate — Publish the part of view state the model should reason over.
  • agent.intent — Name a semantic action rather than describing it in prose. not standardised
  • app.tools — Expose the view's operations as tools the agent can call.
  • ui.highlight — Let the agent point at a row, a node, or a hunk.
  • ui.navigate — Let the agent open the panel it is talking about.
  • ui.prefill — Let the agent propose values, never submit them.
  • tool.invoke — Call a server tool from a button, through the host.
  • tool.cancel — Cancel a call the user has stopped caring about.
  • tool.partialInput — Render something useful while arguments are still streaming.
  • tool.result — Take delivery of the result that this view was rendered for.
  • tool.partialOutput — Update stable elements as results arrive, not after. not standardised
  • state.ownership — Declare who owns each region when both parties can write.
  • state.conflict — Decide what happens when they both do.
  • approval.request — Require a human signature on a sensitive action. not standardised
  • elicit.request — Ask the user a structured question mid-operation. not standardised
  • agent.boundary — Keep hover, scroll, and sort out of the model's context.

Cross-cutting checks

These apply at every level and are the ones that break the most applications.

The handshake is truthful. Every capability present in hostCapabilities behaves as described when used. A capability advertised and not implemented is worse than one that was never advertised, because it defeats exactly the views that checked properly.

The frame is sized from the notification. When a dimension is flexible, ui/notifications/size-changed changes the frame. A zero from a freshly appended frame is treated as “not yet” rather than as “empty”.

Teardown waits. ui/resource-teardown is sent before removal and the host waits for the response, with a bounded but generous deadline. This is the only data-loss defect in the protocol that a view cannot work around.

Context changes are partial. ui/notifications/host-context-changed carries only what changed, and the host does not expect the view to re-initialise.

The sandbox is real. The frame has allow-scripts and not allow-same-origin, the CSP is constructed from the resource metadata, and undeclared origins are blocked.

Nothing is sent before ui/notifications/initialized. A host that sends tool input before the view has finished initialising will lose it.

For application authors

The mirror image, as a pre-ship list.

Read hostCapabilities once, at initialisation, and let it decide which controls exist. Define a fallback for every style variable you use. Format through hostContext.locale and timeZone. Report your size on change only. Answer ui/resource-teardown promptly, and flush before you do. Publish state to the model, not events, and only state that changes an answer. Put every agent write on the undo stack. Handle all five failure modes from Chapter 5, and check that the interface is honest in each.

Publishing a result

A host that runs these checks has a number, and the number is worth publishing in a form somebody can act on: the level claimed, the checks that failed, and the date of the run. The model to copy is the public web platform test dashboards, where a per-feature, per-implementation grid makes it possible to write portable code without guessing.

Nothing here requires that infrastructure. A markdown table in a repository is enough to be more useful than the current situation, which is that application authors discover a host’s level by shipping into it.

What this appendix cannot tell you

Whether a host is good. Every check here is about whether a defined behaviour happens, and none of them is about whether the result is usable. A host can pass every Level 2 check and still render views in a 200 pixel column with the theme variables of a different product. Conformance is the floor, not the ceiling.
