Chapter 28

The Missing Primitive Loop, and the Live Book

How a gap gets found, what a good proposal looks like, and how a static site runs thirty applications next to their own source without hosting anything.

Two subjects in one chapter, because the second is what makes the first credible. A list of missing capabilities is an opinion until somebody can run the applications that needed them and watch the workaround happen.

Anyone can assert that fourteen capabilities are missing. A book whose demonstrations run in your browser, with transcripts showing exactly where each workaround happens, has shown you.

How a gap gets found

Primitives compose into components. Components compose into applications. Applications become coverage tests. A test that cannot be written names a missing primitive.

The loop only works in that direction. Starting from “what should the protocol have” produces a wish list. Starting from “build the thirteen applications people actually ask for” produces fourteen findings, each attached to a recipe that needs it and a workaround somebody had to write.

Every gap in this book arrived that way. state.save was found by the Document Editor needing to survive a reload. tool.partialOutput was found by the Monitoring Console needing a log tail. notify.attention was found by an error arriving at three in the morning in a view nobody was looking at. approval.request was found by asking what the Approve button actually guarantees, and finding that the answer is nothing.

What a good finding contains

Four parts, and Appendix B carries all four for each of the fourteen gaps. A finding missing any of them is a complaint: the recipe pins it to something real, the cost stops it being a wish, the mechanism makes it arguable, and the threat-model note is what stops it being naive.

The recipe that needs it. Not a hypothetical. A named application, in this repository, that a reader can run.

What the workaround costs. Every gap has one, and stating the cost is what separates a finding from a complaint. Persistence through a server tool costs a round trip and stops working at Level 1. Streaming through repeated tool results costs portability. Approval through a queue-and-perform convention costs the guarantee.

A concrete mechanism. One request, one notification, or one context field, specific enough to argue with: ui/set-view-state plus a viewState field in the initialize result; a visibility field on ui/notifications/host-context-changed; ui/request-attention with a severity and a label.

What it reopens. Chapter 4’s threat model, applied to the proposal. A mechanism that reopens one of the five attacks needs a better story than convenience, and saying which attack in the proposal saves everybody an argument later.

Where findings go

Upstream, as issues against the extension specification, rather than into a private extension of your own. A host-specific mechanism for view state solves the problem for one host and fragments it for everybody else, which is exactly the outcome this extension was created to prevent.

The counter-argument is real: sometimes a host has to ship something before a specification exists. The mitigation is to ship it as an experimental capability, which both hostCapabilities and appCapabilities already reserve a slot for, and to file the finding at the same time.

How the live book works

Everything on these pages runs, and the arrangement behind it is simpler than it looks. There is no backend, no build server and no runtime: the whole site is static files, which is possible only because an MCP application needs neither a model nor a server to render.

One source tree, three views of it. The application is executed, in a sandboxed iframe. Its source is read, fetched from the same directory the iframe loaded it from. And the conversation between them is narrated, in the transcript pane, as it happens.

The code pane cannot drift from the running code, because they are the same file over the same URL. That is the entire mechanism, and it replaces a build step that extracts listings and a discipline that keeps them current.

The host is an emulator, not a mock. About two hundred and fifty lines implementing the host half of the bridge: it answers ui/initialize, applies capability rules, resolves tools/call from fixtures, honours resize requests, arbitrates display modes, and tees every message to the log. It is a real host implementation with a fixture file where a server would be, and the capability checks in it are the same checks a real host makes.

The fixtures come from real servers. tools/record_fixtures.mjs starts each recipe’s actual MCP server over stdio, calls the tools listed in its record.json, and writes the responses to fixtures.json. So the sentence this book makes is true: the view in the live pane receives what the code in the server pane produces. The demonstration is honest even though the server is not executing in your browser.

Nothing is hosted. Static files on GitHub Pages, with no backend, no build server and no runtime of any kind. That is possible only because an MCP application needs neither a model nor a server in order to render: it needs something willing to answer the host side of a postMessage conversation, and 250 lines of JavaScript can do that.

Which demonstrations model what

The thirty demonstrations on this site are two different things, and the difference matters when you read their transcripts.

The thirteen recipes model the whole lifecycle. Each has a real MCP server with a ui:// resource and a tool carrying _meta.ui.resourceUri. The host emulator resolves the view the way a host does: tools/list, read the resource URI off the descriptor, resources/read, render what comes back. Their transcripts open with four host-to-server lines before the view has run a single statement, and the frame above them is rendering the document that arrived on line four.

The seventeen capability labs start after the binding. They have no server, no tool and no resource, because each exists to demonstrate one chapter’s capabilities rather than the resource lifecycle. Chapter 6’s lab is about ui/notifications/size-changed, and prefixing it with a tool call it does not have would be scenery. Their transcripts open at ui/initialize.

That split is deliberate, and stating it is the point: a lab that loaded itself by URL while the book insisted hosts never know a URL would be the same defect this chapter exists to guard against.

What the transcript pane is for

It is a teaching device and a test artifact at the same time, and the second use is what keeps the first honest. The log you read on the page is the same log check_demos.mjs records when it drives that page in headless Chrome.

The log you see on a page is the same log tools/check_demos.mjs records into conformance/transcripts/ when it drives the same page in headless Chrome. Layer 1 of Chapter 26 is literally the thing on screen. When a recipe entry says “selecting a row sends exactly one ui/update-model-context”, you can verify it by selecting a row, and the build verifies it by diffing a file.

The fixture chain, exactly

The claim that these demonstrations are honest rests on one chain, and the chain is short enough to state completely and check yourself.

Each recipe has a server.js that is a real MCP server over stdio. It answers initialize by declaring the UI extension, tools/list with descriptors carrying _meta.ui.resourceUri, tools/call by running the tool, and resources/read by returning the view’s HTML with its content security policy attached.

tools/record_fixtures.mjs starts that server as a child process, sends the calls listed in the recipe’s record.json, and writes the responses to fixtures.json. Nothing in that file is hand-written and nothing is edited afterwards, and make fixtures regenerates all thirteen on every build, so a server whose output changes produces a fixture diff in the same commit.

The demonstration’s host configuration imports fixtures.json and answers tools/call from it. So when the Data Explorer renders eight deployments with a worst p95 of 1290ms, those numbers came out of the server whose source is in the next tab.

What is not true is that the server is running in your browser. It is not, and it could not be: a static site has no process to run it in. The fixture is a recording, and the check that keeps the recording current is that make fixtures regenerates it from the server on every build.

Running this against your host

The suite is deliberately unexotic, and porting it to another host is smaller than it looks. Nothing in it depends on the emulator’s internals; it depends on a host that answers ui/initialize honestly and can be told to do host-side things on command.

The demonstrations do not depend on the emulator’s internals. They depend on a host that answers ui/initialize, applies capability rules honestly, and can be told to do host-side things on command: change the container, withdraw a display mode, deliver a tool result, start a teardown. Any host with a development mode can expose those.

The harness depends on three things: a page it can load, a way to observe the message log, and a way to click host-side controls. In this repository the log is in the DOM because the demo widget puts it there. In another host it would more likely be a hook that receives every message, which is easier rather than harder.

What does not port, and is the honest limit from Chapter 26, is driving the view’s own interface. That needs either the view’s registered tools or a host willing to grant allow-same-origin in a test configuration, and the first is the better answer because it is the same mechanism agents and accessibility tools use.

Try this on any page

Three things to do once, in any demonstration on this site. Between them they make the whole architecture visible in about a minute, and none of them needs anything installed.

Open Messages and reload the view. Watch ui/initialize go out, the result come back, ui/notifications/initialized follow, then ui/notifications/size-changed. Four lines, and every MCP application starts the same way.

Press a control in the grey strip. Those are the things only a host can do, so the page does them on the host’s behalf, and each one produces a message you can expand and read.

Then open the index.html tab and find the code that handled it. The file the tab shows is the file the frame above is running, fetched from the same URL, which is the one guarantee that makes a book about a protocol worth reading two months after it was written.

What this book does not do

Two escalations beyond what is here exist, and neither is built. Both would make the demonstrations editable rather than merely runnable, and both are additive: neither changes anything the book claims.

Small client-only examples can be made editable in place with an in-browser bundler, so a reader can change app.tsx and watch the iframe re-render. That needs a custom template carrying the bridge shim, and it is the obvious next step for the labs.

Full server-plus-view examples can open in a browser-based Node runtime, which boots the actual MCP server in a tab and runs it against a real host. That is how the extension’s own examples run locally against its reference host, and it would turn the recipes from demonstrations into things a reader can fork without installing anything.

Neither is here. What is here is thirty applications that run, their sources, their transcripts, and a repository where all of it regenerates with one command.
