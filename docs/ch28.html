Chapter 28

The Coverage Matrix and the Checklists

What eighty-seven capabilities by thirteen recipes actually shows, why the matrix is generated, and what a host is claiming when it claims a level.

Two artifacts come out of the registry on every build, and both are more useful as diagnostics of the book than as references for a reader. A row of the matrix with no marks in it is a capability this book described and never demonstrated, which is a gap in the evidence, and it is visible only because the matrix is generated rather than written.

What the matrix shows

Appendix A carries the full capability by recipe matrix. It is generated from the registry, never hand-maintained, and reading down a column tells you what a recipe needs while reading across a row tells you how well covered a capability is.

The extremes are where the matrix says something. The middle of it is unsurprising and mostly confirms that recipes use the capabilities their entries say they use.

Rows with no marks at all. A capability that no recipe exercises is a capability this book has described and not demonstrated. There are several, and they cluster: op.pause, system.print, and the environment signals that have no visible consequence in a small view. Each is either genuinely rare or a recipe that should exist and does not.

Rows with a mark everywhere. surface.resize, env.theme and host.capabilities are in every recipe, which is what “Level 1” means in practice. If a host gets those three wrong, nothing in Part V renders.

Columns that are unusually short. A recipe that touches few capabilities is either focused or thin. Recipe 5’s column is short and it is focused; Recipe 2’s is short and could carry more.

The delta diagonal. Reading the deltas in order shows the book’s argument as a shape: the first recipe claims sixteen capabilities, and by the thirteenth the deltas are down to a handful each. That taper is the evidence for the completeness claim. If the thirteenth recipe still needed six new primitives, the model would not be converging.

Why it is generated

A hand-maintained matrix is wrong within a week and nobody notices, because nothing reads it. A generated one is wrong only if the registry is wrong, and the registry is what everything else reads.

The generation also enables checks that a document cannot make. The build reports capabilities with no entry in any chapter, which is how the missing tool.cancel entry in Chapter 20 was found. It could equally fail on a Core capability with no covering recipe, which is the check a mature version of this suite would run in CI.

The matrix itself is twelve lines. Every cell is a set membership test against the registry, so a mark on the page means a recipe declared that capability and nothing else can put one there:

What a level claim means

Appendix C turns each level into a checklist of observable behaviours. The translation from capability to check is mechanical, and the phrasing is deliberately in the form an assertion takes.

A host claiming Level 1 is claiming that a view renders, that ui/notifications/size-changed resizes the frame, that hostContext carries a theme and a locale, that ui/open-link works or is honestly absent from hostCapabilities, and that ui/initialize returns a capability set that matches what the host will actually do.

That last clause fails most often, so state it as a rule. A capability advertised and not implemented is worse than one never advertised. A host that lists downloadFile and then ignores ui/download-file breaks every view that checked hostCapabilities and rewards every view that did not.

Level 2 adds the interactive set, and the checks are mostly about the host staying out of the way: that keyboard events reach the frame, that the frame’s focus ring is not clipped by host styling, that a context menu inside the frame is not shadowed by the host’s own.

Level 3 is where hosts diverge most. Display modes, lifecycle signals, and the persistence gap all live here, and a host can be excellent at Levels 1 and 2 while implementing none of Level 3. That is a legitimate position for a host whose views are all cards.

Level 4 is the agentic set, and it has the largest gap between what the checklist asks and what the specification provides. Ten Core capabilities across all levels have no standard mechanism, and Appendix C marks each of them, because a checklist that asked hosts to implement something unspecified would be worthless.

If you are building a host

The useful order is not top to bottom. It is:

  1. Make the handshake truthful. Every other recommendation in this book assumes it. A capability listed in hostCapabilities and not implemented breaks precisely the views that checked properly and rewards the ones that never checked.
  2. Get surface.resize right, including the zero-height first render. More views look broken because of this than because of anything else in the protocol.
  3. Get ui/resource-teardown right, including waiting for the response. This is the only data-loss defect in the protocol that a view cannot work around.
  4. Then work down the levels, and publish which one you pass with the date of the run.

That order is not the order of the checklist, and it is deliberately not the order of the levels. Those three come first because a failure in any of them makes the levels above meaningless: a view that never sized itself correctly does not care how good your display mode support is.

If you are building an application

The order is different. Assume Level 1, check for everything above it, and make the check the thing that decides whether a control exists.

Then use the failure column of the recipe entries in Part V as a design prompt. Every one of those tables was written by asking, for each capability, what the application looks like without it. That exercise takes an hour and produces most of the progressive enhancement work you were going to do anyway, before the code makes it expensive.

Reading the deltas in order

The delta column is the load-bearing part of the matrix, and reading it in recipe order is the closest thing this book has to evidence for its own premise.

Recipe 1 claims sixteen capabilities, because it is the baseline: a table, a selection, an export, an escalation. Recipes 2 and 3 add roughly a dozen each, because monitoring and hierarchy are genuinely different surfaces. By Recipe 7 the deltas are down to three or four, and by Recipes 11 to 13 most of what each one needs is already in the model.

That taper is what convergence looks like. If the thirteenth recipe still needed six new primitives, the honest conclusion would be that eighty-seven is not enough and the model is still growing. It does not, which is weak evidence that the surface has been covered.

Weak, and worth being precise about why. The recipes were written by the same person who wrote the capability list, against one emulator, in one sitting. Convergence under those conditions could equally mean the recipes were chosen to fit. The test that would settle it is Layer 5 from Chapter 27: someone else’s application, someone else’s host, and a delta that still comes out small.

The matrix is evidence, not proof

One last use. The matrix is the closest thing this book has to a proof, and it is not one. What it shows is that thirteen recognisable applications were built from eighty-seven named primitives, that the primitives were sufficient for all thirteen, and that sixteen of them had to be worked around because no mechanism exists.

That is evidence for the completeness test in Chapter 26 and not an answer to it. The answer needs Layer 5 from Chapter 27: the same recipes, unmodified, running in hosts that were not built alongside them.

Using this on your own project

The exercise transfers, and it is cheap. Take your application, list the interactions it has, and map each one to a capability identifier from Appendix A. Three things fall out within an hour.

The host dependency list. Everything you mapped to a wire capability is something a host has to support, and the level column tells you which hosts those are. That list is what you test against, and it is usually shorter than people fear.

The gap list. Anything you mapped to a not standardised capability is a place where you are about to invent a private convention. Better to know before the code than after the second host.

The work list. Everything mapped to yours to build is real engineering that no protocol will do for you, and it is typically the largest of the three. Undo, dialogs, toasts and the whole attention system live here.

An interaction that maps to nothing is the interesting case. Either you have found something the eighty-seven do not cover, which belongs upstream as a finding, or you have described an interaction in terms of your implementation, and never what the user does. Chapter 29 is about telling those two apart.
