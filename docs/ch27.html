Chapter 27

The Verification Layers

Six layers, from a schema to a cross-host dashboard, and an honest account of which of them this repository actually runs.

Six layers, because the failures are layered. A malformed message, an inaccessible combobox and a host that ignores display mode requests are three different problems, they are discovered by three different kinds of machinery, and no single check finds all three. A suite with one layer therefore has a blind spot the size of the other five, and the usual missing layer is the one that looks at pixels. Five of the six run here. The sixth needs hosts this repository does not control, and it is the one that would matter most.

For each layer this chapter says what this repository runs today and what it does not. The second half matters: describing an aspirational test pyramid and shipping none of it is exactly what Chapter 26 argues against.

Layer 0: Schemas

Capability manifests and every bridge message validate against JSON Schemas derived from the extension specification, so nothing untyped ships. This is the cheapest layer to build and the one that catches the errors nobody notices: a field renamed in a draft, a message shape that drifted, an identifier that exists in the prose and nowhere else.

What runs here. The registry is generated from a single Python source and every downstream artifact reads the generated JSON, so an identifier that exists in one place and not another is impossible by construction. tools/check_claims.py goes further and greps the pinned specification text for every message name the registry claims exists: sixty-eight claims, checked on every build.

That check has already earned itself. It reports which anchors exist in the current draft but not in the last dated release, and the answer is eight: ui/download-file, downloadFile, ui/notifications/request-teardown, updateModelContext, sampling/createMessage, notifications/tools/list_changed, resource_link and isError. A book that did not check would have described all eight as though they were settled.

What does not run. Full JSON Schema validation of every message against the SDK’s generated schema. The bridge here validates shape by construction.

Layer 1: Protocol transcripts

Because every message is JSON-RPC over postMessage, a scenario can be replayed and its message log diffed. That is a stronger property than it sounds: the wire is the whole interface between a view and its host, so a transcript that has not changed is a view that behaves identically from the host’s side. A transcript diff in a pull request is a protocol change somebody has to explain.

What runs here. tools/check_demos.mjs drives all thirty demonstrations in headless Chrome over the DevTools Protocol, waits for the handshake, clicks every host control in order, and records the normalised message log to conformance/transcripts/. Timings and request ids are stripped, object keys are sorted, and the result is compared byte for byte with the committed file.

A missing handshake is a hard failure, for the reason Chapter 26 gives: a view that never sends ui/initialize is a view whose script never ran, and nothing else about it can be meaningfully checked. Any console error that is not a missing favicon fails the run as well.

Layer 2: Capability harness

One minimal application per capability group, driven inside a reference host, with assertions on both the observable behaviour and the message log. The point of keeping them minimal is diagnostic: when a lab fails there is one capability in it, so the failure names itself.

What runs here. The seventeen labs are that harness. Each exercises a single chapter’s capabilities, carries a fixture host with controls for the things only a host can do, and has a recorded transcript that the build diffs. Keeping each lab one chapter wide is what makes a failure legible: when one breaks, the set of things that could have broken it is small enough to read.

What does not. They run against the emulator in this repository, not against the basic-host that ships with the official SDK. Running the same labs against that host is the obvious next step and would convert a set of assertions about this book’s host into assertions about a reference one.

Layer 3: Component checks

An axe-core audit of every recipe, run inside the sandboxed frame after the interactions rather than on load, so it sees the interface the interactions produced. axe-core is vendored into tools/vendor/ rather than installed, because this repository has no npm dependencies and an accessibility audit is a poor reason to acquire the first one.

Rules that assume a page are disabled by name, with a reason each. A view is a fragment inside somebody else’s document. The host owns <main>, the landmark structure and the heading outline, so landmark-one-main, page-has-heading-one and region are not defects here; a view that declared its own <main> would be adding a second one to the host’s page. The list is four rules long and each carries its reason in the source, which is a different thing from a suppression file nobody reads. Anything else that fires fails the build, and a per-case allowance that stops firing also fails, so an allowance cannot quietly outlive the defect it excused.

What it found on the first run. Five defects across four recipes. The monitoring console put aria-selected on plain div elements, which no role there permits, and its scrolling log had no keyboard focus. The diff reviewer’s line numbers were under 4.5:1 against the tinted add and delete rows. The spreadsheet’s corner cell was an empty column header. And the image annotator’s labels used a fixed white on a background the user picks, so any light annotation colour produced unreadable text; that one is now computed from the chosen colour’s relative luminance.

What still does not run. The components are a shared stylesheet and helper file, and there is no component library with stories, so each component is audited only in the recipes that use it. Screen reader output was walked by hand and is recorded per recipe rather than claimed in aggregate here, because no automated tool reports what a screen reader actually says.

Layer 2b: Render conformance

Reaching into a frame with an opaque origin needs one Chrome DevTools Protocol call, and without flatten: true the sandboxed frame’s execution context is not addressable at all:

Extracted from from tools/check_render.mjs

  await browser.send("Target.setAutoAttach",
    { autoAttach: true, waitForDebuggerOnStart: false, flatten: true });
  await browser.send("Page.enable");
  await browser.send("Runtime.enable");

That the harness has to go outside the page to see inside the frame is the same fact Chapter 5 states as a security property. The sandbox is doing its job; a test is simply another party the boundary keeps out, and the way in is a debugger rather than a hole in the sandbox.

The layer the first edition of this suite did not have, and the one the book is actually about. Everything above verifies messages. This verifies the interface the messages produce, which is the thing a user sees and the thing none of the other layers can observe. It found four defects on its first run, and three of them were invisible to every message-level check in the suite.

For each of the thirteen recipes, tools/check_render.mjs runs the whole chain with no recording anywhere in it. Six steps, and the fourth is the one that makes the rest meaningful:

  1. Start the recipe’s MCP server as a child process over stdio.
  2. Perform the host’s initialize, declaring the UI extension, so a server is free to register different tools when it is absent.
  3. Call tools/list and read _meta.ui.resourceUri off the tool.
  4. Fetch the view’s HTML through resources/read. That is what the frame renders. Nothing is read from apps/ or from the built site.
  5. Call the tool. Deliver the arguments and result as notifications.
  6. Proxy the view’s own tools/call back to the same server, and forward that server’s progress notifications onward.

Then it asserts on the DOM inside the sandboxed frame: row counts, cell text, which element carries aria-current, whether the error banner is hidden. 110 assertions across the thirteen recipes, followed by an axe-core audit of each. Reaching inside that frame at all takes Target.setAutoAttach with flatten: true, because the frame has an opaque origin and no ordinary evaluation crosses into it, which is the same boundary Chapter 5 describes doing its job.

Captured output from node tools/check_render.mjs

  r01-data-explorer: 18 assertion(s) on rendered output
  r04-document-editor: 12 assertion(s) on rendered output
  r07-workflow-builder: 15 assertion(s) on rendered output
13 case(s), 108 assertion(s) against real servers, 13 audited by axe-core, 0 failing

No model appears in those six steps. A host connects to servers, allocates surfaces and mediates privileged operations, and none of that requires an LLM. A host driven by conformance/render/r01-data-explorer.json is the same architecture as a host driven by a person, which is why the surface is testable at all.

How it reads into the frame. Over the DevTools Protocol, not from page script. Page script cannot: the frame has an opaque origin, which is precisely the property that stops a host reading a view, and Chapter 5 is about why that is correct. A debugger is not page script, and attaching to the child frame gives a session that can evaluate inside it. The sandbox that ships is not weakened; the harness is simply outside the model the sandbox defends against.

That also closes a limitation this chapter used to state. The harness can click inside the view, so a recipe no longer has to register tools in order to be driven. Cases in conformance/render/ interleave three kinds of step: a click inside the frame, a call to one of the view’s registered tools, and a change to the host context, each followed by assertions.

Layer 4: Recipe integration

Each recipe end to end against a scripted mock agent, with recorded tool results, deterministic streaming and deliberate fault injection. The fault injection is the part that earns its keep: capabilities withdrawn mid-session, servers that fail, calls cancelled halfway, teardown with unsaved work.

What runs here. All thirteen recipes are driven by the same harness as the labs, with fixtures recorded from their real servers by tools/record_fixtures.mjs. The fault injection is real: controls that break the server, withdraw capabilities, cancel mid-flight, and tear the view down are part of every recipe’s demonstration and are exercised by the harness.

What each of the two browser layers covers. The transcript layer drives the published demonstrations from the host side, which is what verifies the message log. The render layer drives the recipes from a live server and reaches inside the frame, which is what verifies the interface. Between them a recipe is checked on both halves of the promise it makes.

Registering tools is still worth doing, and Chapter 19 gives three reasons that survive: an agent can drive the view, an accessibility tool can drive it, and a test can express an intention. A case that calls connect_steps says what it means; a case that clicks a coordinate says where a button happened to be.

Layer 5: Cross-host conformance

The same suite run against several hosts, with results published per host and per capability the way the public web platform test dashboards do it. That format matters as much as the results: a per-feature, per-implementation grid is what lets somebody write portable code without guessing.

What does not run. Nothing. This book runs against one emulator. The basic-host in the extension SDK, the MCP-UI client, and the production hosts that implement the standard are all candidates, and the checklists in Appendix C are written so that they could be run against any of them.

The reason this matters more than the missing Layer 3 is that cross-host results are the only evidence that would answer the completeness test in Chapter 26. One host running thirteen recipes proves the recipes work. Several hosts running them unmodified proves the capability model is general, which is the claim the whole book is making.

What one run looks like

node tools/check_demos.mjs starts a static server over docs/, launches headless Chrome, and for each of the thirty demonstrations opens the harness page, waits for ui/initialize and ui/notifications/initialized to appear in the log, clicks every host control in order with time to settle, and then reads the transcript back out of the DOM.

The log is normalised before comparison: request ids and timings are dropped because they vary, and object keys are sorted because insertion order is not meaningful. What is left is a list of direction, method and payload, which is the part that is supposed to be stable.

Captured output from node tools/check_demos.mjs

  lab-surface: 10 messages
  lab-theme: 11 messages
  r01-data-explorer: 9 messages
  r07-workflow-builder: 20 messages
  r13-settings: 11 messages
30 demos driven, 0 transcripts written, 0 failing

“0 transcripts written” is the assertion. The harness runs in a mode where a matching transcript writes nothing, so a demonstration whose behaviour changed fails the run and leaves the diff of its transcript file as the description of what the change actually was. Regenerating is a deliberate command, which keeps an accidental behaviour change from silently becoming the new baseline.

The checks that are not about the protocol

Four more checks run on every build, and between them they catch a class of error that no browser test can see: prose that has drifted from the code, the specification, or the repository it describes.

check_refs.py verifies that every figure the prose asks for exists, that every capability in the registry has exactly one defining entry, and that every @demo names a directory that is really there. It found the missing tool.cancel entry.

check_listings.py takes every code block tagged extracted from a file and checks it against that file line by line. It found two listings that had been quietly abridged and presented as extracted, which is the specific failure mode of a book that quotes its own repository: the code was real when it was copied, somebody shortened it for the page, and nothing anywhere recorded that the two had diverged.

check_counts.py recomputes every number the prose asserts about the repository and fails when the prose disagrees. It found the Core capability count wrong in Chapter 1, which had been written from an estimate, and it found the level 3 total wrong in two appendices after a capability moved between levels. Both are the kind of error that no reader would catch and every reader would be misled by.

check_identifiers.py pulls every protocol identifier out of the prose and requires it to appear in the pinned specification, the SDK, or this repository’s own source. Two hundred and three identifiers, and the reason it exists is that a plausible-looking field name reads as a fact and is not one.

The layer that is not on the list

Human usability sessions. None were run for this edition, and none of the design claims here are backed by watching somebody use these applications. The recipes are built to a set of principles with arguments behind them, and the arguments could be wrong in ways no automated check would detect.

That is the largest single gap in this book’s evidence, larger than Layers 3 and 5 combined, because those two would confirm that the applications work while this one would tell you whether they should exist in that shape at all.
