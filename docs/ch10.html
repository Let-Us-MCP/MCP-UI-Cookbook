Chapter 10

Keyboard, Pointer and Selection

Nine capabilities, one message between them. The browser does almost all of this, which is why the two places it stops are worth naming.

Nine capabilities and one message between them. Eight are the browser working normally inside the sandbox: no host round trip, no permission, nothing to negotiate, and no reason for any of it to involve a model. This is the group where Chapter 4’s principle is least ambiguous, because there is not even a plausible argument for crossing the boundary to sort a list.

Two of them stop at the frame boundary, and those are the ones worth your attention: a shortcut the host may already own, and a drag that cannot leave your view.

How do I make dragging work?

input.pointerCoreLevel 1Platform

Click, hover, drag, and capture across mouse, touch, and pen.

Ground
The browser inside the sandbox provides it. No host round trip.
Recipes
Data Explorer, Image Annotator
Demo
lab-input

Call setPointerCapture(event.pointerId) on pointerdown. Without it the element receives events only while the pointer is inside its own box, so any drag that moves faster than the layout updates leaves the element behind and the gesture dies mid-motion. With capture, every subsequent event for that pointer id is routed to the capturing element until you release it, which means the drag survives leaving not only the element but the frame.

Use Pointer Events rather than mouse events with touch handlers bolted on. They unify mouse, touch and pen, which is the whole reason they exist.

Extracted from from apps/labs/lab-input/index.html

dot.addEventListener("pointerdown", (event) => {
  dragging = true;
  dot.setPointerCapture(event.pointerId);
  offset = { x: event.offsetX, y: event.offsetY };
});
dot.addEventListener("pointermove", (event) => {
  if (!dragging) return;
  const box = pad.getBoundingClientRect();
  dot.style.left = `${Math.max(0, Math.min(box.width - 22,
    event.clientX - box.left - offset.x))}px`;
});
dot.addEventListener("pointerup", (event) => {
  dragging = false;
  dot.releasePointerCapture(event.pointerId);
});

Two more details that only show up on real devices. touch-action: none on the draggable surface stops the browser interpreting a drag as a scroll, which otherwise makes touch dragging impossible. And targets need to be bigger: WCAG 2.2 sets the floor at 24 by 24 CSS pixels at AA, and 44 by 44 at AAA, which is also the long-standing platform convention. Chapter 13 gets the modality from hostContext.deviceCapabilities.touch rather than from a user agent string.

Which keys are mine?

input.keyboardCoreLevel 2Platform

Keys, modifiers, and the platform conventions users already have.

Ground
The browser inside the sandbox provides it. No host round trip.
Recipes
Data Explorer, Spreadsheet, Code and Diff Reviewer
Demo
lab-input

Keys, modifiers, and the platform conventions your users already have from every other application. Two rules cover most of it: read event.key rather than the long-deprecated keyCode, which reports the wrong thing on non-US layouts, and treat event.metaKey || event.ctrlKey as one modifier rather than branching on the platform.

Use the platform’s modifier, not one of them. event.metaKey || event.ctrlKey is the whole of cross-platform accelerator handling and there is no excuse for getting it wrong. Read event.key rather than keyCode, which has been deprecated for a decade and reports the wrong thing on non-US layouts.

Escape needs an explicit rule, because in an embedded view it has at least four plausible meanings and only one of them is yours at any moment. It can close your dialog, clear your selection, leave fullscreen, or mean something to the host that you cannot see. Calling preventDefault() unconditionally takes all four.

Handle it only when you have something open, and call preventDefault() only then. Otherwise let it propagate:

Illustrative, not run

if (event.key === "Escape" && dialog.open) {
  event.preventDefault();
  dialog.close();
}

Can I bind Cmd+F?

input.shortcutCoreLevel 2Not standardised

Own an accelerator without fighting the host for it.

Ground
No standard mechanism exists yet. The entry carries a workaround.
Recipes
Document Editor, Spreadsheet
Demo
lab-input

You can, and so can the host, and there is no way for either of you to find out which one won. Whoever calls preventDefault() first keeps the chord, and “first” depends on where focus happens to be when the key is pressed, which the user changes constantly without thinking about it.

No negotiation exists anywhere in the extension. There is no list of reserved chords in hostContext, no request to claim one, and no notification when you collide. From the user’s side the symptom is not an error but an inconsistency: your find bar opens when focus is inside the frame and does not when it is not, and they have no way to predict which.

Whoever calls preventDefault() first wins, and “first” is decided by whether the event reaches your frame at all, which depends on where focus is. From the user’s side this reads as an application that sometimes has a find bar and sometimes does not.

Take few, and take the document ones:

Bind Leave alone
Cmd/Ctrl+Z, Shift+Cmd/Ctrl+Z Cmd+T, Cmd+W, Cmd+L, Cmd+R
Cmd/Ctrl+C, Cmd/Ctrl+S Any bare letter with no modifier
Escape, Delete, F2 in context Cmd+Shift+anything the host may own

Never bind a bare letter: the user is probably typing. Recipe 4 binds four chords and shows all four on its toolbar, because a shortcut nobody can see is a shortcut nobody uses.

What a mechanism would look like. The host declares reserved chords in hostContext, and the view either avoids them or requests one and is told whether it got it. Neither exists. In the demonstration, press Cmd/Ctrl+F: the view takes it, and the host it is embedded in may or may not agree.

How do I do a context menu?

Demo

input.contextmenuCoreLevel 2Platform

Contextual actions on right click or long press.

Ground
The browser inside the sandbox provides it. No host round trip.
Recipes
File Explorer, Workflow Builder
Demo
lab-input

These are one intent expressed on two modalities: “give me the actions for this thing”. A mouse user right-clicks, a touch user presses and holds, and both expect the same menu in the same place with the same items. Building them as two features produces two menus that drift apart.

Application behaviour. Handle contextmenu with preventDefault() and draw your own menu. Position it in the viewport, keep it inside the frame, close it on Escape and on outside click, and move focus into it so a keyboard user can reach it. On touch, a pointerdown timer of roughly 500ms with cancellation on move or up gives the same menu.

The boundary. Your preventDefault() suppresses the browser’s menu inside your frame. It does not suppress the host’s, if the host has one, and it cannot tell the host that a menu is open. A host that also shows a menu on right click produces two menus, and neither party can currently detect the other. In practice hosts do not do this, but nothing in the protocol prevents it.

Accessibility. A context menu that only opens on right click is unreachable for keyboard users. Give it a second route: Shift+F10, or a visible button, or both. role="menu" with role="menuitem" children, arrow key navigation, Escape to close and return focus.

How do I do selection properly?

input.selectionCoreLevel 2Platform

Single, additive, range, and select-all over text and objects.

Ground
The browser inside the sandbox provides it. No host round trip.
Recipes
Data Explorer, File Explorer, Spreadsheet, Workflow Builder, Code and Diff Reviewer, Monitoring Console
Demo
lab-input

Three gestures, and users bring all three from every other application they have ever used. They notice immediately when any is missing, because the absence does not read as a missing feature; it reads as a broken table. The implementation is about twenty lines and the demonstration below has all of it.

Click replaces the selection and sets the anchor. Cmd/Ctrl-click toggles one item and moves the anchor. Shift-click extends from the anchor to the clicked item.

Extracted from from apps/labs/lab-input/index.html

function select(i, event) {
  if (event.shiftKey) {
    const [lo, hi] = [Math.min(anchor, i), Math.max(anchor, i)];
    for (let k = lo; k <= hi; k += 1) selected.add(k);
  } else if (event.metaKey || event.ctrlKey) {
    selected.has(i) ? selected.delete(i) : selected.add(i);
    anchor = i;
  } else {
    selected.clear();
    selected.add(i);
    anchor = i;
  }
}

The keyboard model is the other half: arrows move, Space toggles, Shift with arrows extends, Cmd/Ctrl+A selects everything, Escape clears. Together they are about twenty lines and they are the difference between a table and a picture of a table.

Accessibility. role="listbox" with aria-multiselectable, or role="grid", and aria-selected on each row. Announce the count on change, not the individual rows, or a screen reader user selecting forty rows hears forty announcements. The lab does exactly one announcement per change.

The other reason selection matters. It is the unit of conversation. Chapter 18’s escalation carries the selection, and Recipe 8 makes a range of diff lines the thing the model is asked about. A view with no selection model has nothing precise to escalate, so its users end up describing what they mean in prose.

How do I do drag and drop?

input.dragdropCoreLevel 2Platform

Drag and drop inside the view, with structured transfer data.

Ground
The browser inside the sandbox provides it. No host round trip.
Recipes
File Explorer, Image Annotator, Workflow Builder
Demo
lab-input

Inside the frame, drag and drop is the HTML drag and drop API, with all of its familiar unpleasantness: dragover must call preventDefault() or the drop never fires, and dataTransfer types are the only structured channel between source and target.

For reordering within one list, pointer events are usually better than the drag API: you get pointer capture, you can animate, and you avoid the drag image entirely. Recipe 7 drags nodes with pointer events and Recipe 3 uses the drag API because it needs a drop target with feedback.

input.dragBoundaryExtendedLevel 2Not standardised

Drag something out of the view and into the host, or the reverse.

Ground
No standard mechanism exists yet. The entry carries a workaround.
Recipes
none yet
Demo
lab-input

The second boundary, and the more visible one. A file dragged from the desktop into your frame works, because the browser routes it. Anything else does not. You cannot drag a row out of your view and onto the host’s conversation. The host cannot drag one of its attachments into your view. There is no dataTransfer shared across the frame boundary and no message that carries one.

Workarounds. For getting data out: copy to the clipboard, or offer ui/download-file. For getting data in: a file input, or a paste target, or a host-proxied resources/read if the thing lives on the server anyway.

How do I do zoom and pan?

input.zoompanCoreLevel 3Platform

Wheel and pinch zoom, pan, reset, fit to content.

Ground
The browser inside the sandbox provides it. No host round trip.
Recipes
Image Annotator, Workflow Builder, Media Viewer
Demo
lab-input

For any spatial surface: wheel to zoom, drag to pan, a reset, and a fit. The reset and the fit are not optional extras. A user who has zoomed to 600% and panned into empty space has no way back without them, and in a 380-pixel frame that happens within about four wheel gestures.

The detail that separates a canvas that feels right from one that fights you is zooming about the pointer rather than the origin. The transform has to be adjusted so the point under the cursor stays under the cursor.

Extracted from from apps/recipes/r06-image-annotator/index.html

const before = scale;
scale = Math.min(6, Math.max(0.4, scale * (event.deltaY < 0 ? 1.12 : 0.89)));
const rect = stage.getBoundingClientRect();
const px = event.clientX - rect.left, py = event.clientY - rect.top;
panX = px - ((px - panX) / before) * scale;
panY = py - ((py - panY) / before) * scale;

{ passive: false } on the wheel listener is required rather than optional. Browsers default wheel listeners to passive so that scrolling stays smooth, and a passive listener that calls preventDefault() is ignored with a console warning. Without the flag your zoom appears to work in development and lets the host’s conversation scroll underneath it in production.

Accessibility. Every spatial gesture needs a non-spatial equivalent. Buttons for zoom in, zoom out, reset and fit, and arrow keys to pan. A canvas that can only be operated by dragging is a canvas that cannot be operated at all by a large number of people.

The keyboard model, in one table

This is the set users bring with them. Implementing it is about twenty lines and not implementing it is the most common reason an embedded table feels unfinished.

Key In a list or grid In a menu In a dialog
Arrow keys Move the active item Move the highlight Nothing
Space Toggle selection Activate Activate the focused control
Enter Open or activate Activate and close Submit
Shift with arrows Extend the selection Nothing Nothing
Cmd/Ctrl+A Select all Nothing Select the field’s text
Home, End First, last item First, last item Nothing
Escape Clear the selection Close, restore focus Close, restore focus
Tab Leave the widget Close, then leave Cycle inside

The row that matters most is the last one. A composite widget is one tab stop, and the arrow keys move within it. A table where Tab visits every cell is a table nobody can get past.

Conformance checks

  1. Keyboard events originating in the view are not swallowed by the host.
  2. A list of N rows presents one tab stop, not N.
  3. Shift-click and Cmd/Ctrl-click produce range and additive selection.
  4. contextmenu inside the view is not shadowed by a host menu.
  5. Pointer capture keeps a drag alive when the pointer leaves the element.
  6. A wheel listener that calls preventDefault() is honoured, so the view can zoom without the host scrolling.
  7. Every gesture in the view has a keyboard equivalent.

What to remember

Nine capabilities and one line of protocol between them. The lesson is not that this group is easy; it is that the effort belongs in your view rather than in the channel. When something here does not work, the answer is almost never a message you are missing.
