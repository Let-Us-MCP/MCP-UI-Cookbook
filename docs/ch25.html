Chapter 25

Components III: Spatial, Media and Agent-Native

Canvases in a small frame, transports you should probably not replace, and five components that exist only because there is a model in the room.

Two familiar groups, then five components with no precedent anywhere in web design. Spatial and media components you have built before and mostly port unchanged. The last five could not have existed before there was a second party acting on the interface, so there is no established pattern to copy and every agentic application ends up inventing them badly at least once.

Spatial

Component Composes APG pattern
Canvas input.pointer, input.zoompan, surface.viewport (application)
Node graph input.dragdrop, input.selection, input.zoompan (application)
Bounding box editor input.pointer, input.zoompan, history.transaction (application)
Image annotation input.pointer, file.dropzone, file.export (application)
Minimap input.pointer, surface.viewport (decorative)

Report a fixed height and scroll inside it. Recipe 6 uses 260px, Recipe 7 uses 280px, both chosen to work at 380px wide. A canvas that grows with its content fights surface.resize and loses.

Pointer capture, touch-action: none, and zoom about the cursor. All three in Chapter 10, and all three are the difference between a canvas that feels right and one that fights.

Add a minimap. Recipe 7 draws one into a 220 by 148 <canvas> in eleven lines: fillRect per node, strokeRect for the viewport.

Every gesture needs a button. Zoom in, zoom out, reset, fit, and arrow keys to pan. A canvas operable only by dragging cannot be operated at all by a significant number of people, and this is the component group where that failure is both most common and least noticed, because the developer testing it always has a pointer.

Undo per gesture, not per frame. A drag produces one transaction on pointerup, not sixty during pointermove. Recipe 7 records the start position on pointerdown and pushes a single transaction at the end.

Media

Component Composes APG pattern
Player transport media.playback, input.keyboard Toolbar, Slider
Scrubber media.playback, input.pointer Slider
Caption selector media.playback, input.keyboard Listbox
Thumbnail strip input.selection, input.keyboard Tabs, Listbox

Use the native controls unless you have a reason. <video controls> handles keyboard, screen readers, captions, picture-in-picture and playback rate in zero lines.

Replace them and you inherit the contract: Space to play, arrows to seek, aria-valuetext on the slider in minutes and seconds, and aria-pressed on the caption toggle. Recipe 12 does all of that in about 40 lines and is still worse than the native set.

The aria-valuetext line is the one that is always missing:

Extracted from from apps/recipes/r12-media-viewer/index.html

  $("#seek").max = String(clip.seconds);
  $("#seek").value = String(at);
  // A range input announces its raw value, so a seek bar reads as "1601" to a
  // screen reader unless you say what the number means. This is the most
  // common defect in custom transports.
  $("#seek").setAttribute("aria-valuetext",
    `${clock(at)} of ${clock(clip.seconds)}`);

A <input type="range"> announces its numeric value and nothing else, so a seek bar at eighty seconds reads as “80” with no unit and no total. The render harness asserts the announced string, which is the only way this stays fixed: the visible clock and the announced text are computed from the same clock function, so they cannot disagree.

Pause when hidden. Chapter 15. Audio continuing from a frame nobody can see is genuinely alarming, and it is the fastest way to make a user close a conversation.

Fullscreen goes through the host. ui/request-display-mode, not the Fullscreen API, because fullscreen is not in the extension’s permission set. Chapter 17.

A thumbnail strip is a tab list. Give it roving tabindex, aria-current on the selected item, and real labels, and no image alt text that says “thumbnail”.

Agent-native

An approval card is a rendering problem with a content problem underneath it. Recipe 10’s server sends five fields per request, and the card’s whole job is to make them readable in the order a person decides in:

Extracted from from apps/recipes/r10-approval-center/server.js

    id: "refund-8841", title: "Refund 1,240.00 USD", risk: "high",
    at: "2026-08-18T09:12:00Z",
    description: "Refund invoice 2026-0814 to Meridian Systems in full.",
    consequence: "The money leaves today and cannot be recalled from here.",
    question: "Which invoices does this refund cover?",

consequence and question are the two that separate this from a notification. The first says what becomes true and whether it is reversible; the second is a prompt the card can hand to the conversation, so a user who is not ready to approve has somewhere to go other than Deny.

These five have no conventional web precedent because the situation they address is new: an interface with a second actor in it that the user cannot see and cannot interrupt. Each one exists to make some invisible part of that situation visible.

Component Composes Where it appears
Approval card approval.request, dialog.confirm, agent.contextUpdate Recipe 10
Tool status chip tool.invoke, op.progress, op.cancel, op.error Recipes 9, 11
Streaming log tool.partialOutput, input.selection, a11y.announce Recipe 9
Context inspector agent.contextUpdate, agent.boundary Every demonstration
Proposal card ui.prefill, history.transaction, state.ownership Recipes 4, 7

The approval card is a heading, a consequence sentence, a <dl> of five provenance fields, and two buttons. Recipe 10 renders “asked by”, “on behalf of”, “tool”, “arguments” and “prior approvals”. High risk adds a second confirmDialog. Without those fields users learn to click through it.

The tool status chip carries a name, one of five states, a progress value and exactly the controls that state allows. Queued has none. Running has Cancel. Failed has Retry. Cancelled and Done have neither. Recipe 11 puts the state name in text, not only in colour.

The streaming log is the append-only list from Chapter 24 with the selection and follow behaviour that terminals taught everybody: follow the tail until the user scrolls up, then stop following and say so. Recipe 9 turns following off automatically when the user scrolls away from the bottom, which is the behaviour nobody notices when it is right.

The context inspector shows what the view has published to the model. It is a debugging tool that deserves to ship. A user who can see that the assistant knows about three selected rows and nothing else can predict what it will say, and the same panel is how a developer finds out that their view has been publishing hover state for a week. Every demonstration in this book has one, in the form of the “Show what the model was told” control.

The proposal card is the shape that makes agent editing safe. The agent’s version, visible next to the current one, with Accept and Decline, and accepting recorded as one undo transaction. Chapters 19 and 21 both arrive at it, from prefill and from conflict policy respectively, which is a decent sign that it is the right primitive.

Definition of done, for each

No reference implementation exists for any of these five, and no design system has a page about them, so here is a definition of done for each. They are all small; the difficulty is knowing what to include.

Approval card. Renders a title, a risk level, a consequence sentence, and a provenance list of at least four fields. Approve and Deny are both single actions; high risk adds a confirmation. Every decision produces exactly one context update carrying the outcome and nothing else. It never accepts an approval over its own tool interface.

Tool status chip. Carries a name, one of five states, a progress value when it has one, and exactly the controls that state allows. Queued has none. Running has Cancel. Failed has Retry. Cancelled and Done have neither. The state name is visible as text, not only as a colour.

Streaming log. Appends, trims to a cap, and never rebuilds. Follows the tail until the user scrolls away, then stops and shows that it has stopped. Selection is by identifier so it survives the next thousand lines.

Context inspector. Shows the last payload published to the model, verbatim, and says when nothing has been published. It is one control and about ten lines, and it is the fastest way to find out that a view has been leaking hover state for a week.

Proposal card. Shows the agent’s version next to what is currently there, with Accept and Decline. Accepting is one undo transaction. The tool that created it returns “proposed, not applied”, so the agent does not report a change that has not happened.

What all five have in common

Every agent-native component makes an invisible thing visible. What the model was told. What it is doing. What it is proposing. What it wants permission for. What it has been told before.

That is the design brief for this whole layer, and it comes out of the same constraint the rest of the book keeps hitting: the two parties cannot see each other. The user cannot see the model’s context. The model cannot see the screen. Components that surface one to the other are the ones that make an agentic interface feel like a place.

Conformance checks

  1. A spatial surface reports a stable height rather than growing with its content.
  2. Every pointer gesture has a button or key equivalent.
  3. A drag produces one undo transaction, not one per pointer event.
  4. Media pauses when the frame is hidden.
  5. Immersive playback goes through ui/request-display-mode.
  6. An approval card renders provenance, and its decision produces exactly one context update.
  7. A streaming log appends and trims, and never rebuilds its container.
  8. Every agent-initiated change is announced once and is reversible.
