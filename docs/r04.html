    Recipe 4

    Document Editor

    The recipe where the agent writes too. Undo, autosave through a tool, a teardown that flushes, and a rewrite that has to be proposed rather than applied.

    r04Document EditorNeeds level 4

    Authoring with agent-assisted rewriting.

    Capability delta

    All capabilities
    history.transactionhistory.undohistory.redostate.savestate.restorelifecycle.dirtylifecycle.beforeClosestate.ownershipstate.conflictui.prefillui.highlightinput.shortcutagent.samplingsurface.close

    This is the recipe the ownership model in Chapter 21 was written for, and the one where the gaps in Chapter 16 hurt most. It is also the clearest demonstration of why undo is the safety mechanism that makes agentic editing acceptable.

    What stays local, what crosses

    Normally local Worth crossing
    Type, format, undo, redo “Rewrite this to be shorter”
    Autosave “Check these dates against the ticket”
    Find “Draft a reply to the vendor”
    Accept or decline a proposal

    Accepting a proposal is local. The agent’s text enters the document only when a human presses Accept, and that press pushes one undo transaction.

    The ownership map

    Region Owner Policy
    Document body Shared Agent proposes, human accepts, one transaction
    Selection and caret User Agent never touches
    Save state View Autosave on pause, flush on teardown

    Persistence through a tool

    There is no state.save message, so the document lives on the server and the view calls save_document with visibility: ["app"]. The model neither sees that tool nor can call it, which means the model cannot save a document it has not been asked to save.

    Autosave fires 900 milliseconds after typing stops, which is also when the undo transaction is committed. One pause, one save, one undo step.

    The teardown flush

    Illustrative, not run

    bridge.on("teardown", async ({ reason }) => {
  $("#log").textContent = `Host is closing this view: ${reason}`;
  if (dirty) {
    $("#log").textContent += " Flushing unsaved changes first.";
    await save();
  }
});

    This is the only window in the protocol where a view can finish something. Press “Close the view” in the demonstration: the control reports how long the view took to answer, which is exactly the measurement a conformance test makes to find out whether a host really waits.

    Proposal, not replacement

    The agent’s propose_rewrite tool does not touch the document. It shows the proposed text with Accept and Decline, and returns “Shown to the user. Not applied.” so the agent does not report a change that has not happened.

    Accepting is one transaction. One Cmd+Z puts the human’s words back, which is the entire safety argument for letting a model near a document.

    Try this

    Type in the document and watch the chip. Amber on the first keystroke, green about 900 milliseconds after you stop, with a save_document call in the transcript between the two.

    Press “Agent proposes a rewrite”. The document is untouched; the proposal appears below it. Press Accept, then Cmd/Ctrl+Z once. Your words are back.

    Type something, then immediately press “Close the view”. The note in the transcript reports how many milliseconds the view took to answer ui/resource-teardown, and the save happened inside that window.

    Press “Agent reads the document”. The tool reports the text and the dirty flag, which is the pull half of the pair whose push half is ui/update-model-context.

    What it needs from the host

    Level Needs Without it
    1 Render, resize, theme Nothing works
    2 lifecycle.beforeClose Unsaved work is lost on teardown
    4 tool.invoke No load and no save; the editor is a scratchpad
    4 app.tools The agent cannot propose anything
    4 agent.sampling Drafting happens in the conversation instead

    What happens when things go wrong

    The host does not wait for the teardown response. Indistinguishable from the inside. Autosave is what makes it survivable: at worst 900 milliseconds of typing is lost.

    The save fails. The dirty flag stays set, the chip stays amber, the tool’s own message appears under the document, and the next autosave retries. Both failure shapes are handled: a result carrying isError: true, which means the tool ran and refused, and a rejected call, which means it never ran. The document is never marked saved on a failure, and the render harness asserts it by refusing one save and checking that the chip still reads “unsaved”.

    The agent proposes while the user is typing. The proposal appears below rather than replacing anything, so there is no race. Chapter 21’s lab shows the harder version of this, where the agent writes directly into a shared field.

    Keyboard and screen reader

    The editable region is role="textbox" with aria-multiline. Undo and redo announce their labels. The proposal card is a live region so its arrival is announced, and its buttons are reachable in tab order immediately after the document. Formatting shortcuts are duplicated as toolbar buttons.

    Conformance checks

    1. load_document populates the editor.
    2. Typing sets the dirty state; a pause clears it via save_document.
    3. ui/resource-teardown receives a response, and the response comes after a save when the document was dirty.
    4. propose_rewrite does not modify the document.
    5. Accepting a proposal is exactly one undo step.
    6. get_document reports the current text and dirty state.
