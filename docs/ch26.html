Chapter 26

The Verification Layers

Six layers, from a schema to a cross-host dashboard, and an honest account of which of them this repository actually runs.

Verification is layered because the failures are layered. A malformed message and an inaccessible combobox and a host that ignores display mode requests are three different problems, and no single check finds all three.

This chapter describes six layers and says, for each, what this repository runs today and what it does not. That second half matters: a book that described an aspirational test pyramid and shipped none of it would be exactly the thing Chapter 25 is arguing against.

Layer 0: Schemas

Capability manifests and every bridge message validate against JSON Schemas derived from the extension specification. Nothing untyped ships.

What runs here. The registry is generated from a single Python source and every downstream artifact reads the generated JSON, so an identifier that exists in one place and not another is impossible by construction rather than by discipline. tools/check_claims.py goes further and greps the pinned specification text for every message name the registry claims exists: sixty-eight claims, checked on every build.

That check has already earned itself. It reports which anchors exist in the current draft but not in the last dated release, and the answer is eight: ui/download-file, downloadFile, ui/notifications/request-teardown, updateModelContext, sampling/createMessage, notifications/tools/list_changed, resource_link and isError. A book that did not check would have described all eight as though they were settled.

What does not run. Full JSON Schema validation of every message against the SDK’s generated schema. The bridge here validates shape by construction rather than against a schema document.

Layer 1: Protocol transcripts

Because every message is JSON-RPC over postMessage, a scenario can be replayed and its message log diffed. A transcript diff in a pull request is a protocol change somebody has to explain.

What runs here. tools/check_demos.mjs drives all thirty demonstrations in headless Chrome over the DevTools Protocol, waits for the handshake, clicks every host control in order, and records the normalised message log to conformance/transcripts/. Timings and request ids are stripped, object keys are sorted, and the result is compared byte for byte with the committed file.

A missing handshake is a hard failure, for the reason Chapter 25 gives. So is any console error that is not a favicon.

Layer 2: Capability harness

One minimal application per capability group, driven in a reference host, with assertions on both behaviour and transcript.

What runs here. The seventeen labs are that harness. Each exercises one chapter’s capabilities, each has a fixture host with controls for the things only a host can do, and each has a recorded transcript.

What does not. They run against the emulator in this repository, not against the basic-host that ships with the official SDK. Running the same labs against that host is the obvious next step and would convert a set of assertions about this book’s host into assertions about a reference one.

Layer 3: Component checks

Part IV components in isolation, with interaction tests, automated accessibility audits, and keyboard checklists transcribed from the ARIA Authoring Practices Guide into executable assertions.

What does not run. This layer is not implemented. The components exist as a shared stylesheet and helper file rather than as a component library with stories, and no axe-core run is wired into the build. The accessibility claims in this book come from the checklist in Chapter 13 applied by hand, which is weaker than an automated audit for the half of the list a machine can check and stronger for the half it cannot.

Saying so is more useful than a passing badge would be.

Layer 4: Recipe integration

Each recipe end to end against a scripted mock agent: recorded tool results, deterministic streaming, and fault injection.

What runs here. All thirteen recipes are driven by the same harness as the labs, with fixtures recorded from their real servers by tools/record_fixtures.mjs. The fault injection is real: controls that break the server, withdraw capabilities, cancel mid-flight, and tear the view down are part of every recipe’s demonstration and are exercised by the harness.

The limitation, stated plainly. The harness cannot click inside the frame, because the frame has an opaque origin and no DOM access is possible from outside. So recipes are driven from the host side and through the tools they register. Recipes 4, 7, 10 and the ownership lab are driven deeply this way. Recipes with no registered tools are checked for their handshake, their initial render and their host-side flows, and their internal interactions are verified by hand.

That limitation is worth noticing for a second reason: it is the same argument Chapter 18 makes for registering tools in the first place. A view that exposes its operations is a view an agent can drive, an accessibility tool can drive, and a test can drive.

Layer 5: Cross-host conformance

The same suite against several hosts, with results published per host and per capability, in the manner of the public web platform test dashboards.

What does not run. Nothing. This book runs against one emulator. The basic-host in the extension SDK, the MCP-UI client, and the production hosts that implement the standard are all candidates, and the checklists in Appendix C are written so that they could be run against any of them.

The reason this matters more than the missing Layer 3 is that cross-host results are the only evidence that would answer the completeness test in Chapter 25. One host running thirteen recipes proves the recipes work. Several hosts running them unmodified proves the capability model is general, which is the claim the whole book is making.

The layer that is not on the list

Human usability sessions. None were run for this edition, and none of the design claims here are backed by watching somebody use these applications. The recipes are built to a set of principles with arguments behind them, and the arguments could be wrong in ways no automated check would detect.

That is the largest single gap in this book’s evidence, and it is a bigger one than Layers 3 and 5 combined.
