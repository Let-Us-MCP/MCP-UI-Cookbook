Chapter 17

UI to Agent

Three ways for a view to reach the conversation, one of which is quiet, one of which starts a turn, and one of which skips the conversation entirely.

Part III is the part with no equivalent in ordinary web development. A web page has one user. An MCP application has a person who reads the pixels and a model that reads the text, and the model can act.

This chapter is the view speaking outward: publishing what is true, asking for a turn, and reaching a model directly. The next chapter is the reverse direction.

Three weights

Before the entries, the distinction that decides which one you want.

Context update is push, and it is quiet. The view says what is currently true. Nobody is asked to do anything, no turn starts, and the fact is available when the next thing the user says needs it.

Message is a turn. The view puts content into the conversation and expects the agent to respond. This is heavy and should be traceable to a deliberate user action.

Sampling skips the conversation. The view asks the host’s model for a completion and gets a result back privately. No turn, no visible exchange, and the answer belongs to the view.

Reaching for the wrong one is the most common design error in this part of the protocol. A view that sends a message every time a selection changes has turned a mouse into a conversation partner. A view that only ever publishes context and never offers a way to ask about it has built something the user cannot get an answer out of.

ui/update-model-context carries content, structuredContent, or both, and replaces whatever the view published before.

Replacement is the important word. The specification is explicit: each request overwrites the previous context from this view, hosts may deduplicate identical updates, and if several arrive before the next user message the host should send only the last. The design assumes a view that publishes a current state, not a stream of events.

Extracted from from apps/labs/lab-agent/index.html

function update() {
  if (!bridge?.hostCapabilities.updateModelContext) return;
  if (!selected.size) return;
  const payload = {
    content: [{ type: "text", text:
      `The user has ${selected.size} ticket(s) selected:\n${selectionText()}` }],
    structuredContent: {
      selected: [...selected].map((i) => ({ id: ROWS[i][0], owner: ROWS[i][1],
                                            ageDays: ROWS[i][2], state: ROWS[i][3] })),
    },
  };
  bridge.updateModelContext(payload);
}

Publish state, not events. “Three tickets are selected, here they are” is state. “The user clicked row 4” is an event, and by the time the model reads it the user has clicked six other things.

Publish the minimum that changes an answer. The demonstration has a control that starts publishing hover position, which is the reductio: it works, the host accepts it, and it makes every answer worse by burying the selection under noise.

Failure modes. Unsupported when updateModelContext is absent, which is a real Level 1 host, so the interface must still be usable: the escalation button carries the selection in its text instead. Denied comes back as a JSON-RPC error and should not be fatal; the view keeps working, the model knows less.

ui/message puts content into the conversation with a role. This is how the user says “talk about this”, and the important design property is that it is a user action with a visible consequence.

Application behaviour. Carry the selection and the question, and stop. Recipe 8’s “Explain this change” sends the selected diff lines. Recipe 1’s “Ask about these” sends the selected deployments as CSV. Neither summarises the whole view, because the whole view is not what the user pointed at.

Say what will happen. A button labelled “Ask about these” is honest about starting a turn. A view that quietly sends a message when a row is clicked has taken an action on the user’s behalf in a conversation they are reading.

Host behaviour. The host should add the message with the role given, and may ask for consent. That last clause is worth designing for: your promise may sit in front of a confirmation dialog for a second or two.

Failure modes. Unsupported when hostCapabilities.message is absent, and this one hurts, because escalation is the main route from a view back into the conversation. The fallback is to make the selection copyable, so the user can paste it themselves. It is worse, and it is not nothing.

Structured intent

Here is a gap that is easy to miss because there is a way to work around it that almost works.

When a user clicks “Explain this node”, the view knows two things precisely: a verb and a target. {"intent": "explain", "target": "node-17"} is what it would like to send. What it can send is a sentence, through ui/message, and the agent parses the sentence back into a verb and a target it might get wrong.

That round trip through prose is lossy, and it is lossy in a way that varies between models. It also makes the interaction untestable: an assertion about “the agent understood the user wanted to explain node 17” is an assertion about a sampled token.

The workaround that almost works. Register a tool. A view that exposes explain_node(id) gives the agent a precise entry point, and Chapter 18 is about exactly that. What tools cannot express is the direction: tools are the agent calling the view, and intent is the view telling the agent what the user just meant. In practice, views send a message with a structured payload alongside the prose and hope the model reads it.

What a mechanism would look like. ui/intent with a verb, a target and arguments, delivered to the agent as a structured turn rather than as text. Appendix B has it.

sampling/createMessage is core MCP, and the extension makes it available to views when hostCapabilities.sampling is present. The view sends messages and gets a completion back, and the conversation is not involved.

This is genuinely different from the other two. Escalation asks the user’s agent, in front of the user, and the answer appears in the chat. Sampling asks a model, privately, and the answer comes back to your code.

When it is right. Work that belongs to the view rather than to the conversation. Drafting a suggestion into a text field. Classifying a free-text field. Summarising a selection for a label. Recipe 4 uses it to draft a rewrite, which is then shown as a proposal rather than applied.

When it is wrong. Anything the user should see being asked. If the answer is going to be the substance of what the user does next, it belongs in the conversation where they can push back on it.

Host behaviour. The host chooses the model, and should rate limit, apply cost controls, and involve a human. Your call may be slow, may be refused, and may return something from a smaller model than the conversation uses.

Failure modes. Check hostCapabilities.sampling before offering the feature, and hostCapabilities.sampling.tools before including tools in the request. Press “Withdraw sampling” in the demonstration: the button stays, and explains that the view cannot reach a model on its own and that escalation is the alternative. That is the honest degradation, because the underlying user need has not gone away.

What a good context payload looks like

Three properties, and the demonstration lets you break each of them.

It is a state, not an event. Present tense, complete, and true right now. “Three tickets are selected, here they are” survives being read two turns later; “the user clicked row 4” does not.

It has both halves. content for the model to read as language, and structuredContent for anything the model may need to quote back exactly. Identifiers, numbers and dates belong in the structured half, because a model copying an identifier out of prose is a model that occasionally copies it wrong.

It is small. Not because there is a limit, but because it is displacing conversation. Publishing four selected rows is proportionate. Publishing the whole table on the grounds that the model might want it is spending somebody else’s context window on a table the view has already rendered.

Failure modes across the group

Unsupported. Check hostCapabilities for message, updateModelContext and sampling separately; a host may have any combination. The demonstration withdraws each one so you can watch the view rearrange itself.

Denied. All three can return a JSON-RPC error, and none of them should be fatal. A view whose escalation was refused still has a selection the user can copy.

Deferred. Specific to context updates, and easy to mistake for a failure. The host may hold your update until the next user message, so a model that “does not know” about a selection published half a second ago may simply not have been asked anything yet.

Slow. Specific to sampling. The host chooses the model, applies rate limits, and may involve a human, so a sampling call is not a function call with a predictable latency. Show that something is happening and offer a way out.

Conformance checks

  1. A selection change sends exactly one ui/update-model-context.
  2. A second change replaces the first rather than appending to it.
  3. Nothing is published for hover, scroll or sort.
  4. ui/message is sent only in response to a deliberate user action.
  5. With message absent, the escalation control is not rendered.
  6. With sampling absent, no sampling/createMessage is sent.
  7. sampling/createMessage includes tools only when hostCapabilities.sampling.tools is present.

The shape to carry forward

Three routes, and the cost rises steeply along them. A context update is a line of JSON that might improve the next answer. A message is a turn with a model behind it. Sampling is a model call your view pays for and the user never sees.

Most applications need the first constantly, the second on a button, and the third rarely. An application that has reached for the third for something the first would have handled is an application that has misunderstood what the conversation is for.
