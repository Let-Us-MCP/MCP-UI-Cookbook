Chapter 6

Surfaces and Geometry

You do not own the rectangle. Reporting your size, reading what room you have, moving between display modes, and asking to be closed.

An MCP application is lent a rectangle. It does not own one. The host decides how wide the rectangle is, whether it may grow, whether it can go fullscreen, and when it stops existing. Four capabilities describe that negotiation, and between them they cause more visible breakage than any other group in this book, because getting them wrong produces a scrollbar inside a scrollbar or a view that is six pixels tall.

Reporting your size

The host renders your document inside a frame and cannot see into it. The frame has whatever height the host gave it, and your content has whatever height it has, and nothing reconciles those two facts unless you send a message.

Application behaviour. Observe your own content and report its size when it changes. A ResizeObserver on document.body is the standard shape, and the SDK does exactly this when autoResize is left on. Report on change only. An observer that fires during layout will fire repeatedly, and sending every callback turns a resize into a flood.

Extracted from from emulator/app-bridge.js

autoResize(element = document.documentElement) {
  let last = { width: 0, height: 0 };
  const report = () => {
    const width = Math.ceil(element.scrollWidth);
    const height = Math.ceil(element.scrollHeight);
    if (width === last.width && height === last.height) return;
    last = { width, height };
    this.notify("ui/notifications/size-changed", { width, height });
  };
  new ResizeObserver(report).observe(element);
  report();
  return this;
}

Host behaviour. When a dimension is flexible, the host must listen and resize the frame. When a dimension is fixed, the host may ignore the report entirely, and your content has to fit or scroll inside itself.

Failure modes. The interesting one is the first report. A frame that has just been appended can measure zero, and a host that believes a zero collapses the view to nothing. Both sides should be defensive: report only positive sizes, and treat a zero as “not yet” rather than “empty”.

The other failure mode is the nested scrollbar, which is not a bug in either party. It is what happens when a view sets height: 100% on a container while the host has given it a flexible height. The container fills a frame whose size is derived from the container, and the resulting circularity settles wherever the first measurement happened to land.

hostContext.containerDimensions describes each axis independently, in one of three modes.

Field present Mode What it means
height or width Fixed The host controls it. Fill the space and scroll inside.
maxHeight or maxWidth Flexible You control it, up to that limit.
Neither Unbounded You control it, with no limit.

The two axes can differ, and commonly do: a fixed width with a flexible height is the standard inline card. A view that assumes fixed scrolls inside a frame that was willing to grow. A view that assumes flexible overflows one that was not. The demonstration above lets you switch between them and watch the content react.

Extracted from from apps/labs/lab-surface/index.html

function describe(dimensions) {
  if (!dimensions) return "Unbounded in both directions.";
  const axis = (fixed, max, name) =>
    fixed != null ? `${name} is fixed at ${fixed}px`
    : max != null ? `${name} is flexible up to ${max}px`
    : `${name} is unbounded`;
  return [
    axis(dimensions.width, dimensions.maxWidth, "Width"),
    axis(dimensions.height, dimensions.maxHeight, "Height"),
  ].join(". ") + ".";
}

The same object also carries safeAreaInsets, platform and deviceCapabilities, which Chapter 12 covers. All of it can change through ui/notifications/host-context-changed, so read it in a function rather than in a constant.

Accessibility. Reflow is a WCAG requirement, not a nicety. Content must remain usable at 320 CSS pixels of width without two-dimensional scrolling, and a host is entitled to give you exactly that on a phone.

Three modes exist: inline, fullscreen, and pip. Both parties declare which they support, and the negotiation has a shape worth memorising.

The view declares appCapabilities.availableDisplayModes during initialisation. The host declares hostContext.availableDisplayModes in its answer. The view checks the host’s list before asking, sends ui/request-display-mode, and reads the mode that comes back, which is authoritative and may not be the mode it asked for. When the mode changes for any other reason, the host sends ui/notifications/host-context-changed with the new displayMode.

Four rules follow from that, and three of them are things applications get wrong:

The response is the truth, not the request. A host may decline and return the mode you are still in. Code that assumes success produces an interface convinced it is fullscreen while sitting in a card.

Do not ask for a mode you did not declare. The host is permitted to refuse a mode the view never claimed to support, and it is permitted to refuse for any other reason too.

Handle the mode changing without being asked. The user may have a fullscreen control in the host’s own chrome.

Layout for the mode you are in, not the mode you requested. Press “Withdraw fullscreen” in the demonstration and then press the view’s own button: the view checks the list, finds fullscreen gone, and says so instead of sending a request that would fail.

This capability is a pair of messages pointing in opposite directions, and the asymmetry is deliberate.

The view sends ui/notifications/request-teardown. It is a notification: no id, no answer, no guarantee. The host may ignore it, defer it, or act on it.

If the host acts, it sends ui/resource-teardown, which is a request with an id and a reason, and it should wait for the response before removing the frame. That waiting period is the only moment in the entire protocol where a view can finish something before it stops existing. Chapter 14 spends the whole chapter on what to do with it.

Failure modes. A host that tears down without sending ui/resource-teardown takes your unsaved work with it, and there is nothing the view can do about that except not have unsaved work. A host that sends it and does not wait for the answer is worse, because it looks correct. The transcript tells you which you are dealing with: press “Tear the view down” in the demonstration and read the two entries at the bottom of the log.

What to remember

Geometry is the only part of this protocol where both parties are guessing about the same number at the same time. The view knows how tall its content is; the host knows how much room there is. Neither can see what the other knows, and the two messages that carry the answer are one notification and one context field. Get those two right and most layout bugs in embedded applications disappear.
