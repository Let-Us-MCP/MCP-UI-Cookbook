Chapter 6

Surfaces and Geometry

How to size your view, read the space you were given, go fullscreen, and ask to be closed. Most embedded layout bugs are in this chapter.

You do not own the rectangle you render into. The host decides how wide it is, whether it may grow, and when it stops existing.

Four capabilities cover that. Get them right and most embedded layout bugs go away. Get them wrong and you get a scrollbar inside a scrollbar, or a view six pixels tall.

How do I make the frame fit my content?

Send ui/notifications/size-changed whenever your content resizes. The host cannot see inside your frame. If you do not tell it, nothing does.

Extracted from from emulator/app-bridge.js

autoResize(element = document.documentElement) {
  let last = { width: 0, height: 0 };
  const report = () => {
    const width = Math.ceil(element.scrollWidth);
    const height = Math.ceil(element.scrollHeight);
    if (width === last.width && height === last.height) return;
    last = { width, height };
    this.notify("ui/notifications/size-changed", { width, height });
  };
  new ResizeObserver(report).observe(element);
  report();
  return this;
}

Three rules:

  • Report on change only. A ResizeObserver fires during layout. Sending every callback floods the channel.
  • Never report a zero. A freshly appended frame measures zero before it lays out. See the six-pixel bug below.
  • Let the SDK do it. @modelcontextprotocol/ext-apps has this built in and turns it on by default.

What the host owes you: if a dimension is flexible, it listens and resizes within a frame or two. If a dimension is fixed, it may ignore you entirely, and your content has to fit or scroll inside itself.

How much room do I actually have?

Read hostContext.containerDimensions. Each axis is independently one of three modes.

Field present Mode What you do
height or width Fixed Fill it. Scroll inside.
maxHeight or maxWidth Flexible Size yourself, up to the limit.
Neither Unbounded Size yourself. No limit.

A fixed width with a flexible height is the standard inline card, so do not assume the axes match.

The usual mistake is assuming one mode and getting the other. Assume fixed and you scroll inside a frame that was happy to grow. Assume flexible and you overflow one that was not. The demo switches between them so you can watch the content react.

Extracted from from apps/labs/lab-surface/index.html

function describe(dimensions) {
  if (!dimensions) return "Unbounded in both directions.";
  const axis = (fixed, max, name) =>
    fixed != null ? `${name} is fixed at ${fixed}px`
    : max != null ? `${name} is flexible up to ${max}px`
    : `${name} is unbounded`;
  return [
    axis(dimensions.width, dimensions.maxWidth, "Width"),
    axis(dimensions.height, dimensions.maxHeight, "Height"),
  ].join(". ") + ".";
}

Read it in a function, not once at startup. Any of it can change through ui/notifications/host-context-changed.

The same object carries safeAreaInsets, platform and deviceCapabilities, which Chapter 12 covers.

Accessibility. WCAG’s Reflow criterion wants your content usable at 320 CSS pixels wide with no two-dimensional scrolling. A host on a phone may hand you exactly that.

How do I go fullscreen?

Send ui/request-display-mode, then use the mode that comes back rather than the one you asked for.

Illustrative, not run

const { mode } = await bridge.requestDisplayMode("fullscreen");
// mode may still be "inline". The host is allowed to say no.

Four steps, and three of them get skipped:

  1. You declare appCapabilities.availableDisplayModes at startup.
  2. The host declares hostContext.availableDisplayModes in its answer.
  3. You check the host’s list before asking.
  4. The host answers with the mode it actually set, and may change it later through ui/notifications/host-context-changed.

What goes wrong:

  • Assuming the request succeeded. You get an interface convinced it is fullscreen, sitting in a card.
  • Asking for a mode you never declared. The host may refuse on that alone.
  • Ignoring a change you did not request. The host may have its own fullscreen control.
  • Laying out for the mode you asked for. Lay out for the mode you got.

Press “Withdraw fullscreen” in the demo, then press the view’s own button. The view checks the list, finds fullscreen gone, and says so instead of firing a request that would fail.

How do I close myself?

Send ui/notifications/request-teardown. It is a notification: no id, no answer, no guarantee.

If the host agrees, it sends ui/resource-teardown, which is a request, and it should wait for your response before removing the frame. That wait is the only moment in the protocol where you can finish something. Chapter 14 is about what to do with it.

A host that tears down without sending ui/resource-teardown takes your unsaved work with it. A host that sends it and does not wait is worse, because it looks correct from the outside. Press “Tear the view down” in the demo and read the last two transcript entries.

Three geometry bugs

The six-pixel view. A frame that has just been appended has no layout yet, so the first ResizeObserver callback can report zero. A host that believes it collapses the frame. Now the view has nothing left to observe, so it never grows back.

Fix on both sides: views send only positive sizes, hosts treat zero as “not yet”. This one survives manual testing, because the first frame on a page is usually fine and the second is not.

The nested scrollbar. You set height: 100% on a container while the host gave you a flexible height. The container fills a frame whose height is derived from the container, and the circularity settles wherever the first measurement landed.

Rule: in a flexible dimension, never put a percentage height on anything in the chain the observer measures. Let content decide, and put the scroll on an inner element with an explicit max-height.

The oscillating frame. A hover effect changes an element’s height. You report a new size, the host resizes, the pointer is now over something else, and the layout bounces. Reserve the space up front and change only appearance on hover.

Conformance checks

  1. A size reported in a flexible dimension resizes the frame within one animation frame.
  2. A reported size of zero does not collapse the frame.
  3. containerDimensions is in the initialize result and describes each axis independently.
  4. A container change sends ui/notifications/host-context-changed with only the changed keys.
  5. ui/request-display-mode returns the resulting mode, and the host never switches a view to a mode absent from its appCapabilities.
  6. ui/notifications/request-teardown is honoured with ui/resource-teardown or ignored, never acted on silently.
  7. The host waits for the teardown response before removing the frame.

What to remember

Both parties are guessing at the same number. You know how tall your content is. The host knows how much room there is. Neither can see what the other knows, and one notification plus one context field is the entire bridge.
