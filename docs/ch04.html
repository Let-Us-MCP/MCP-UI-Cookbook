    Chapter 4

    The Local-First Principle

    Sorting a column is not a conversation. Where the agent boundary goes, why it goes there, and what it costs when it goes somewhere else.

    Here is a design that keeps getting built. A table appears in the chat, the user clicks a column header to sort it, and the click sends a message to the model. The model decides what sorting by that column means, calls a tool, the tool returns the rows in a new order, and the view re-renders.

    It works, which is the problem. It takes two seconds, costs a few thousand tokens, sometimes sorts by the wrong column because the header label was ambiguous, and occasionally produces a chatty paragraph about how it has sorted the table. Every one of those failures is a symptom of the same decision: an interface operation was routed through a language model. Nothing in the protocol pushed anybody towards it, and the fix is one line of JavaScript, which is why the design keeps surviving code review.

    The Local-First Interaction Principle. An MCP application should not invoke a model in order to perform ordinary user-interface behaviour.

    Scrolling, sorting, resizing, selecting, dragging, opening a menu, copying content and changing a local filter all execute locally, without a message leaving the frame.

    The agent boundary is crossed only when the interaction needs reasoning, external data, a privileged operation, semantic interpretation, or the conversation itself. Four of those five are served by a tool call, and never by a turn. :::

    Why the line falls there

    Take one interaction, sorting eight rows by a column, and price it both ways. The numbers below are not close, and the row that decides the design is not the one about latency. Latency is what a user complains about; determinism is what stops you writing a test; and the tokens are what quietly shorten every answer later in the same session.

    Local Through the model
    Code rows.sort(by) ui/message, then a tools/call, then a re-render
    Latency one frame, about 16ms 1 to 3 seconds
    Tokens none the table in, a tool call out
    Same input, same output always usually
    Testable expect(rows[0].service).toBe("billing") not with an assertion

    Direct manipulation stops feeling direct at roughly 200 milliseconds, which means the right-hand column is out of budget before the model has finished reading the request. No amount of streaming fixes that, because what streams is the answer and what the user is waiting for is the sort.

    The determinism row is the one that decides Part VI. Recipe tests assert that sorting by p95 puts billing first. You cannot write that assertion against a sampled token, so any interaction routed through a model drops out of the test suite.

    The cost row compounds. Recipe 1 publishes 4 selected rows once, about 60 tokens. The same view publishing on every mouseenter sends 40 updates crossing the same table, and the host is permitted to forward only the last, so 39 of them bought nothing.

    Trust is the one you cannot measure and will hear about. A control that sorts by the wrong column once in twenty teaches people to stop clicking it and start typing into the chat, which is the outcome an embedded application exists to prevent.

    The test, in one question

    For any interaction, ask one question: could a competent implementation answer this with the data already in the frame? Almost everything a user does with a table, a canvas or a form answers yes, and the ones that answer no split further into two very different cases.

    If yes, do it locally. Sorting, filtering, paging, selecting, expanding, zooming, panning, undoing, and formatting all answer yes, and every one of them appears in the recipes as local behaviour with a conformance check asserting that it sends no message at all. That check is the enforceable form of this principle: a view that starts a turn to sort a column fails a test in this repository, and it should fail one in yours.

    If no, ask what is actually missing. Missing data means a tool call, which your view can make directly through the host without the model’s involvement at all: that is tool.invoke, and a refresh button is its canonical use. Missing judgement means the model, and the crossing should carry the user’s intent and the relevant state, not a description of the interface.

    The second half of that answer is the one people skip. “The view needs new data” is not the same as “the model needs to be asked”. A tool call from a button is a straight line: view, host, server, view. The model is not in it.

    Three ways to cross

    A tool call. The cheapest thing that leaves the frame. Your view calls a server tool through the host and gets structured data back, and nothing enters the conversation at all. Refresh, load more, save, validate against a rule only the server knows.

    A context update. The view tells the model what is currently true about the interface, so that the next thing the user says can be answered against it. This is push: nobody is asked to do anything. “Three rows are selected, here they are.”

    Recipe 1’s entire crossing, in fourteen lines. Everything else the Data Explorer does happens without a message:

    Extracted from from apps/recipes/r01-data-explorer/index.html

    // Sorting, filtering, paging and selecting never leave the frame. Only the
// selection, once it exists, is worth telling the model about, and it is sent
// as structured data rather than as a description of a table.
function publish() {
  if (!bridge.hostCapabilities.updateModelContext) return;
  const picked = rows.filter((r) => selected.has(r.id));
  if (!picked.length) return;
  bridge.updateModelContext({
    content: [{ type: "text", text:
      `The user selected ${picked.length} deployment(s): `
      + picked.map((r) => `${r.service}@${r.version} in ${r.env}`).join(", ") }],
    structuredContent: { selected: picked },
  });
}

    The early return on an empty selection is the line that stops this becoming the over-crossing example. Selecting a row and deselecting it publishes once, not twice, because there is nothing worth saying about an empty table.

    A message. The view puts something into the conversation and expects a turn to happen. This is the heavy one, and it should be traceable to a deliberate user action, usually a button that says what will happen. “Ask about these rows” is honest. Sorting a column and quietly starting a turn is not.

    Chapter 18 has all three on the wire, and a demonstration where you can watch the difference between publishing a selection and publishing a mouse. The three are not interchangeable and choosing between them is not a matter of taste: they involve different parties, cost different amounts, and differ absolutely in whether the user can be shielded from a mistake.

    Both mistakes are common

    Two mistakes are symmetrical and about equally common, and they fail in opposite directions. One makes the assistant look stupid, and it announces itself the first time somebody says “these” and gets a blank answer. The other makes it look expensive and slowly degrades every answer in the session, and it announces itself never, because a context window filling with duplicates produces worse answers and no error.

    Under-crossing produces an application the model cannot see. The user selects three deployments, asks “why are these slow”, and the model has no idea what “these” refers to because the view never published the selection. From the user’s side this reads as the assistant being stupid, and there is nothing in the interface to suggest why.

    Over-crossing produces the sorting example, plus its uglier relative: a view that publishes its entire state on every change, so the model’s context fills with sixteen near-identical snapshots of a table. The specification is direct about this. Each ui/update-model-context overwrites the previous one, hosts may deduplicate identical updates, and where several arrive before the next user message the host should forward only the last. The protocol is built expecting you to be disciplined and forgiving you when you are not, which is not the same as it being free.

    The three crossings, priced

    The weights are not a rhetorical ordering. The three routes differ by roughly an order of magnitude in every dimension that matters, and by an unbounded amount in the one that matters most, which is reversibility.

    Tool call Context update Message
    Who is involved Host, server Host Host, model, the user reading
    Typical latency Tens of milliseconds to a second Immediate A turn
    Token cost None The payload, once The payload plus a response
    Visible to the user No Usually not Yes, in their conversation
    Reversible By calling again By publishing again No

    The last row is the one that should decide the design. A tool call that was wrong can be repeated. A context update that was wrong is replaced by the next one. A message that was wrong is a paragraph in somebody’s conversation that they did not ask for, and there is no unsend.

    That asymmetry is why a message needs a deliberate user action behind it and the other two do not, and it is why “the button that starts a turn should say so” is a rule.

    Write the split down first

    Every recipe in Part V declares its split explicitly, in a table like this one, before any code:

    Normally local Worth crossing
    Scroll, sort, filter, page “Why is p95 high on these?”
    Select rows “Investigate this anomaly”
    Open a tooltip “What does this term mean here?”
    Export CSV “Verify these against the invoice system”

    Writing that table is a five minute exercise that removes most of the architectural argument from the rest of the work. It also produces the list of tools the server actually needs, which is usually shorter than the list somebody was about to build.

    What over-crossing looks like

    The clearest way to see the principle violated is to watch the messages. A view that publishes on every change produces a log like this:

    Illustrative, not run

    app→host  ui/update-model-context   { hovering: "INC-4102" }
app→host  ui/update-model-context   { hovering: "INC-4118" }
app→host  ui/update-model-context   { hovering: "INC-4133" }
app→host  ui/update-model-context   { selected: ["INC-4133"] }

    Four messages, of which one carries information. The host is permitted to deduplicate and to forward only the last before a user message, so this may cost nothing at all, or it may cost three quarters of the view’s context budget. Neither outcome is one you chose.

    The lab in Chapter 18 has a control that turns hover publishing on so you can watch this happen, and the counter next to it shows the ratio: thousands of local events, a handful of published facts.

    The one exception

    There is a case where routing an ordinary interaction through the model is right: when the user cannot perform it directly. Voice control, accessibility tooling, and hands-free operation all mean the model is the only pointing device available.

    That is why a view can register its own tools. Expose show_panel, highlight_line_item and get_state through appCapabilities.tools, and the agent gets a semantic interface to the same operations the mouse performs, named in terms of what they do to the document instead of where they are on screen. Chapter 19 has the registration mechanism and the naming rules.

    The same tools serve three callers: an agent driving the view because the user cannot, an assistive technology doing the same thing for the same reason, and tools/check_render.mjs, which drives Recipes 4, 7 and 10 through them because a sandboxed frame with an opaque origin admits no other way in. Three motivations, one interface, and the third one is how the book proves the first two work.
