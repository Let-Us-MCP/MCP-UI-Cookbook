Recipe 9

Monitoring Console

Sustained streaming, a selection that survives it, connectivity reported honestly, and an error that happens while nobody is looking.

The recipe that runs over time, and the one that exposes tool.partialOutput as the most consequential gap in Part III. Everything in it is about staying correct while data keeps arriving.

What stays local, what crosses

Normally local Worth crossing
Follow the tail, or stop following “What caused this burst of resets?”
Select a line “Is this error related to the deploy?”
Filter by service “Summarise the last ten minutes”
Reconnect

Appending, never rebuilding

The single most important line in this recipe is the one that is not there: the list is never replaced.

Illustrative, not run

$("#log").append(node);
while ($("#log").children.length > 220) $("#log").firstChild.remove();
if ($("#follow").checked) $("#log").scrollTop = $("#log").scrollHeight;

Appending and trimming preserves selection, focus and scroll position. Replacing the container’s children destroys all three, and at five lines a second the user notices immediately. Press “Stream 40 more lines” with a line selected: the selection stays.

Following, and stopping

Follow the tail until the user scrolls up, then stop and leave the checkbox unticked. Every terminal has taught people this behaviour, and it is the kind of thing nobody notices when it is right.

Streaming without a streaming mechanism

There is no partial tool result. What this recipe does is receive repeated ui/notifications/tool-result notifications, each carrying a batch, which works and is not something the specification promises. Chapter 20 has the gap and the three workarounds. This recipe uses the one that produces the best interface and is the least portable, and says so.

Connectivity, honestly

Three states: live, reconnecting, offline. The critical design decision is what happens to the data in the last two. The console keeps the lines it has and raises a banner saying the view is showing the last lines that arrived, which is not the current state.

A console that clears itself when the connection drops has destroyed the evidence at the exact moment somebody needs it.

The error nobody saw

When an error line arrives while document.hidden is true, the console raises a banner that survives until the user comes back, and publishes the alert to the model’s context. Neither is a substitute for notify.attention, which does not exist. Both are what you can do instead.

Try this

Select a log line, then press “Stream 40 more lines”. The selection survives, because the list appends and trims and never rebuilds.

Scroll up while lines are arriving. Following stops and the checkbox unticks itself, which is the behaviour every terminal has taught people.

Watch the rate chip. It is the only honest signal that the buffer is dropping lines during a burst.

What happens when things go wrong

The frame is hidden by CSS. No visibilitychange fires, the console keeps rendering, and nothing tells it otherwise. Chapter 15 has this gap; the mitigation here is that rendering a log line is cheap.

A burst larger than the buffer. The buffer is 220 lines, so a burst of a thousand loses the oldest. The rate chip is what tells the user this is happening.

Keyboard and screen reader

The log carries role="log" for its semantics and aria-live="off" to silence it. A log region is politely live by default, so every arriving line would be read out, and at five lines a second a screen reader user hears nothing but the log. The announcement rate is a property of the interface and not of the data, so the recipe announces a summary every five seconds instead:

Extracted from from apps/recipes/r09-monitoring-console/index.html

  setInterval(() => {
    if (!unannounced) return;
    const errors = unannouncedErrors
      ? `, ${unannouncedErrors} error${unannouncedErrors === 1 ? "" : "s"}`
      : "";
    announce(`${unannounced} new line${unannounced === 1 ? "" : "s"}${errors}`);
    unannounced = 0;
    unannouncedErrors = 0;
  }, SUMMARY_MS);

“Twelve new lines, two errors” is one utterance carrying what a person needs to decide whether to look. Nothing is announced when nothing arrived, so an idle console is silent. Lines carry their level in text as well as colour.

The selected line carries aria-current, not aria-selected. aria-selected is only allowed on elements with a role that defines a selection, and a div inside a log region has none, so the attribute was invalid and axe-core reported it as critical. aria-current is permitted anywhere and says what is meant. The log itself carries tabindex="0", because a scrolling region that cannot take focus cannot be scrolled from a keyboard at all.

Conformance checks

  1. tail_logs returns 24 lines and all render.
  2. A selected line stays selected after 40 more lines arrive.
  3. Scrolling up unticks Follow; scrolling to the bottom does not re-tick it.
  4. Going offline raises a banner and keeps the existing lines.
  5. An error line arriving while hidden raises a banner visible on return.
  6. The buffer never exceeds 220 elements.
