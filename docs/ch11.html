    Chapter 11

    Clipboard, Files and System Integration

    Two messages that exist because the sandbox closed a door, one permission, and three capabilities with no route at all.

    A sandboxed frame cannot navigate the browser and cannot save a file, and both restrictions are deliberate: navigation would let a hostile view move the user somewhere convincing, and unmediated downloads would let it write to disk without anyone seeing. The two escape hatches the extension provides are both here, ui/open-link and ui/download-file, and they are shaped identically because they solve the same problem: put a human in the path.

    Both work the same way. The view asks, the host decides, and the human can see it happen. Everything else in this chapter is either the browser working normally or a door that is still shut.

    How do I copy to the clipboard?

    clipboard.writeCoreLevel 2On the wire

    Copy text or structured content, with a fallback when denied.

    Messages
    clipboardWritepermissions
    Ground
    The MCP Apps extension defines a message for it.
    Recipes
    Data Explorer, File Explorer, Spreadsheet, Code and Diff Reviewer
    Demo
    lab-clipboard

    Ship both paths, because copying is the only exit a sandboxed frame has that works without the host’s cooperation. It cannot save a file unaided, nothing can be dragged out of it, and there is no address bar to paste a URL into. The asynchronous Clipboard API is the better path when you have the permission; the execCommand fallback needs nothing but a user gesture and works in the host that granted you nothing.

    The asynchronous Clipboard API, navigator.clipboard.writeText, needs the clipboardWrite permission declared by your server in _meta.ui.permissions and granted by the host in the frame’s allow attribute. It is the better path: it handles multiple formats and does not touch the DOM.

    The execCommand("copy") fallback needs no permission at all, but it does need a user gesture and a focused selection, which is why it involves a temporary off-screen textarea. It is deprecated and it works everywhere.

    Extracted from from apps/labs/lab-clipboard/index.html

    async function copyText(text) {
  try {
    await navigator.clipboard.writeText(text);
    return "Clipboard API";
  } catch {
    const area = document.createElement("textarea");
    area.value = text;
    area.setAttribute("readonly", "");
    area.style.position = "fixed";
    area.style.opacity = "0";
    document.body.append(area);
    area.select();
    const ok = document.execCommand("copy");
    area.remove();
    if (!ok) throw new Error("both clipboard paths refused");
    return "execCommand fallback";
  }
}

    Copy what the destination wants. A table copied as a single string of text is useless in a spreadsheet. Tab-separated values with newlines paste into every spreadsheet ever written, and Recipe 5 copies ranges that way for exactly that reason. CSV for a file, TSV for the clipboard.

    Failure modes. The whole point of the pair above is that failure is rare and recoverable. Show the confirmation once, after the copy succeeded, and do not show which path it took. The user does not care.

    Can I read the clipboard?

    clipboard.readExtendedLevel 2Not standardised

    Read what the user has on the clipboard.

    Ground
    No standard mechanism exists yet. The entry carries a workaround.
    Recipes
    Spreadsheet
    Demo
    lab-clipboard

    No, and it is refused twice over. The extension’s permission set is exactly camera, microphone, geolocation and clipboardWrite, so there is nothing a host could grant you even if it wanted to. Independently, navigator.clipboard.readText from an opaque origin is refused by the browser regardless of policy. Press the button in the demonstration and read the NotAllowedError it produces.

    What to do instead. Give the user somewhere to paste. A focused input, a textarea, or a drop zone that also handles the paste event. The browser delivers pasted content to a focused element without any permission at all, because the user’s Cmd+V is the consent. That covers the realistic use case, which is importing data, and it does not cover the unrealistic one, which is reading the clipboard without being asked.

    Why the door is shut. A view that could read the clipboard silently could read whatever the user last copied, which is often a password. Any proposal here needs a user gesture and a host-mediated permission, and probably a visible indication in the host’s own chrome.

    How do I let the user pick a file?

    file.openCoreLevel 2Platform

    Open the system file picker and read what comes back.

    Ground
    The browser inside the sandbox provides it. No host round trip.
    Recipes
    File Explorer
    Demo
    lab-clipboard

    <input type="file">, with no permission and no message. The sandbox does not interfere here for a reason worth understanding: the user picked the file themselves in a dialog the browser drew, so consent is unambiguous, and the bytes stay in your frame unless your code sends them somewhere. That is the same reasoning that lets paste work while clipboard reads are refused.

    Application behaviour. Read with FileReader or file.text(). Validate type and size before reading, not after, because a 400MB file read into a string in a frame with a modest memory budget is a crash, and a crash is not an error you can catch. Say what you accept, in the interface, before the picker opens.

    How do I accept a dropped file?

    file.dropzoneCoreLevel 2Platform

    Accept dropped files with validation, preview, and progress.

    Ground
    The browser inside the sandbox provides it. No host round trip.
    Recipes
    File Explorer, Image Annotator
    Demo
    lab-clipboard

    The same input by another route, and the one users reach for first when they already have the file in a window. Offer both: the picker is discoverable and the drop zone is fast, and people split roughly evenly between them.

    Application behaviour. Four events. dragover must call preventDefault() or the drop never fires, which is the single most common bug in every drop zone ever written. dragenter and dragleave drive the visual state, and dragleave fires when the pointer crosses onto a child element, so count depth or use pointer-events: none on the children. drop reads event.dataTransfer.files.

    Validate visibly. Wrong type, too large, too many: say which, name the file, and leave the zone ready for another attempt. A drop zone that silently does nothing when a file is rejected is indistinguishable from a broken one.

    How do I show the user what a document is?

    preview.documentCoreLevel 2Platform

    Show what a document is before anyone acts on it, at a chosen size.

    Ground
    The browser inside the sandbox provides it. No host round trip.
    Recipes
    File Explorer
    Demo
    r03-file-explorer

    A file arrives, by drop or by picker or as a link from a tool, and the user has a decision to make about it. Attach it, replace with it, delete it, send it. Every one of those decisions is easier with the document in front of them and harder with a filename in front of them, and notes.txt is a filename that could be anything.

    The good news is that a preview needs nothing the protocol does not already give you. tools/check_sandbox.mjs runs both routes inside a real sandboxed frame with an opaque origin, and both work:

    Extracted from from conformance/sandbox.json

        "previewDataUri": {
      "ok": true,
      "value": "rendered"
    },
    "previewObjectUrl": {
      "ok": true,
      "value": "rendered"
    },

    The first is a data: URI built from base64 that arrived in a tool result. The second is URL.createObjectURL on a File the user dropped, which the frame renders without the bytes going anywhere. The probe records that URL’s scheme as blob:null, which is the opaque origin appearing in the URL itself: the handle is meaningful inside this document and meaningless everywhere else, including to the host. Neither needs a permission and neither needs a CSP entry, because neither is a network request. An ordinary URL on somebody else’s origin does need a CSP entry, which makes it the one route to avoid: a preview that has to reach the network fails in the host with the strict policy, and the strict policy is the default.

    Size is the caller’s decision, not the document’s. The shared component takes one of three, and only the body changes between them:

    Extracted from from apps/lib/view.css

    .preview.sm .preview-body { max-height: 48px; }
.preview.md .preview-body { max-height: 150px; }
.preview.lg .preview-body { max-height: 360px; }

    Small answers “which file is this” in a list. Medium answers “is this the right one” beside a button. Large answers “what does it say” when reading is the point. The header carrying the name and type is identical at all three, because a preview whose name disappears as it shrinks has become a thumbnail.

    Truncate by size too. Reading four hundred kilobytes of text into a 48 pixel box costs exactly what reading it into a large one costs and shows a fiftieth of it. Recipe 3 slices at 220, 1200 and 8000 characters.

    Say what you cannot show. A type with no preview gets a sentence naming the type and offering the routes that do work, which are opening it and downloading it. Rendering unknown bytes as text produces mojibake, and mojibake reads as a bug in your application rather than as a file you cannot display.

    Accessibility. The image carries alt naming the file, because “Preview of cover.png” is what a screen reader user needs and “thumbnail” is what they already assumed. The size control is a group of toggle buttons with aria-pressed, not a <select>, because three options is below the count where a menu earns its cost and the current size should be visible without opening anything.

    Failure modes. Unsupported does not arise; this is platform behaviour. Denied arises when the bytes come through a server tool the host will not proxy, and the answer is the filename and metadata you already had. Failed is a tool that returned isError, and Recipe 3 shows the server’s own message in the preview’s place while leaving the tree untouched.

    How do I preview something the server only linked?

    preview.resourceExtendedLevel 3On the wire

    Preview a resource the server linked rather than embedded.

    Messages
    resource_linkserverResourcesresources/read
    Ground
    The MCP Apps extension defines a message for it.
    Recipes
    File Explorer
    Demo
    r03-file-explorer

    A tool result can carry a resource_link rather than the bytes, which is the right shape when the thing is large or when the model has no use for its contents. The link carries uri, name, mimeType, size and optional icons, which is enough to render a small preview with no round trip at all.

    For anything larger you need the bytes, and they come through the host with resources/read, which means the host must declare serverResources. Where it does not, the metadata on the link is what you have, and a small preview built from name, mimeType and size is a genuine preview rather than a placeholder.

    Recipe 3’s server exposes each file as a resource as well as through a tool, because a thing with a URI is a resource and modelling it as one lets the view read it the way it reads anything else. Sending base64 image data into the model’s context through content would be tokens spent on something it cannot look at.

    How do I save a file?

    file.exportCoreLevel 2On the wireDraft only

    Hand a generated artifact to the host to save.

    Messages
    ui/download-filedownloadFile
    Ground
    The MCP Apps extension defines a message for it.
    Recipes
    Data Explorer, Image Annotator, Media Viewer
    Demo
    lab-clipboard
    file.saveCoreLevel 2On the wireDraft only

    Persist app-generated content through the host.

    Messages
    ui/download-fileresource_link
    Ground
    The MCP Apps extension defines a message for it.
    Recipes
    none yet
    Demo
    lab-clipboard

    allow-downloads is not in the sandbox, so an anchor with a download attribute is inert and a blob URL goes nowhere. ui/download-file is the way out, and it takes standard MCP content types.

    The contents array takes standard MCP resource types rather than a bespoke download format, which means the same shapes you already use in tool results. For inline content, send an EmbeddedResource: its resource.uri supplies the suggested filename and its text or blob carries the bytes.

    Illustrative, not run , quoted from the extension specification

    { "jsonrpc": "2.0", "id": 1, "method": "ui/download-file",
  "params": { "contents": [ { "type": "resource", "resource": {
    "uri": "file:///deployments.csv",
    "mimeType": "text/csv",
    "text": "service,env,version\ncheckout,production,4.18.2\n" } } ] } }

    For something the host can fetch itself, send a ResourceLink with a URL instead. The difference matters for large files: an EmbeddedResource puts every byte through postMessage, while a ResourceLink lets the host fetch directly, with its own network identity and its own idea of what that URL is allowed to be.

    A refusal resolves. It does not throw. This is the single most important line in the section and the one that costs people an afternoon. McpUiDownloadFileResult carries an optional isError, and the specification uses it for a host that declined and for a user who cancelled the save dialog. The promise resolves either way:

    Extracted from from apps/recipes/r01-data-explorer/index.html

          const result = await bridge.downloadFile({ contents: [{
        type: "resource", resource: { uri: "file:///deployments.csv",
          mimeType: "text/csv", text: csv() } }] });
      if (result?.isError) {
        toast("The host declined to save that file.");
        return;
      }
      toast("Handed to the host");

    A try/catch around that call catches nothing when the user cancels, so the view says the file was saved and no file exists. What a rejection does mean is that no answer arrived at all: a timeout, or the bridge going away. Both need handling and they need different sentences. ui/open-link and ui/message work the same way, with isError on McpUiOpenLinkResult and McpUiMessageResult.

    Pass the params object, not the contents. App.downloadFile in the extension SDK takes the request’s params, so the argument is { contents: [...] } and not [...]. Handing it the array directly leaves params.contents undefined, and a host with nothing to download does nothing at all. tools/check_sdk_api.py compares this repository’s bridge against the SDK’s signatures on every build, because the version of that helper which took a bare array is what this book used to publish.

    Failure modes. Absence has no fallback worth the name. If hostCapabilities.downloadFile is absent, a sandboxed frame genuinely cannot save a file. The honest response is to not show an export button, and to offer copy instead, which is what Recipe 6 does: press “Refuse downloads” in its demonstration and the export path switches to the clipboard with a sentence explaining why.

    How do I open a link?

    link.openCoreLevel 1On the wire

    Delegate external navigation instead of attempting it.

    Messages
    ui/open-linkopenLinks
    Ground
    The MCP Apps extension defines a message for it.
    Recipes
    Code and Diff Reviewer, Approval Center
    Demo
    lab-clipboard

    Level 1, and the one capability in this chapter that a purely card-shaped view is likely to need. A summary card with no interaction at all still usually wants to link somewhere: to the ticket, the dashboard, the document it is summarising.

    An <a href> inside a sandboxed frame without allow-top-navigation cannot navigate, and window.open is blocked. ui/open-link asks the host to do it. The host should open in the user’s default browser or a new tab, and may refuse.

    Application behaviour. Check hostCapabilities.openLinks at initialisation. If it is absent, do not render links as links: render them as text you can copy, or omit them. A blue underlined word that does nothing when clicked is worse than plain text.

    Handle the refusal at the moment of the click as well, because a host may allow links in general and decline a specific one on policy grounds. The demonstration has a control that removes the capability so you can see both paths.

    Can I share or print?

    system.shareExtendedLevel 3Not standardised

    Invoke the operating system share sheet.

    Ground
    No standard mechanism exists yet. The entry carries a workaround.
    Recipes
    Media Viewer
    Demo
    no live demo
    system.printExtendedLevel 3Not standardised

    Request host-mediated printing.

    Ground
    No standard mechanism exists yet. The entry carries a workaround.
    Recipes
    none yet
    Demo
    no live demo

    No, and for the same reason both times. navigator.share needs the web-share policy-controlled feature and window.print needs the allow-modals sandbox token; neither is in the extension’s permission set, and no message replaces either.

    The unpleasant part is that feature detection lies. navigator.share is a function on the object, so if (navigator.share) passes, and then the call either rejects or silently does nothing depending on the browser. Detect the capability from hostCapabilities and your own fallback plan, not from the presence of the API.

    navigator.share needs the web-share permission policy. window.print needs allow-modals. Neither is granted. Feature detection reports them as present and then they fail or do nothing, which is worse than absent.

    Workarounds. For sharing: ui/open-link with a canonical URL, or copy the URL to the clipboard. Recipe 12 does the first and falls back to the second, and says which it did. For printing: ui/download-file with a generated PDF, or accept that printing an embedded view is not a thing that happens.

    Worked example: getting a table out of a frame

    The Data Explorer in Recipe 1 has eight rows the user might want elsewhere. Four routes exist and the recipe offers two of them, which is the right number.

    Copy works everywhere, needs no capability, and puts the data where the user’s next action already expects it. It is the default and it should be the first thing you build.

    Export through ui/download-file produces a file, needs hostCapabilities.downloadFile, and is the only way to move something too large to paste. The recipe omits the button when the capability is absent.

    Drag out does not exist. Chapter 10 has the gap.

    A link to the data on the server through ui/open-link is the fourth route, and it is worth considering before the other three: if the rows came from a system that has a URL for them, sending the user there gives them the data and the context, and costs one message.

    That ordering generalises. Ask what the user is going to do with the thing, then pick the route that lands closest to it, rather than picking the route that is easiest to build.

    Whichever route, generate the CSV properly. Three of the four end in a string somebody’s spreadsheet will open, and the line everybody writes is wrong:

    Illustrative, not run

    rows.map((r) => r.join(",")).join("\n")     // wrong

    A value containing a comma adds a column. A value containing a quote confuses the parser. A value containing a newline ends the record early. None of those produce an error: the spreadsheet opens, shows something plausible, and is false. Quote a field when it contains any of the three, and double the quotes inside it:

    Extracted from from apps/lib/view.js

      function toCsv(rows) {
    const field = (value) => {
      const text = value === null || value === undefined ? "" : String(value);
      return /[",\r\n]/.test(text) ? `"${text.replace(/"/g, '""')}"` : text;
    };
    return rows.map((row) => row.map(field).join(",")).join("\r\n");
  }

    CRLF between records is what RFC 4180 asks for and what Excel wants; everything else tolerates it. This book shipped the naive version until somebody asked whether the export had been checked, and the answer was that the message had been checked and the bytes never had. The fixtures contain no commas, so no demonstration would ever have shown it. The render harness now calls this function with a comma, a quote, a newline, a null and a zero, because a helper only ever called with safe input is a helper nobody has tested.

    The same run now goes further and takes the file off the disk. The host emulator decodes the contents, builds a blob, names it from the last segment of resource.uri, and lets the browser save it; the driver then opens what landed and checks the first line and the line endings. Until that was written, nothing in this repository had ever produced a file, and “download works” meant “a correctly shaped request was sent”.

    Host behaviour, in detail

    For ui/open-link, the host opens in the user’s default browser or a new tab, and may refuse. A host that opens links in a frame inside its own window has missed the point of the message, which is to get the navigation out of the sandbox and somewhere the user can see an address bar.

    For ui/download-file, the host should confirm, derive the filename from the last segment of resource.uri, sanitise it against path traversal, and may refuse on size or policy grounds. For a ResourceLink it fetches the content itself, which means the fetch happens with the host’s network identity rather than the view’s, and the host should treat the URL accordingly.

    For clipboardWrite, the host maps your server’s requested permission onto the frame’s allow attribute and reports back what it actually granted in hostCapabilities.sandbox.permissions. Requested and granted are different fields for a reason, and a view that assumes the request was honoured is a view that breaks silently in the host that declined it.

    Conformance checks

    1. With clipboardWrite granted, navigator.clipboard.writeText succeeds inside the frame.
    2. Without it, the execCommand fallback still copies from a user gesture.
    3. ui/download-file with an EmbeddedResource produces a file named from the last segment of its URI.
    4. A declined ui/download-file resolves with isError: true and the view says the file was not saved.
    5. ui/download-file with downloadFile absent from hostCapabilities is never sent by a conforming view.
    6. ui/open-link opens outside the sandbox, or returns an error.
    7. An <a download> inside the frame does nothing, and the view does not rely on it.
    8. A file chosen with <input type="file"> is readable in the view and is not transmitted anywhere the view did not send it.

    What to remember

    Every capability here that reaches outside the frame either has a message (ui/open-link, ui/download-file) or is a gap (clipboard.read, system.share, system.print). Everything that stays inside works.

    That line is the sandbox boundary, and it is worth drawing on your own requirements before you write any code. Anything that stays inside the frame costs you an afternoon. Anything that reaches outside is either one of two messages or a gap you will be working around for the life of the product.
