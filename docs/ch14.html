    Chapter 14

    Accessibility

    Three preferences the host never sends, one live region you have to build, and the reason an embedded frame makes all of this harder than a page.

    Accessibility is a section in every entry of this book, because that is the only arrangement that survives a deadline. A chapter at the end gets read once and cut first; a section in the entry you are already reading gets implemented while you are implementing the entry.

    This chapter carries the four capabilities that fit nowhere else, and the problems that come specifically from running inside someone else’s window.

    What is harder inside a frame?

    Four things, none of which are your fault and all of which are your problem. They come from the frame boundary, and knowing them changes what you build rather than merely what you test.

    Your view is a document inside a document. A screen reader user reaches it by moving into the frame, and inside it your headings start again at whatever level you chose. Use a sensible internal hierarchy and give the frame a meaningful title, because the title is what the host can expose as the frame’s accessible name.

    You cannot see the host’s landmarks. You do not know whether the conversation is a main, whether there is already an h1, or what else has role="status". Assume your announcements are competing with the host’s.

    Focus cannot cross the boundary. A keyboard user who tabs in must be able to tab out, so no focus traps outside <dialog> and no roving list that cycles forever. Chapter 8 has the gap.

    The user’s preferences reach you by a different route than the theme. The host sends colours. The operating system sends motion, contrast and text size, through media queries. Those two can disagree, and the demonstration above has a control that makes them disagree on purpose.

    How do I respect reduced motion?

    env.reducedMotionCoreLevel 2Platform

    Respect a stated preference for less movement.

    Ground
    The browser inside the sandbox provides it. No host round trip.
    Recipes
    Dashboard, Media Viewer, Settings and Preferences
    Demo
    lab-a11y

    prefers-reduced-motion: reduce works inside the sandbox and reflects the operating system setting directly. Nothing is proxied and no host involvement is needed, which also means the host cannot override it for you: if the user asked their machine for less motion, that preference reaches your frame whatever the host thinks.

    Application behaviour. The blunt instrument is a stylesheet rule that collapses every animation and transition, and it is the right default:

    Extracted from from apps/lib/view.css

    @media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .001ms !important;
    transition-duration: .001ms !important;
  }
}

    The finer instrument is to check the query in JavaScript where motion is functional. A dashboard that repaints a sparkline every 1.4 seconds is not decorating; it is moving, continuously, in somebody’s peripheral vision. Recipe 2 slows its polling to four seconds under a reduced motion preference, which is a different response from removing an animation and a more honest one.

    What to keep. Reduced motion does not mean no feedback. Replace slides with crossfades, replace crossfades with instant changes, and keep the state change legible. A toast that appears instantly is fine; a toast that never appears is a regression.

    What breaks under forced colours?

    env.contrastCoreLevel 2Platform

    Survive forced colours and high contrast.

    Ground
    The browser inside the sandbox provides it. No host round trip.
    Recipes
    Image Annotator, Settings and Preferences
    Demo
    lab-a11y

    prefers-contrast: more and forced-colors mode both work inside the frame without the host’s involvement, and forced colours is the one that breaks views. It replaces the entire palette, including the host’s variables, so any state you signalled with a background colour stops being visible at the exact moment the user most needs contrast.

    The embedded-specific trap. In forced colours, the operating system replaces the palette. Anything you drew with a background image, a gradient, or a box-shadow to indicate state loses that indication entirely, because those properties are not overridden and the colours around them are. State has to be carried by something that survives: a border, an outline, text, or an icon.

    The same applies to your own custom properties. A view that indicates selection only by background: var(--color-background-info) shows no selection at all under forced colours. Recipe 1 sets both a background and an aria-selected attribute, and the attribute is what makes it survive.

    What happens when text doubles?

    env.textScaleCoreLevel 2Platform

    Stay usable when text is two sizes larger than you designed for.

    Ground
    The browser inside the sandbox provides it. No host round trip.
    Recipes
    Settings and Preferences
    Demo
    lab-a11y

    Size in relative units so the root scale carries through, never fix a pixel height on anything containing text, and let the frame grow through surface.resize. The third one is the embedded-specific part: a page reflows into the space it already has, while your view has to ask for more, and a view that reports a stale height at 200% zoom clips its own content.

    The difference from a page is the width you have to work with. In a page, enlarged text reflows into a column that is usually still comfortable. In a 380 pixel frame at 200% zoom you have the effective width of a phone held sideways, and a two-column layout gets about three words per line before it becomes unreadable.

    WCAG 2.2 asks for usability at 200% zoom and reflow at 320 CSS pixels of width. Both are testable with the browser’s own zoom, and a four hundred pixel card at 200% is roughly a phone, so testing one gets you most of the other.

    How do I announce a change nobody caused?

    a11y.announceCoreLevel 2Yours to build

    Tell assistive technology that something changed.

    Ground
    The view implements it. Nobody else can.
    Recipes
    Data Explorer, Spreadsheet, Approval Center, Settings and Preferences
    Demo
    lab-a11y

    One polite live region, created once and reused, updated by setting its text. Creating a region per announcement does not work, because a screen reader announces changes to a region it already knows about, and a freshly inserted element is often missed entirely.

    Everything in an agentic application is a change nobody caused. A tool result arrives. The agent highlights a row. A log gains forty lines. A sighted user notices; nobody else does unless you say so.

    Use polite, not assertive. Assertive interrupts whatever is being read, and in an application where results arrive continuously that is unusable.

    Extracted from from apps/lib/view.js

    function announce(text) {
  let region = $("#live-region");
  if (!region) {
    region = h("div", { id: "live-region", class: "sr-only",
                        role: "status", "aria-live": "polite" });
    document.body.append(region);
  }
  region.textContent = "";
  setTimeout(() => { region.textContent = text; }, 30);
}

    The clear-then-set with a small delay is not superstition. Screen readers announce changes to a live region, and setting the same string twice is not a change, so the second identical event is silent without it.

    Announce the outcome, not the event. “Six of forty selected” rather than one announcement per row. Where events arrive faster than a person can listen, the announcement belongs on a timer: Recipe 9’s log is aria-live="off" with a five second summary, because a politely live log at five lines a second reads out continuously and tells the user nothing. “Import failed. Row 812 has a malformed date.” rather than “error”. The demonstration announces at phase boundaries only, which is what a sighted user actually perceives from a progress bar.

    What not to announce. Hover. Scroll position. Anything the user did deliberately and can already feel. A live region that narrates the mouse is worse than no live region.

    Two things this environment makes harder

    Announcing agent activity. In an ordinary application, changes the user did not cause are rare enough to be exceptional. Here they are the normal case: a tool result arrives, the agent highlights a row, a proposal appears. Each one needs an announcement, and together they need a budget, or the live region becomes a narration nobody can follow.

    The rule that works is to announce outcomes that change what the user can do and to stay silent about everything else. An agent proposing a rewrite is worth announcing, because there is now a decision to make. An agent highlighting a row is worth announcing once, briefly. A tool result that only refreshes numbers already on screen is not.

    Naming things the user did not name. A screen reader reads names, and in an agentic interface many elements exist because a model produced them. A row labelled only by its data reads as a string of values; the same row with an aria-label that names what it is reads as a thing. Recipe 2’s tiles carry “Checkout p95, 412 milliseconds” rather than a heading and a number in separate nodes, and that single change is the difference between a dashboard that can be listened to and one that cannot.

    The checklist that fits on a card

    Every recipe in Part V is built against this list, and Appendix C turns it into assertions.

    Every interactive element is reachable by Tab and operable by Enter or Space. Every composite widget is one tab stop with arrow key navigation inside it. Every control has a name, and the name is what a person would call it. State changes that were not caused by focus are announced. Focus is visible, and the ring is not clipped by an overflow: hidden ancestor. Nothing depends on colour alone. Nothing depends on hover alone. Every spatial gesture has a button or a key equivalent. Text stays usable at 200%. Motion respects the preference.

    Ten lines, and running axe-core against your view will confirm perhaps half of them. The other half need a keyboard and five minutes, which is a cheaper test than most of the automated ones in Part VI and catches more.

    Conformance checks

    1. Tab order covers the view and leaves it, with no element skipped and none reachable only by pointer.
    2. A list of N rows presents one tab stop for all N.
    3. prefers-reduced-motion suppresses animation and slows anything that repaints continuously.
    4. Under forced colours, selection and status remain distinguishable without relying on background colour.
    5. Text at 200% remains usable, and the view reports its new height.
    6. A change the user did not cause is announced once into a polite live region.
    7. No announcement is produced by hover or scroll.
