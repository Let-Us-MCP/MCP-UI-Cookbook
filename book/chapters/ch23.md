The components in this chapter are the ones that carry data, and all three
groups run into the same two constraints: there is no address bar, and there
is very little room.

## Navigation

| Component | Composes | APG pattern |
|---|---|---|
| Tabs | `input.keyboard`, `surface.focus`, `ui.navigate` | Tabs |
| Breadcrumbs | `input.keyboard` | Breadcrumb |
| Tree | `input.keyboard`, `input.selection`, `input.contextmenu` | Tree View |
| Accordion | `input.keyboard`, `surface.resize` | Accordion |
| Sidebar | `input.keyboard`, `surface.viewport` | (layout) |
| Toolbar | `input.keyboard`, `env.inputMode` | Toolbar |
| Command palette | `input.shortcut`, `surface.focus`, `input.keyboard` | Combobox |
| Split view | `input.pointer`, `surface.viewport` | (layout) |

**There is no URL.** Everything a URL normally does has to be done some other
way. You cannot deep link into a view. The user cannot bookmark a state. The
back button belongs to the host and does not know your tabs exist. Pressing it
leaves the conversation, which is a considerably worse outcome than going back
one tab.

Three consequences. Navigation state has to be shallow, because there is no
history to unwind. Every panel needs a visible way back, because the browser's
is not available. And navigation state is one of the few things worth
publishing to the model, because "the user is looking at the line items panel"
changes what a good answer looks like.

**Tabs are the default and the tree is the exception.** In four hundred
pixels, a tab strip with more than four labels wraps or scrolls, and both look
like a mistake. If you need more than four, you probably need a different
structure rather than a scrolling tab strip.

**A tree is one tab stop.** `role="tree"` with roving tabindex, arrows to move
and expand, Home and End, and typeahead if the tree is large. Recipe 3 builds
one, and the roving tabindex is what keeps a hundred-file tree from being a
hundred tab stops.

**Toolbars overflow rather than wrap.** A wrapped toolbar changes the height
of the view on a resize, which triggers `surface.resize`, which changes the
frame, which can change the wrap. Put the extras behind a menu.

**A command palette is the best answer to a narrow surface**, and it is also
the component most likely to lose its shortcut to the host. Give it a visible
entry point.

## Structured data

| Component | Composes | APG pattern |
|---|---|---|
| List | `input.selection`, `input.keyboard` | Listbox |
| Virtual list | `surface.scroll`, `input.selection` | Listbox |
| Table | `input.selection`, `input.keyboard`, `clipboard.write` | Grid |
| Editable grid | `input.selection`, `history.transaction`, `clipboard.write` | Grid |
| Pagination | `input.keyboard` | (native) |
| Comparison grid | `input.selection` | Grid |
| Property list | `input.selection`, `clipboard.write` | (definition list) |

This is the group most MCP applications are made of, and the group with the
most predictable failures.

**Column budget.** Four columns is comfortable at 380 pixels, six is the
ceiling, and beyond that the answer is a property list per row rather than a
wider table. Recipe 1 shows six and drops to a card layout under 480 pixels.

**Sort, filter and page locally.** Chapter 3. All three are answerable from
data already in the frame.

**Selection is the unit of conversation.** Chapter 9 has the gesture model,
Chapter 17 has what to do with it. A table without a selection model gives its
users nothing precise to ask about.

**Streaming updates must not rebuild the list.** Appending a row is fine.
Replacing the container's children destroys selection, focus and scroll
position at the same time, and the user notices all three. Recipe 9 appends
and trims, never redraws, which is what makes selecting a log line survive a
thousand lines arriving after it.

**Virtualise past a few thousand rows**, and be aware that virtualisation and
`surface.resize` interact badly: a virtual list has a fixed height by design,
so it wants a fixed container, which means telling the host a stable size and
scrolling inside it.

**Copy as the destination wants it.** TSV for the clipboard, CSV for a file.
Chapter 10.

## The column budget, worked

Six columns at 380 pixels is the practical ceiling, and reaching it takes
deliberate work rather than restraint alone.

Right-align every number and use tabular figures, which buys a character of
width per column and makes outliers scannable. Put units in the header rather
than in every cell: "p95 ms" once beats "412ms" eight times. Use chips for
enumerated values, because a chip reads at a glance and a word does not. Format
dates to the shortest form that is still unambiguous, which usually means
dropping the year for anything inside the current one. And put anything that is
only occasionally needed behind row expansion rather than in a column.

When that is not enough, the answer is not a horizontal scrollbar. It is a
different component: a property list per row, which turns a wide table into a
tall list and is what every mobile client does with the same problem. Recipe 1
switches at 480 pixels.

## Visualization

| Component | Composes | APG pattern |
|---|---|---|
| Chart | `surface.viewport`, `env.theme`, `input.pointer` | (image or table) |
| Timeline | `input.zoompan`, `input.selection` | (image or table) |
| Heatmap | `input.pointer`, `env.contrast` | (image or table) |
| Progress visualization | `op.progress`, `env.reducedMotion` | Progressbar |
| Status indicator | `env.contrast` | (status) |

**You probably cannot load a charting library.** The default CSP is
`default-src 'none'` with self and inline for scripts. Loading a library from
a CDN means your server declaring that origin in `resourceDomains`, and a host
declining it leaves you with no chart at all. Bundling it into the resource
means shipping a few hundred kilobytes of JavaScript in an HTML string on every
`resources/read`.

Inline SVG is the answer for most of what embedded applications actually need.
A sparkline is nine lines. A bar chart is fifteen. Recipe 2's sparklines are
generated with `createElementNS` and no dependency at all, and Recipe 12 draws
its media thumbnails the same way, which is also how the demonstrations avoid
declaring any external origin.

**Theme through variables, not through constants.** A chart with `#0f5c8c`
baked in is invisible in a dark theme. `stroke="var(--color-text-info)"` works
inside SVG and follows the host.

**Colour alone is never the encoding.** Forced-colors mode replaces your
palette. A status that is only a green dot becomes a dot. Pair every colour
with a shape, a label, or text.

**Charts need a text equivalent.** A `<table>` behind a disclosure, or an
`aria-label` that states the shape of the data, or figures in the caption.
"Checkout p95, 412 milliseconds, up 18 percent since the 4.18.2 deploy" is
worth more to every reader than the sparkline is, and Recipe 2 puts exactly
that sentence under each tile.

**Progress that never moves is worse than no progress.** An indeterminate
spinner with a phase name beats a determinate bar whose number is invented.
Chapter 16.

## A table that survives everything

The four properties that separate a table people can work in from a table
people take screenshots of. All four appear in Recipe 1, and none of them is
more than a few lines.

**Selection survives updates.** Keyed by identifier, not by row index. A table
that re-sorts and keeps three rows selected is behaving; one that keeps rows
three, four and five selected is not.

**Scroll survives updates.** Append and patch rather than replace. Recipe 9
appends up to a cap and never rebuilds, which is what makes a log tail usable
at five lines a second.

**Focus survives updates.** The consequence of the first two, and the one users
feel most sharply. A grid that rebuilds on every tick moves focus to the
document body twice a second, which makes keyboard operation impossible.

**Numbers are aligned and tabular.** `text-align: right` and
`font-variant-numeric: tabular-nums`. Two declarations, and they turn a column
of figures into something you can scan for an outlier. This is not
accessibility and it is not decoration; it is the reason the table exists.

## Charts without a dependency, in practice

The three shapes that cover most of what an embedded view needs, and what each
costs in inline SVG.

A **sparkline** is a `polyline` whose points are the series scaled to the box.
Nine lines, no axes, no labels, and it belongs next to a number rather than
instead of one. Recipe 2 builds one per tile.

A **bar chart** is a loop of rects with a shared scale. Fifteen lines. The
work is in the labels, not the bars, and in a narrow frame the labels usually
have to go under the bars rather than beside them.

A **status strip** is not a chart at all: a row of chips with text in them. It
is what most dashboards actually need, it is legible at any size, and it
survives forced colours because the state is in the words.

Anything beyond those three is worth asking whether the view is the right place
for it. A dense multi-series chart in four hundred pixels is a chart nobody can
read, and the honest answer is often a table plus a link the host can open.

## What to remember

The URL bar and the CDN are the two things this chapter keeps running into,
and they are the two things a page has that a view does not. Design navigation
that does not need history, and visualisation that does not need a dependency,
and most of the rest of your components will port over unchanged.
