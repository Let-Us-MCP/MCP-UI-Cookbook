Capabilities are too small to build an interface out of and applications are
too large to reuse, so components are the layer in between: the pieces with
names a designer already uses, assembled from capabilities and assembled into
recipes.

Every entry answers three questions: what it composes, which Authoring
Practices Guide pattern governs its keyboard behaviour, and what changes
because it lives in someone else's window. The third question is the one that
makes this part worth writing. The first two are answered better by the APG
itself, and every entry here links to it instead of paraphrasing it.

The third question is the only reason these chapters exist. Plenty of
references tell you how to build a combobox. None tell you how to build one
that is four hundred pixels wide, inside an opaque origin, next to a model that
may fill it in.

The recipes are built from two files: `apps/lib/view.css` and
`apps/lib/view.js`, about 500 lines together, and all thirteen share them.
That is small enough to read in a sitting and is the whole component layer
behind every demonstration on this site. There is no framework underneath it
and no build step over it, which is a claim you can check by viewing source on
any recipe.

## Overlays

| Component | Composes | APG pattern |
|---|---|---|
| Alert | `dialog.alert`, `surface.focus` | Alert Dialog |
| Confirmation | `dialog.confirm`, `surface.focus`, `input.keyboard` | Alert Dialog |
| Modal | `surface.displayMode`, `surface.focus`, `input.keyboard` | Dialog (Modal) |
| Sheet, drawer | `surface.focus`, `input.pointer`, `env.reducedMotion` | Dialog (Modal) |
| Popover | `surface.focus`, `input.keyboard` | Disclosure |
| Tooltip | `input.pointer`, `env.inputMode` | Tooltip |
| Context menu | `input.contextmenu`, `input.longpress`, `surface.focus` | Menu |

**Use `<dialog>` and `showModal()`.** It gives you the focus trap, the inert
background, the Escape handling and the `aria-modal` semantics. A hand-rolled
overlay gives you none of them, and in a frame a keyboard user cannot escape
from, the difference is not cosmetic.

This is the whole confirmation component the thirteen recipes share. Every
behaviour a hand-rolled overlay would have to reimplement is inherited from the
element, and the promise makes it usable from an `await`:

<!-- listing: extracted from `apps/lib/view.js` -->
```js
  // window.confirm is blocked in a sandbox without allow-modals, and blocking
  // the thread would freeze the bridge anyway. This is the in-view version:
  // same semantics, one promise, focus trapped by <dialog>.
  function confirmDialog({ title, body, confirm = "Confirm", cancel = "Cancel",
                           destructive = false }) {
    return new Promise((resolve) => {
      const dialog = h("dialog", {},
        h("h2", { text: title }),
        body ? h("p", { class: "muted", text: body }) : null,
        h("div", { class: "row", style: "justify-content:flex-end" },
          h("button", { class: "quiet", text: cancel,
            onclick: () => { dialog.close(); resolve(false); } }),
          h("button", { class: destructive ? "danger" : "primary", text: confirm,
            onclick: () => { dialog.close(); resolve(true); } })));
      dialog.addEventListener("cancel", () => resolve(false));
      dialog.addEventListener("close", () => dialog.remove());
      document.body.append(dialog);
      dialog.showModal();
    });
  }
```

The `cancel` listener is the one people leave out. It fires when the user
presses Escape, and without it the promise never settles and the code awaiting
the answer waits forever in a frame that looks fine.

**Everything is clipped by the frame.** A popover that would overflow the
viewport in a page just overflows; here it is cut off by the iframe's edge and
there is no way to render outside it. Position with the frame's bounds, not
the screen's, and prefer flipping to a different side over letting the content
extend past the boundary. A dropdown that opens downward at the bottom of the
frame is a dropdown nobody can read.

**Tooltips need a second route.** They are hover-only by construction, and
`hostContext.deviceCapabilities.hover` tells you when hover does not exist.
On a touch device, move the content into the label, a popover triggered by
tap, or a description that is always visible.

**Context menus need a keyboard route.** Shift+F10, a visible button, or both.
Chapter 10 has the details.

#### Why `<dialog>` and not a div

The list of what a hand-rolled overlay loses is longer than people expect, and
hand-rolled overlays are still the common case, usually because somebody
needed one animation the native element did not offer. Each item below is a
behaviour you are then committing to re-implement, and most of them are
invisible until somebody uses a keyboard or a screen reader.

`showModal()` puts the dialog in the top layer, which means it renders above
everything regardless of stacking context, and no `z-index` arms race is
needed. It makes the rest of the document inert, so clicks and focus cannot
reach it. It gives you `::backdrop` as a real pseudo-element. It handles
Escape, firing a `cancel` event you can intercept. It restores focus to the
previously focused element on close. And it carries the modal semantics
assistive technology needs without a single ARIA attribute.

A div with `position: fixed` gives you none of those, and the versions people
write typically reimplement two of them badly. The one thing to remember is
the `cancel` event: a dialog whose promise is only resolved by its buttons
hangs forever when the user presses Escape, and in an application that awaits
the answer, a hung promise is a frozen interface.

## Controls

| Component | Composes | APG pattern |
|---|---|---|
| Button | `input.pointer`, `input.keyboard` | Button |
| Checkbox, radio | `input.keyboard`, `input.selection` | Checkbox, Radio Group |
| Toggle | `input.keyboard` | Switch |
| Slider | `input.pointer`, `input.keyboard` | Slider |
| Stepper | `input.keyboard` | Spinbutton |
| Segmented control | `input.keyboard`, `input.selection` | Radio Group |
| Filter chip | `input.selection`, `input.keyboard` | Checkbox |
| Dropdown | `input.keyboard`, `surface.focus` | Listbox |
| Combobox | `input.keyboard`, `input.selection`, `surface.focus` | Combobox |

**Start from the native element.** `<button>`, `<input type="checkbox">`,
`<input type="range">`, `<select>` all work, all come with keyboard and screen
reader support, and all are one CSS file away from matching your design. The
recipes use native elements everywhere except the combobox, which does not
exist natively.

**Target size is a host-dependent decision.** WCAG 2.2 requires 24 by 24 CSS
pixels at AA and 44 by 44 at AAA, and `deviceCapabilities` is where you find
out whether you are on touch. A toolbar designed at 28 pixels clears AA and is
still unpleasant on a phone, and you cannot detect a phone by width when the
same width is a side panel on a desktop.

**Disabled controls carry an obligation.** A disabled button is a promise that
something could enable it, and the user is entitled to know what. If the
reason is a missing host capability, do not disable, omit: Chapter 1's
argument. If the reason is state, say so.

**The combobox is the one worth buying.** It is the most
complex pattern in the APG, it involves a listbox that must be positioned
within the frame, and getting the `aria-activedescendant` and expanded state
right takes longer than any other component here. If a plain `<select>` or a
text input with a datalist will do, take it.

## Text input

| Component | Composes | APG pattern |
|---|---|---|
| Text field | `input.keyboard`, `surface.focus` | (native) |
| Search field | `input.keyboard`, `input.shortcut` | (native) |
| Multiline editor | `input.keyboard`, `history.transaction` | (native) |
| Autocomplete | `input.keyboard`, `input.selection` | Combobox |
| Token input | `input.keyboard`, `input.selection`, `clipboard.write` | Combobox |
| Rich text editor | `history.transaction`, `input.selection`, `ui.prefill` | (none) |
| Code editor | `input.keyboard`, `clipboard.write`, `input.selection` | (none) |

**Validate on blur and on submit, never on keystroke.** Telling somebody their
email is invalid while they are typing the at sign is the fastest way to make
a form feel hostile. Recipe 13 tracks a `touched` flag per field and only
shows an error after the field has been left once.

<!-- listing: extracted from `apps/recipes/r13-settings/index.html` -->
```js
  if (!email && (!live || $("#email").dataset.touched)) {
    $("#email").setAttribute("aria-invalid", "true");
    $("#email-err").hidden = false;
    $("#email-err").textContent = "That is not an address this will reach.";
    ok = false;
  } else {
    $("#email").removeAttribute("aria-invalid");
    $("#email-err").hidden = true;
  }
```

Two attributes do the accessibility work. `aria-invalid` is what a screen
reader announces when focus lands back on the field, and the error element is
referenced by `aria-describedby` so the message is read as part of the field
and not as a stray paragraph. Toggling `hidden` on the message rather than
emptying its text keeps the layout from jumping as the user moves through the
form.

**Undo grouping is per pause, not per keystroke.** Chapter 16. In a rich text
editor this is the difference between an undo stack somebody can use and one
that steps back a character at a time.

**Search fields want a shortcut and cannot safely have one.** Cmd/Ctrl+F is
the convention and the host may own it. Bind it, expect to lose it sometimes,
and always provide the visible field.

**Rich text is where the agent shows up.** A text field can be prefilled and
the user sees the value change. A document cannot: the agent's rewrite has to
appear as a proposal, with the original still visible, and accepting it has to
be one undo transaction. Recipe 4 is the worked example, and the proposal card
is a component in its own right that Chapter 25 lists.

**Code editors are a decision about weight.** A real editor is a large
dependency inside a frame with a restrictive CSP and no CDN unless the server
declares one. A `<pre>` with syntax highlighting done server-side covers
reading, which is most of what a review interface does. Recipe 8 renders a
diff with no editor at all.

### What each overlay costs

A quick reference, because the trade is genuinely different from a page. In a
page an overlay costs the user a moment; in a 380 pixel frame it costs them the
entire interface for as long as it is open.

| Component | Cost in a four hundred pixel frame | Use when |
|---|---|---|
| Alert | Blocks everything, clipped by the frame | Almost never; usually a toast |
| Confirmation | Blocks, but small | The action is destructive and not undoable |
| Modal | Covers the whole view | The task genuinely needs the whole surface |
| Sheet or drawer | Covers most of the view, animates | A secondary task the user returns from |
| Popover | Clipped at the frame edge | Short content anchored to a control |
| Tooltip | Unreachable without hover | Never the only route to information |
| Context menu | Clipped, needs a keyboard route | Per-item actions, with a visible alternative |

The pattern in the right-hand column is that the answer is almost always
"smaller than you think". A modal inside a card is a card that has become
unusable for the duration; a sheet that covers eighty percent of a small frame
is a modal wearing a different animation.

### The one component worth not building

The combobox, and it is worth being specific about why. It is the most complex
pattern in the Authoring Practices Guide. It needs a listbox positioned within
a frame that clips it. It needs `aria-activedescendant`, an expanded state, a
value that may or may not be one of the options, and typeahead that does not
fight the input. And it needs all of that to work with a virtual list once the
option count passes a few hundred.

Recipe 1 uses a plain `<select>` for its environment filter for exactly this
reason. The filter has four options. A combobox would be worse in every
dimension including the one it exists to improve, because typing to filter
four items is slower than reading four items, and the native control already
opens above or below depending on where the frame sits in the host's window.

## Design at your narrowest width

Every component in this chapter is smaller than the version you have built
before, and the reduction is not proportional. Halving the width does not halve
what fits, because labels, padding and touch targets do not scale down with
it.

A toolbar of nine buttons becomes four and an overflow menu. A three-column
form becomes one column. A 600 pixel modal has to work at 380. None of that is
new to anyone who has built a responsive layout; what is new is that the
narrow case is the *common* case here, because an inline card in a chat
transcript is narrower than a phone and the host chose the width, not the
user.

The useful discipline is to design at the narrowest width you will accept, and
to let `surface.resize` report the height. Everything in this book is built at
380 pixels first, and the recipes look the same at 900 because the layout only
ever had one column to lose.

## Conformance checks

1. Every overlay traps focus while open and restores it on close.
2. Escape closes any overlay and resolves whatever was awaiting it.
3. No overlay renders outside the frame's bounds.
4. Native controls are used where they exist, and replacements carry the same
   keyboard behaviour.
5. Hit targets clear 24 by 24 CSS pixels everywhere, and 44 by 44 when
   `deviceCapabilities.touch` is set.
6. Validation errors appear on blur and on submit, not on keystroke.
7. Every error is associated with its field through `aria-describedby`.
