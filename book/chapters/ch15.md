You have no storage. Persist through a server tool instead.

Undo is a different story: nobody can build it for you, and in an application
where a model can also edit the document it is the mechanism that makes that
acceptable.

@demo lab-state

## Where do I keep state?

@cap state.save

@cap state.restore

On the server, through a tool.

`localStorage` either throws or is discarded with the frame, because the view's
origin is opaque. The demo probes it at startup and reports what it found.

There is no message either. No `ui/set-state`, no `ui/get-state`, nothing in
`hostContext` that round-trips. The OpenAI Apps SDK has `setWidgetState`, which
is exactly this feature, and the extension's own "Future Considerations" lists
state persistence as deferred.

**The workaround is a server tool.** Persist through `tools/call`, keyed by
something stable that the server knows: a conversation identifier, a document
id, the tool's own arguments. Recipe 4 does this, with a `save_document` tool
marked `visibility: ["app"]` so the model neither sees it nor can call it.

<!-- listing: extracted from `apps/recipes/r04-document-editor/server.js` -->
```js
save_document: {
  description: "Persist the draft. Called by the view, not by the model.",
  inputSchema: { type: "object", properties: { html: { type: "string" } },
                 required: ["html"] },
  visibility: ["app"],
  run: ({ html }) => {
    document = html;
    saves += 1;
    return { content: [{ type: "text",
      text: `Saved revision ${saves} at the server.` }] };
  },
},
```

**What the workaround costs.** A round trip for every save, which means
debouncing and an autosave interval rather than saving on every keystroke.
Server state for something that is conceptually local, like a scroll position
or which panel is open, which feels wrong because it is. And no persistence at
all when `hostCapabilities.serverTools` is absent, which is a real Level 1
host.

**What a mechanism would look like.** `ui/set-view-state` and a `viewState`
field in the initialize result, scoped to the view identity the host already
has, with a size limit the host enforces. Cheap, obviously useful, and
proposed by prior art on both sides of this ecosystem.

**Design around it in the meantime.** Ask what genuinely has to survive. A
document does. A sort order probably does not, and reconstructing it from the
tool arguments is free. The recipes here persist documents and preferences and
deliberately forget everything else, which is not a compromise so much as a
discipline the gap forced.

## How do I build undo?

@cap history.transaction

A stack of transactions, not a stack of snapshots. Each transaction knows how
to apply itself and how to reverse itself.

<!-- listing: extracted from `apps/labs/lab-state/index.html` -->
```js
const past = [];
const future = [];

function apply({ label, forward, back }) {
  forward();
  past.push({ label, forward, back });
  future.length = 0;
  draw();
  announce(label);
}
```

Three properties of that shape matter.

**Clearing the redo stack on a new action** is what makes the history a line
rather than a tree, and it is what every user expects.

**A label per transaction** is what lets you say "Undid delete Contracts"
instead of "Undid". In an application where an agent also makes changes, the
label is how a user tells whose change they are about to reverse.

**Closures rather than snapshots** is the part that matters in an agentic
application. A snapshot-based undo reverts the whole document to an earlier
state, which also silently reverts anything the agent did in between. A
transaction reverses exactly its own change and leaves the rest alone.

**Grouping.** One transaction per meaningful unit, not per event. Typing gets
grouped by pause: Recipe 4 commits a transaction after 900 milliseconds of
inactivity. Dragging gets one transaction on drop, not one per pointermove.
The test is whether a user pressing Undo once gets back to a state they
recognise.

## What belongs in the undo stack?

@cap history.undo

@cap history.redo

The operations themselves are four lines each once the transaction model
exists. What deserves the attention is what belongs in the stack.

**Include the agent's changes.** This is the argument of Chapter 20 arriving
early. When an agent rewrites a paragraph, that rewrite goes on the same undo
stack as the user's own edits, so a single Cmd+Z takes it back. An agent whose
changes cannot be undone is an agent people will not let near their document,
and correctly so.

Recipe 4 makes accepting a proposed rewrite exactly one transaction, so one
Undo restores the human's words. That is the whole safety story for
agent-assisted editing, and it is nine lines of code.

**Do not include selection, scroll, or view state.** Undo that restores a
scroll position feels broken, because the user's model of undo is about
content. Some editors undo selection changes as part of restoring context,
which is a defensible variant, but undoing a *pure* selection change as its
own step is not.

**Bind the shortcuts.** Cmd/Ctrl+Z and Shift+Cmd/Ctrl+Z, with the caveats from
Chapter 9 about the host possibly owning them. Provide visible buttons too,
because a shortcut the user cannot see is a shortcut most users do not have.

**Accessibility.** Announce the label, both ways. A screen reader user
pressing Undo needs to hear what was undone; a silent stack change is
indistinguishable from a key that did nothing.

## Where the two interact

These two capabilities interact in a way worth naming. Undo depth is state,
and it is state that does not survive a teardown, because the closures cannot
be serialised. So a view that persists its document but not its history comes
back with a document it cannot un-edit.

That is usually the right trade. Serialising a transaction stack means
representing every operation as data rather than as a closure, which is a
substantially larger design, and the value of undoing something from before a
reload is low. But it should be a decision rather than a discovery. Recipe 4
persists the document, drops the history, and says so.

## What actually has to survive?

Because persistence is expensive here, the useful discipline is to sort state
into three buckets before writing any of it.

**Reconstructible.** Anything derivable from the tool arguments or the tool
result. A sort order, a filter, which tab is open, the current page. All of it
comes back for free on the next render, and persisting it is work that buys
nothing.

**Worth a round trip.** Documents, drafts, annotations, preferences. Things a
person made. These go to a server tool, and the cost is real, so debounce them
and save on pause rather than on change.

**Deliberately forgotten.** Undo history, scroll position, transient
selections. Losing them is mildly annoying and keeping them is disproportionate
work, particularly for undo, where serialising a stack of closures means
redesigning the whole transaction model as data.

Recipes 4 and 13 persist exactly the second bucket and say so in their entries.
The value of writing the buckets down is that it turns "we should save state"
into three short lists, one of which is empty work.

## A transaction, in full

The shape is small enough to state completely, and every recipe that has undo
uses exactly this.

A transaction is an object with a label, a `forward` closure and a `back`
closure. `apply()` runs forward, pushes it onto the past, and clears the
future. `undo()` pops the past, runs back, and pushes onto the future.
`redo()` does the reverse. Four methods, about twenty lines, and no library.

Three refinements the recipes add, each for a specific reason.

**Coalescing by pause.** Typing produces one transaction per quiet period
rather than per keystroke, because undo that steps back a character at a time
is undo nobody uses.

**Capturing by value, not by reference.** A `back` closure that restores an
array must have captured a copy, or it restores a reference to the array that
was mutated. This is the bug that makes undo appear to work and then not.

**Recording the index.** Removing an item and putting it back at the end is not
an undo. Recipe 3's move records where the node came from, which is the
difference between reversing a change and approximating it.

## Conformance checks

1. `localStorage` inside the frame either throws or is discarded with the
   frame, and the view does not depend on it.
2. A view's persisted state survives a teardown and a re-render, through
   whatever server tool it uses.
3. An app-only save tool is absent from the agent's tool list.
4. Undo reverses exactly the last transaction and leaves later changes alone.
5. A new action clears the redo stack.
6. An agent-initiated change is undone by one Cmd/Ctrl+Z.
7. Undo and redo announce what they did.

## What to remember

Persistence is a gap with a workable but heavy workaround, so keep the set of
things that must survive as small as you can defend. Undo is not a gap, it is
a design, and in an agentic application it is the mechanism that makes it safe
for a model to touch a document at all.
