The shortest chapter in Part II, and the one with the highest ratio of
"already solved" to "your problem". Three of its four capabilities are HTML
input types that have had a decade of platform work behind them, and the main
advice is to use them.

@demo lab-pickers

## Use the native ones

@cap picker.date

@cap picker.time

@cap picker.color

`<input type="date">`, `type="time"`, and `type="color"` work inside the
sandbox with no permission and no message. They come with keyboard support,
screen reader support, the platform's own calendar and colour panel, and
localisation for every region the browser knows about, which is more than your
component library knows about.

The argument for replacing them is usually visual: they do not match the
design. That is true, and the cost of replacing them is a component that has
to reimplement date arithmetic, week-start conventions, month names in the
user's language, and a keyboard model, and that will still be wrong for the
calendar systems you have not heard of. In a four hundred pixel card next to
somebody's conversation, the trade is not close.

**The one thing you have to add.** The picker collects a value; you have to
*display* values in the user's terms, and the browser's idea of "the user" is
the machine, not the person the host is serving. Formatting comes from
`hostContext.locale` and `hostContext.timeZone`, through `Intl`.

<!-- listing: extracted from `apps/lib/view.js` -->
```js
function formatters(hostContext) {
  const locale = hostContext?.locale || undefined;
  const timeZone = hostContext?.timeZone || undefined;
  return {
    number: (n, options) => new Intl.NumberFormat(locale, options).format(n),
    date: (value, options = { dateStyle: "medium" }) =>
      new Intl.DateTimeFormat(locale, { ...options, timeZone })
        .format(value instanceof Date ? value : new Date(value)),
    time: (value) => new Intl.DateTimeFormat(locale, {
      timeStyle: "medium", timeZone })
      .format(value instanceof Date ? value : new Date(value)),
  };
}
```

Press "Switch to ja-JP / Tokyo" in the demonstration. The pickers keep their
ISO values, which is correct, and everything the view renders changes, which
is also correct. A view that formats with the default locale looks right on
the developer's machine and wrong for most of its users.

**Accessibility.** Native inputs come with the platform's accessibility
already wired. What they still need from you is a real `<label>` associated
with the input, a hint about the expected format when there is one, and enough
contrast on the border that the field is visible in a high contrast theme.

## Picking something the server owns

@cap picker.resource

The fourth is different in kind. A file picker reaches the user's machine. A
resource picker reaches the *server's* namespace, and the view has no
connection to the server. Everything goes through the host.

`resources/read` is available to the view when
`hostCapabilities.serverResources` is present. Give it a `ui://` or other URI
and the host proxies the read to the server and returns the contents.

<!-- listing: extracted from `apps/labs/lab-pickers/index.html` -->
```js
$("#load").onclick = async () => {
  try {
    const result = await bridge.readServerResource($("#uri").value);
    $("#out").textContent = result.contents?.[0]?.text ?? JSON.stringify(result);
  } catch (error) {
    $("#out").textContent = `Refused: ${error.message}`;
  }
};
```

**The awkward part, and a live discrepancy.** The specification's list of
standard MCP messages available to a view names exactly one resource method:
`resources/read`. On a plain reading, a view can read a resource it already
knows the URI of and cannot discover one.

The SDK disagrees. `@modelcontextprotocol/ext-apps` ships
`App.listServerResources()`, and its own documentation uses it to build a
picker by filtering the returned list on MIME type. `hostCapabilities` also
carries `serverResources.listChanged`, which only means something if listing
is proxied at all.

So the honest position is that `resources/list` from a view is supported by
the reference implementation and unstated in the specification text, which
means hosts may reasonably differ. Treat it as an enhancement: try the list,
and have a fallback for a host that refuses. This book files it as a
documentation gap rather than as a design one, because the SDK's behaviour
looks like the intended one.

A picker can also learn its options without listing at all: from the tool
result that rendered the view, from a server tool that returns a list, or from
a namespace the server documents. The last two are worth preferring anyway,
because a server tool returning a list also gets you filtering and pagination.
In the demonstration the options come from the host fixture, and the "missing"
entry is there so you can watch a refused read.

**Security.** This is the good path for reading server-side data, and it is
worth choosing over a `fetch` to your own API even when you could declare the
origin in `connectDomains`. A read through the host is visible to the host,
subject to the host's policy, and appears in the transcript. A direct fetch is
a hole you asked the host to open and then used unobserved.

**Failure modes.** Unsupported when `serverResources` is absent: the picker
should not appear, and whatever it was going to configure needs a different
route. Denied and failed both come back as JSON-RPC errors, and the error
message is the host's, so display it rather than replacing it with your own
guess.

## Dropzones

@cap file.dropzone

Covered in Chapter 10, listed here because a dropzone and a picker are two
routes to the same thing and an application that offers one should usually
offer both. The picker is discoverable, the dropzone is fast, and users split
roughly evenly between them.

The one addition specific to this chapter: a dropzone that accepts a *type* of
file should say so in its resting state, not only in its error state. "Drop a
JSON annotation file" tells somebody what to look for. "Drop files here"
followed by "wrong file type" tells them what they did wrong.

## What a picker costs at each level

| Level | What you get | What you build |
|---|---|---|
| 1 | Native date, time and colour inputs | Formatting through the host's locale |
| 2 | The same, plus files through `file.open` | Validation and preview |
| 3 | Resource reads through the host | The list, and a fallback when reads fail |

The table is worth reading as a warning about the third row. A resource picker
looks like a small feature and it is the only one here that depends on a host
capability, a server round trip, and a listing mechanism the specification does
not describe. Budget accordingly, and consider whether a server tool returning
exactly the options you need would be simpler than a general picker.

## Failure modes across the group

**Unsupported.** The native inputs cannot be unsupported; every browser has
them. `picker.resource` is unsupported when `serverResources` is absent, and
the correct response is to omit the picker and configure the thing some other
way, usually from the tool arguments that rendered the view.

**Denied.** Only `picker.resource` can be denied, as a JSON-RPC error from the
host. Show the host's message rather than replacing it with a guess.

**Failed.** A resource that does not exist returns an error with the URI in it.
Say which resource, because a picker with three options and one broken one is
a picker whose failure the user can work around.

**Cancelled and timeout.** The native pickers cannot be cancelled from outside,
and a dismissed picker simply leaves the value unchanged, which needs no
handling. A resource read has no timeout of its own, so give it one.

## Conformance checks

1. Native date, time and colour inputs render and open their platform pickers
   inside the sandbox.
2. Values are displayed using `hostContext.locale` and `hostContext.timeZone`,
   not the machine's.
3. Changing the host locale re-renders every formatted value without a reload.
4. `resources/read` through the host returns content for a known URI.
5. A read for an unknown URI returns an error, and the view reports it.
6. With `serverResources` absent, the view sends no `resources/read`.

## What to remember

Two rules. Use the platform's inputs, because they are better than the ones
you would write and they are free. And format every value you display through
the host's locale and timezone rather than the browser's, because in this
environment the browser is not where the user is.

## A note on what "native" buys you

The date input is worth one more paragraph, because the argument generalises to
every native control in Chapter 22.

Ask what a replacement has to know. Which day the week starts on, in the user's
region. The names of the months, in the user's language, in the correct
grammatical case for a date rather than for a list. Whether the region uses a
non-Gregorian calendar. How to type a date rather than pick one, because most
people type. What a screen reader should say when the value changes. How the
picker behaves at 200% zoom, and on a touch device, and under forced colours.

The browser knows all of that, for every locale it supports, and it was paid
for by somebody else. A component library knows some of it for the locales its
authors tested. A component you write in a four hundred pixel frame at the end
of a sprint knows the first two.

The visual mismatch is real and it is the only cost. In an embedded view that
is already visually distinct from its host by design, it is a smaller cost than
it looks.
