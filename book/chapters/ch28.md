Two subjects that belong together, because the second is what makes the first
credible. A book can assert that fourteen capabilities are missing. A book
whose demonstrations run in your browser, and whose transcripts show exactly
where each workaround happens, has shown you.

## The loop

::: {.principle}
Primitives compose into components. Components compose into applications.
Applications become coverage tests. A test that cannot be written names a
missing primitive.
:::

The loop only works in that direction. Starting from "what should the protocol
have" produces a wish list. Starting from "build the thirteen applications
people actually ask for" produces fourteen findings, each attached to a recipe
that needs it and a workaround somebody had to write.

Every gap in this book arrived that way. `state.save` was found by the
Document Editor needing to survive a reload. `tool.partialOutput` was found by
the Monitoring Console needing a log tail. `notify.attention` was found by an
error arriving at three in the morning in a view nobody was looking at.
`approval.request` was found by asking what the Approve button actually
guarantees, and finding that the answer is nothing.

## What a good finding looks like

Four parts, and Appendix B carries all four for each of the fourteen.

**The recipe that needs it.** Not a hypothetical. A named application, in this
repository, that a reader can run.

**What the workaround costs.** Every gap has one, and stating the cost is what
separates a finding from a complaint. Persistence through a server tool costs
a round trip and stops working at Level 1. Streaming through repeated tool
results costs portability. Approval through a queue-and-perform convention
costs the guarantee.

**The shape of a mechanism.** One request, one notification, or one context
field, described concretely enough to argue with. `ui/set-view-state` and a
`viewState` field in the initialize result. A `visibility` field in
`ui/notifications/host-context-changed`. `ui/request-attention` with a severity
and a label.

**What it reopens.** Chapter 4's threat model, applied to the proposal. A
mechanism that reopens one of the five attacks needs a better story than
convenience, and saying which attack in the proposal saves everybody an
argument later.

## Where findings go

Upstream, as issues against the extension specification, not into a private
extension. A host-specific mechanism for view state solves the problem for one
host and fragments it for everybody else, which is the outcome the extension
exists to prevent.

The counter-argument is real: sometimes a host has to ship something before a
specification exists. The mitigation is to ship it as an `experimental`
capability, which both `hostCapabilities` and `appCapabilities` already
reserve a slot for, and to file the finding at the same time.

## The live book

Everything on these pages runs, and the arrangement is simpler than it looks.

**One source tree, three views of it.** The application is executed, in a
sandboxed iframe. Its source is read, fetched from the same directory the
iframe loaded it from. And the conversation between them is narrated, in the
transcript pane, as it happens.

The code pane cannot drift from the running code, because they are the same
file over the same URL. That is the entire mechanism, and it replaces a build
step that extracts listings and a discipline that keeps them current.

**The host is an emulator, not a mock.** About two hundred and fifty lines
implementing the host half of the bridge: it answers `ui/initialize`, applies
capability rules, resolves `tools/call` from fixtures, honours resize
requests, arbitrates display modes, and tees every message to the log. It is a
real host implementation with a fixture file where a server would be, and the
capability checks in it are the same checks a real host makes.

**The fixtures come from real servers.** `tools/record_fixtures.mjs` starts
each recipe's actual MCP server over stdio, calls the tools listed in its
`record.json`, and writes the responses to `fixtures.json`. So the sentence
this book makes is true: the view in the live pane receives what the code in
the server pane produces. The demonstration is honest even though the server
is not executing in your browser.

**Nothing is hosted.** Static files on GitHub Pages. No backend, no build
server, no runtime. That is possible because an MCP application does not need
a model or a server to render, only something willing to answer the host side
of a `postMessage` conversation.

## What the transcript pane is for

It is a teaching device and a verification artifact at the same time, and the
second use is the one worth noticing.

The log you see on a page is the same log `tools/check_demos.mjs` records into
`conformance/transcripts/` when it drives the same page in headless Chrome.
Layer 1 of Chapter 26 is literally the thing on screen. When a recipe entry
says "selecting a row sends exactly one `ui/update-model-context`", you can
verify it by selecting a row, and the build verifies it by diffing a file.

## The fixture chain, in detail

The claim that the demonstrations are honest rests on one chain, and it is
short enough to state completely.

Each recipe has a `server.js` that is a real MCP server over stdio. It answers
`initialize` by declaring the UI extension, `tools/list` with descriptors
carrying `_meta.ui.resourceUri`, `tools/call` by running the tool, and
`resources/read` by returning the view's HTML with its content security policy
attached.

`tools/record_fixtures.mjs` starts that server as a child process, sends the
calls listed in the recipe's `record.json`, and writes the responses to
`fixtures.json`. Nothing is hand-written and nothing is edited afterwards.

The demonstration's host configuration imports `fixtures.json` and answers
`tools/call` from it. So when the Data Explorer renders eight deployments with
a worst p95 of 1290ms, those numbers came out of the server whose source is in
the next tab.

What is *not* true is that the server is running in your browser. It is not,
and it could not be: a static site has no process to run it in. The fixture is
a recording, and the check that keeps the recording current is that
`make fixtures` regenerates it from the server on every build.

## What it would take to run this against your host

The suite is deliberately unexotic, and the port is smaller than it looks.

The demonstrations do not depend on the emulator's internals. They depend on a
host that answers `ui/initialize`, applies capability rules honestly, and can
be told to do host-side things on command: change the container, withdraw a
display mode, deliver a tool result, start a teardown. Any host with a
development mode can expose those.

The harness depends on three things: a page it can load, a way to observe the
message log, and a way to click host-side controls. In this repository the log
is in the DOM because the demo widget puts it there. In another host it would
more likely be a hook that receives every message, which is easier rather than
harder.

What does not port, and is the honest limit from Chapter 26, is driving the
view's own interface. That needs either the view's registered tools or a host
willing to grant `allow-same-origin` in a test configuration, and the first is
the better answer because it is the same mechanism agents and accessibility
tools use.

## Try this on any page

Three things worth doing once, in any demonstration on this site, because they
make the whole architecture visible in about a minute.

Open the Messages tab and reload the view. Watch the handshake: two lines out,
one line back, then a size report. That is the whole startup sequence for every
MCP application there has ever been.

Press a control in the grey strip. Those are the things only a host can do, so
the page does them on the host's behalf, and each one produces a message you
can expand and read.

Then open the `index.html` tab and find the code that handled it. The file the
tab shows is the file the frame above is running, fetched from the same URL,
which is the one guarantee that makes a book about a protocol worth reading two
months after it was written.

## The escalation path this book does not take

Two levels above what is here, both worth naming.

Small client-only examples can be made editable in place with an in-browser
bundler, so a reader can change `app.tsx` and watch the iframe re-render. That
needs a custom template carrying the bridge shim, and it is the obvious next
step for the labs.

Full server-plus-view examples can open in a browser-based Node runtime, which
boots the actual MCP server in a tab and runs it against a real host. That is
how the extension's own examples run locally against its reference host, and
it would turn the recipes from demonstrations into things a reader can fork
without installing anything.

Neither is here. What is here is thirty applications that run, their sources,
their transcripts, and a repository where all of it regenerates with one
command.
