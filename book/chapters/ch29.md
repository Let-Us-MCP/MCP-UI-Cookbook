Two subjects in one chapter, because the second is what makes the first
credible. A list of missing capabilities is an opinion until somebody can run
the applications that needed them and watch the workaround happen.

Anyone can assert that sixteen capabilities are missing. A book whose
demonstrations run in your browser, with transcripts showing exactly where each
workaround happens, has shown you. Appendix B names the recipe behind every one
of the sixteen, and every one of those recipes is on this site with its message
log open, so the sentence "there is no message for this" is checkable in the
place it is made.

## How a gap gets found

::: {.principle}
Primitives compose into components. Components compose into applications.
Applications become coverage tests. A test that cannot be written names a
missing primitive.

The last step is the one that does the work. A conformance check is a sentence
about observable behaviour, and a sentence you cannot phrase without inventing
a message is a gap with a name attached.
:::

The loop only works in that direction. Starting from "what should the protocol
have" produces a wish list. Starting from "build the thirteen applications
people actually ask for" produces sixteen findings, each attached to a recipe
that needs it and a workaround somebody had to write.

Every gap in this book arrived that way. `state.save` was found by the
Document Editor needing to survive a reload. `tool.partialOutput` was found by
the Monitoring Console needing a log tail. `notify.attention` was found by an
error arriving at three in the morning in a view nobody was looking at.
`approval.request` was found by asking what the Approve button actually
guarantees, and finding that the answer is nothing.

## What a good finding contains

Four parts, and Appendix B carries all four for each of the sixteen gaps. A
finding missing any of them is a complaint: the recipe pins it to something
real, the cost stops it being a wish, the mechanism makes it arguable, and the
threat-model note is what stops it being naive.

**The recipe that needs it.** Not a hypothetical. A named application, in this
repository, that a reader can run.

**What the workaround costs.** Every gap has one, and stating the cost is what
separates a finding from a complaint. Persistence through a server tool costs
a round trip and stops working at Level 1. Streaming through repeated tool
results costs portability. Approval through a queue-and-perform convention
costs the guarantee.

**A concrete mechanism.** One request, one notification, or one context field,
specific enough to argue with: `ui/set-view-state` plus a `viewState` field in
the initialize result; a `visibility` field on
`ui/notifications/host-context-changed`; `ui/request-attention` with a severity
and a label.

**What it reopens.** Chapter 5's threat model, applied to the proposal. A
mechanism that reopens one of the five attacks needs a better story than
convenience, and saying which attack in the proposal saves everybody an
argument later.

## Where findings go

Upstream, as issues against the extension specification. A host-specific
mechanism for view state solves the problem for one host and fragments it for
everybody else, which is exactly the outcome this extension was created to
prevent.

The counter-argument is real: sometimes a host has to ship something before a
specification exists. The mitigation is to ship it as an `experimental`
capability, which both `hostCapabilities` and `appCapabilities` already
reserve a slot for, and to file the finding at the same time.

## How the live book works

Everything on these pages runs, and the arrangement behind it is simpler than
it looks. There is no backend, no build server and no runtime: the whole site
is static files served by GitHub Pages, which is possible only because an MCP
application needs neither a model nor a server in order to render. What it
needs is something willing to answer the host side of a `postMessage`
conversation, and that fits in 250 lines of JavaScript.

**One source tree, three views of it.** The application is executed, in a
sandboxed iframe. Its source is read, fetched from the same directory the
iframe loaded it from. And the conversation between them is narrated, in the
transcript pane, as it happens.

The code pane cannot drift from the running code, because they are the same
file over the same URL. That is the entire mechanism, and it replaces a build
step that extracts listings and a discipline that keeps them current.

**The host is an emulator, not a mock.** About two hundred and fifty lines
implementing the host half of the bridge: it answers `ui/initialize`, applies
capability rules, resolves `tools/call` from fixtures, honours resize
requests, arbitrates display modes, and tees every message to the log. It is a
real host implementation with a fixture file where a server would be, and the
capability checks in it are the same checks a real host makes.

Resolving a view is the part worth reading, because it is the sequence
Chapter 3 describes and nothing about it is simulated:

<!-- listing: extracted from `emulator/host.js` -->
```js
    const uri = descriptor?._meta?.ui?.resourceUri;
    if (!uri) {
      throw new Error(`${toolName} has no _meta.ui.resourceUri, so a host has `
        + "nothing to render");
    }
```

The view is never named by anyone. The host looks up the tool the model
called, reads the binding off its descriptor, and reads that resource. A tool
without the field is not an error condition to recover from; it is an ordinary
tool, and the host renders its text.

**The fixtures come from real servers.** `tools/record_fixtures.mjs` starts
each recipe's actual MCP server over stdio, calls the tools listed in its
`record.json`, and writes the responses to `fixtures.json`. So the sentence
this book makes is true: the view in the live pane receives what the code in
the server pane produces. The demonstration is honest even though the server
is not executing in your browser.

**Everything regenerates.** `make` rebuilds the pages, `make fixtures` re-records
the server responses, and `make check` runs the ten checks Chapter 27
describes. A contributor who changes a recipe's server and forgets to
re-record gets a fixture diff in the same commit, and a contributor who
changes a recipe's behaviour and forgets to update its entry gets a transcript
diff. Neither failure can reach the published site quietly.

## Which demonstrations model what

The thirty demonstrations on this site are two different things, and the
difference matters when you read their transcripts. One group starts before
the view exists and shows you how it came to exist. The other starts at the
moment the view is already loaded, because what it has to show happens after
that point and a prologue would be theatre.

**The thirteen recipes model the whole lifecycle.** Each has a real MCP server
with a `ui://` resource and a tool carrying `_meta.ui.resourceUri`. The host
emulator resolves the view the way a host does: `tools/list`, read the resource
URI off the descriptor, `resources/read`, render what comes back. Their
transcripts open with four host-to-server lines before the view has run a
single statement, and the frame above them is rendering the document that
arrived on line four.

**The seventeen capability labs start after the binding.** They have no server,
no tool and no resource, because each exists to demonstrate one chapter's
capabilities. Chapter 7's lab is about
`ui/notifications/size-changed`, and prefixing it with a tool call it does not
have would be scenery. Their transcripts open at `ui/initialize`.

That split is deliberate, and stating it is the point: a lab that loaded itself
by URL while the book insisted hosts never know a URL would be the same defect
this chapter exists to guard against.

## What the transcript pane is for

It is a teaching device and a test artifact at the same time, and the second
use is what keeps the first honest. The log you see on a page is the same log
`tools/check_demos.mjs` records into `conformance/transcripts/` when it drives
the same page in headless Chrome, so Layer 1 of Chapter 27 is literally the
thing on screen. When a recipe entry says "selecting a row sends exactly one
`ui/update-model-context`", you can verify it by selecting a row, and the build
verifies it by diffing a file. A pane that only illustrated would drift within
a month; this one cannot, because a drift is a failing build.

## The fixture chain, exactly

The claim that these demonstrations are honest rests on one chain, and the
chain is short enough to state completely and check yourself. It has four
links: a real server, a recorder that runs it, a fixture file nobody edits, and
a host configuration that reads only that file. Break any link and the numbers
on the page stop corresponding to the code in the tab beside them, which is
why each link has a check behind it.

Each recipe has a `server.js` that is a real MCP server over stdio. It answers
`initialize` by declaring the UI extension, `tools/list` with descriptors
carrying `_meta.ui.resourceUri`, `tools/call` by running the tool, and
`resources/read` by returning the view's HTML with its content security policy
attached.

`tools/record_fixtures.mjs` starts that server as a child process, sends the
calls listed in the recipe's `record.json`, and writes the responses to
`fixtures.json`. Nothing in that file is hand-written and nothing is edited
afterwards, and `make fixtures` regenerates all thirteen on every build, so a
server whose output changes produces a fixture diff in the same commit.

The whole recorder is one handshake and a loop over the plan:

<!-- listing: extracted from `tools/record_fixtures.mjs` -->
```js
    const write = (message) => child.stdin.write(`${JSON.stringify(message)}\n`);
    write({ jsonrpc: "2.0", id: 0, method: "initialize", params: {
      protocolVersion: "2026-07-28",
      clientInfo: { name: "fixture-recorder", version: "1.0.0" },
      capabilities: { extensions: {
        "io.modelcontextprotocol/ui": { mimeTypes: ["text/html;profile=mcp-app"] } } },
    } });
    calls.forEach((call, i) => write({
      jsonrpc: "2.0", id: i + 1, method: "tools/call",
      params: { name: call.tool, arguments: call.arguments ?? {} },
    }));
```

Newline-delimited JSON over the child process's stdin, which is exactly what a
host does over stdio. The recorder declares the UI extension in its
`initialize` so the server answers as it would to a real host, and there is no
mode flag anywhere in a recipe's server that behaves differently under
recording.

The demonstration's host configuration imports `fixtures.json` and answers
`tools/call` from it. So when the Data Explorer renders eight deployments with
a worst p95 of 1290ms, those numbers came out of the server whose source is in
the next tab.

What is *not* true is that the server is running in your browser. It is not,
and it could not be: a static site has no process to run it in. The fixture is
a recording, and the check that keeps the recording current is that
`make fixtures` regenerates it from the server on every build.

## Running this against your host

The suite is deliberately unexotic, and porting it to another host is smaller
than it looks. The demonstrations do not depend on the emulator's internals.
They depend on a host that answers `ui/initialize`, applies capability rules
honestly, and can be told to do host-side things on command: change the
container, withdraw a display mode, deliver a tool result, start a teardown.
Any host with a development mode can expose those four, and a host that cannot
withdraw a display mode on command cannot be tested against Chapter 7 by
anybody, including its own authors.

The harness depends on three things: a page it can load, a way to observe the
message log, and a way to click host-side controls. In this repository the log
is in the DOM because the demo widget puts it there, and `check_demos.mjs`
reads it with a `page.evaluate` call. In another host it would more likely be
a hook that receives every message, which is easier: reading structured
objects out of a callback beats scraping list items out of a page, and it
removes the one part of this harness that is coupled to how the book is
presented.

What does not port, and is the honest limit from Chapter 27, is driving the
view's own interface. That needs either the view's registered tools or a host
willing to grant `allow-same-origin` in a test configuration, and the first is
the better answer because it is the same mechanism agents and accessibility
tools use.

## Try this on any page

Three things to do once, in any demonstration on this site. Between them they
make the whole architecture visible in about a minute, they need nothing
installed, and they work in whatever browser you are already reading this in.
Do them on Recipe 1 if you want the fullest version, because it is the only
one that exercises all four host-to-server lines and then renders eight rows
from the result.

Open Messages and reload the view. Watch `ui/initialize` go out, the result
come back with `hostCapabilities` and `hostContext` in it,
`ui/notifications/initialized` follow, and then
`ui/notifications/size-changed` carrying the height the document turned out to
need. Four lines, in that order, and every MCP application on any host starts
the same way. Nothing after line four is guaranteed by the specification.

Press a control in the grey strip. Those are the things only a host can do,
which is why they sit outside the frame: resizing the container, changing the
theme, withdrawing a capability, delivering a tool result. The page does them
on the host's behalf, and each one produces a message you can expand and read
in full, including the ones your view is expected to ignore.

Then open the `index.html` tab and find the code that handled it. The file the
tab shows is the file the frame above is running, fetched from the same URL,
which is the one guarantee that makes a book about a protocol worth reading two
months after it was written.

## What this book does not do

Two escalations beyond what is here exist, and neither is built. Both would
make the demonstrations editable in the browser instead of merely runnable,
and both are additive: neither changes anything the book claims, and neither
is a prerequisite for anything in it. They are listed because the absence is a
choice, and a reader who wants either now can build it without waiting for
this book to change.

Small client-only examples can be made editable in place with an in-browser
bundler, so a reader can change `app.tsx` and watch the iframe re-render. That
needs a custom template carrying the bridge shim, and it is the obvious next
step for the labs.

Full server-plus-view examples can open in a browser-based Node runtime, which
boots the actual MCP server in a tab and runs it against a real host. That is
how the extension's own examples run locally against its reference host, and
it would turn the recipes from demonstrations into things a reader can fork
without installing anything.

Neither is here. What is here is thirty applications that run, their sources,
their transcripts, and a repository where all of it regenerates with one
command. That was the smallest thing that could make a book about a protocol
checkable, and checkable was the requirement.
