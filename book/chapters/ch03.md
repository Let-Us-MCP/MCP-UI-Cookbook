A tool declares one view. `McpUiToolMeta.resourceUri` is a single optional
string, so one tool call produces at most one rendered surface, and the surface
belongs to whichever tool the model happened to invoke.

Every recipe server in this book builds its descriptors through one function,
and the binding is the last field:

<!-- listing: extracted from `apps/lib/mcp-server.js` -->
```js
  const descriptors = Object.entries(tools).map(([toolName, tool]) => ({
    name: toolName,
    description: tool.description,
    inputSchema: tool.inputSchema ?? { type: "object" },
    annotations: tool.annotations,
    // The link from a tool to its view. Without this the tool is a normal
    // tool and the host renders text, which is the correct fallback.
    _meta: { ui: { resourceUri, visibility: tool.visibility ?? ["model", "app"] } },
  }));
```

Note that `resourceUri` is closed over from the server's own configuration, so
every tool on one of these servers points at the same view. That is a property
of these thirteen servers and not of the protocol: nothing stops a server
binding different tools to different views. What nothing allows is one tool
binding to two.

On the wire the field is a string, and `make wire` records it from all
thirteen servers so that this claim is checkable rather than asserted:

<!-- listing: extracted from `conformance/wire/r02-dashboard.json` -->
```json
          "_meta": {
            "ui": {
              "resourceUri": "ui://cookbook/dashboard",
              "visibility": [
                "model",
                "app"
              ]
            }
          }
```

There is no array here and no second field beside it. `visibility` controls
*who may call the tool*, not what it renders, and a tool visible only to the
app still renders exactly one view when it is called.

**Nothing in this protocol owns a screen.** There is no page object, no
container that holds several views, and no message anywhere in the extension
that describes an arrangement. A large share of the difficulty in building
anything beyond a single artifact descends from that one fact.

## What does "no page" actually mean?

In ordinary web development a page owns the viewport. It issues whatever
requests it needs, keeps the responses, decides the arrangement, and commits a
render. Composition is a named responsibility held by an object that always
exists, and every framework in the last twenty years assumes it.

Here the surface is the conversation, and the conversation belongs to the host.
Your server supplies views. The host places them, one at a time, into a flow
your server cannot address. Four things follow, and none of them has a
workaround at the protocol level:

- **Views cannot address each other.** Each runs in its own sandboxed iframe
  with an opaque origin. There is no handle, no name, no channel.
- **Views cannot be positioned relative to each other.** No message carries a
  layout, a size relationship, or an ordering.
- **Views cannot share state.** No storage, no shared worker, no common origin.
- **A tool call cannot return two of them.** `resourceUri` is one string.

@cap surface.compose

@cap surface.viewMessage

Both of these are on the specification's own list of deferred features, under
"Other Advanced Features": *Support multiple UI resources in a tool response*
and *View-to-View communication*. They are registered as future work, so this
is a gap with a queue position.

## What happens if two tools with views run in one turn?

The specification does not say. It defines what a host must do when it renders
a view and says nothing about what it should do when a second one arrives in
the same assistant turn, which leaves hosts free to replace, stack, ignore, or
fail. Host behaviour here is not something this book has tested, and Chapter 27
explains why untested cross-host claims are not made anywhere in it.

What you can rely on is the reverse: a host with no extension support ignores
`_meta.ui.resourceUri` entirely and treats the invocation as an ordinary tool
call. Degradation to text is guaranteed by construction, which is why the
`content` field discussed in Chapter 2 is never vestigial and why a view that
carries information absent from `content` has already broken one host.

## Why would anyone design it this way?

Because the alternative is much harder to make safe, and safety is the property
this architecture is organised around.

Predeclared templates, sandbox isolation, server-declared CSP allowlists and
host-mediated egress all exist so that a host can render code from a server it
does not trust. One view at a time, with every outbound request brokered, is a
policy a host can state in a sentence and enforce in code.

Composition changes the question to several mutually untrusted servers
negotiating one surface. Who gets the space. What happens when one view's
content covers another's controls. Whether view A may infer anything from view
B's dimensions. Whether a malicious view can position itself over a legitimate
one, which is the phishing case from Chapter 5 with a new attack surface
attached. Each of those needs an answer before any of it can ship, and the
extension is one year old.

The direction the specification does push is a single view with more reach. An
app may call any tool on its server, and it may ask the host to perform actions
through capabilities the user has already connected. A calendar app asks for a
meeting to be scheduled instead of integrating a calendar itself. That is a
coherent trajectory and it does not pass through panel layout.

## So how do I build a dashboard?

Four constructions are in use. The first is the only one that produces a
genuinely combined view, and it is the one to reach for.

### Separate the data tools from the render tool

Give your data tools no `resourceUri` at all. They fetch, compute and mutate,
and they return `structuredContent`. Then give one render tool the
`resourceUri` and no business logic whatsoever. The model calls the data tools,
does whatever narrowing the request needs, and passes the finished set to the
render tool, which draws once against input the model has already checked.

The schema that seemed to be missing for a combined view turns out to be the
render tool's `inputSchema`. You author it. It does not have to resemble any
data tool's output, because its job is to describe the finished picture.

<!-- listing: illustrative -->
```js
// Data tool: no view, returns rows.
server.registerTool("search_listings", { inputSchema, outputSchema }, handler);

// Render tool: a view, no logic, takes the finished set.
server.registerTool("render_listings", {
  inputSchema: { type: "object", properties: {
    ids: { type: "array", items: { type: "string" } },
    title: { type: "string" },
  }, required: ["ids"] },
  _meta: { ui: { resourceUri: "ui://listings/board" } },
}, handler);
```

Two properties make this worth the extra tool. The model's judgement sits
between the data and the render, so the view shows what was actually asked for
instead of everything the backend could return. And a tool without a
`resourceUri` does not cause a render, so a conversation that calls four data
tools redraws once.

The weakness is ordering. Nothing in the protocol enforces that the data tools
run first, so the dependency lives in the render tool's description and in the
model's willingness to follow it. Write the dependency into the description
explicitly, naming the tool that must run first and the fields you expect.

### Escalate the display mode instead of multiplying views

Where one view is not enough, ask for more room. `ui/request-display-mode`
offers `inline`, `fullscreen` and `pip`, and hosts vary in which they support,
so check `hostContext.availableDisplayModes` before offering the control.
Chapter 7 has the negotiation. This keeps the single-view model and gives you a
larger canvas to arrange things inside, where you own the layout completely.

### Refresh from inside the view

For anything interactive, call the tool from the view with `tools/call` instead
of routing through the model. The view keeps its state, avoids a remount, and
updates in place. This also lets the initial render carry less: bootstrap with
what you need to draw, then fetch the rest from inside. Chapter 20 has the
mechanism.

### Send the user somewhere with more room

Where the artifact is genuinely larger than a panel, `ui/open-link` hands the
user to a full application in a browser, and `ui/download-file` hands them a
self-contained file. Both are honest about the boundary, and both are better
than an interface that pretends a conversation is a dashboard.

## What this does not affect

The model's reasoning across several tool outputs is untouched. Every result
reaches its context, each valid against its own schema, and synthesis in
language needs no schema at all. Asking "what schema describes the
combination?" has no answer because no such schema was ever implied:
`outputSchema` constrains one return value, and nothing in MCP constrains a
whole response.

Combining results in prose is the default and it works. It is combining them
*on screen* that has no construction.

## Conformance checks

1. A tool declares at most one `resourceUri`.
2. A host with no extension support renders `content` and ignores the resource
   reference.
3. A data tool with no `resourceUri` triggers no render.
4. A render tool's `inputSchema` validates the combined payload the model
   assembles.
5. `hostContext.availableDisplayModes` is checked before a fullscreen control
   is offered.

## What to remember

Ask what the natural unit of your product is before you design anything. Where
that unit is one artifact rendered well and interacted with in place, the fit
is close and the remaining friction is incidental. Where the unit is a composed
screen, you are working against the grain of the design, and no arrangement of
schemas will change that, because the object you are looking for is not in the
protocol.
