Two groups, one theme: the user is waiting, may stop waiting, and deserves an
accurate account either way.

Media takes time and the platform handles almost all of it. A tool call takes
time and the protocol handles some of it.

@demo lab-media

## How do I play audio or video?

@cap media.playback

`<video>` and `<audio>` work inside the sandbox. Controls, seeking, playback
rate, volume, and caption tracks through `<track>` are all platform behaviour
with no host involvement.

Three embedded-specific notes.

**Media has to come from somewhere.** The restrictive default CSP is
`media-src 'self' data:`, so a view loading video from a CDN must declare that
origin in `resourceDomains`, and a host may decline it. Data URIs work and are
impractical past a few hundred kilobytes.

**Autoplay will not work, and should not.** Autoplay policies require a user
gesture or a muted element, and a view that starts playing sound inside
somebody's conversation without being asked is an actively bad citizen. Start
paused, always.

**Custom transports need the keyboard.** If you replace the native controls,
you inherit the accessibility contract: Space to play and pause, arrows to
seek, a labelled slider with a real `aria-valuetext`, and a caption toggle
with `aria-pressed`. Recipe 12 does this, and the honest note is that the
native controls do it better with less code, so replace them only when you
have a reason.

## How do I go fullscreen for media?

@cap media.fullscreen

Through `ui/request-display-mode`, not `Element.requestFullscreen()`.

The obvious API is the wrong one here. `requestFullscreen` needs the
`fullscreen` permission policy, and the extension's permission set is exactly
`camera`, `microphone`, `geolocation` and `clipboardWrite`. A host has no
defined way to grant it.

The supported route is `ui/request-display-mode` with `"fullscreen"`, which is
the same mechanism Chapter 6 describes. The host takes over its own window and
tells you the resulting mode. That is better in an embedded context: the host
knows what "fullscreen" means in its own chrome, and your view stays a view.

**Application behaviour.** Declare `fullscreen` in
`appCapabilities.availableDisplayModes`, check the host's list before asking,
and re-layout on the mode you actually get. A player at 200 pixels tall and
one at 800 need different control sizes, and the host tells you which you are
in through `ui/notifications/host-context-changed`.

## How do I show progress?

@cap op.progress

Core MCP defines `notifications/progress`, carrying a `progressToken`, a
`progress` number, an optional `total`, and an optional `message`. The token
ties it to the request it is about.

**The catch.** The extension's list of messages a view may receive does not
name `notifications/progress`. In practice hosts that proxy `tools/call` can
forward it, and the demonstration's fixture host does, but you cannot rely on
it. Treat progress as an enhancement, not as the basis of your interface.

**Application behaviour.** Determinate when you have a `total`, indeterminate
when you do not, and a phase name in both cases. "Building the index" is worth
more than a percentage, because it tells the user whether the thing that is
slow is the thing they expected to be slow. The demonstration shows four named
phases moving a bar, and the phase text is what makes the wait legible.

**Accessibility.** `role="progressbar"` with `aria-valuenow`, or a live region
that announces phase changes only. Not both, and not every tick. Chapter 13
has the reasoning.

## How do I cancel?

@cap op.cancel

Core MCP again: `notifications/cancelled` with the `requestId` of the request
you are abandoning and an optional reason. The SDK sends it when you abort the
`AbortSignal` you passed to a request.

**The part people get wrong is the interface, not the message.** Cancelling is
easy. Returning the view to a state that matches reality is not.

If a tool call was cancelled after three of five steps, the correct interface
does not show a progress bar at zero and does not show one at sixty percent
either. It says the operation stopped after three steps, and it says whether
those three steps changed anything.

<!-- listing: extracted from `apps/recipes/r11-agent-control/index.html` -->
```js
function cancel(task) {
  task.controller?.abort();
  task.state = "cancelled";
  task.steps.push("cancelled by the user");
  task.error = `Stopped after ${task.done} of ${task.total} steps. `
    + "Completed steps were not rolled back.";
  draw();
  bridge.notify("notifications/cancelled",
    { requestId: task.requestId, reason: "The user cancelled" });
}
```

**The other direction.** The host can cancel you, through
`ui/notifications/tool-cancelled` with a reason. That happens when the user
asks the agent something else, when a classifier intervenes, or when sampling
fails. Your view must handle it, and the right handling is almost always to
keep the last good state and explain, rather than to blank the view.

@cap op.pause

Extended, yours to build, and rarer than it looks. Most long operations cannot
be paused, only cancelled and restarted. Offer pause only when the underlying
work genuinely supports resumption, because a pause button that quietly means
cancel is worse than no pause button.

## How do I offer a retry?

@cap op.retry

The measure of a retry is whether the user has to rebuild the interaction.

A retry button next to the failure, which repeats the same call with the same
arguments and the same form still filled in, costs nothing and saves the
user's work. A failure that clears the form and returns the user to the start
is the same failure plus a punishment.

**Application behaviour.** Keep the arguments. Keep the last good data on
screen. Make the retry idempotent, or make it obvious that it is not. For
automatic retries, back off exponentially and cap it, and stop after a small
number rather than hammering a service that has told you it is unwell.

## How do I report a failure?

@cap op.error

A tool result can fail in two different ways, and the difference is worth
knowing. A JSON-RPC error means the call did not happen: unknown tool, bad
arguments, host refused. A result with `isError: true` means the tool ran and
failed, and its `content` is a message intended to be read.

**A structured error carries three facts.** What failed, whether retrying
could help, and what the recovery action is. The fixture in the demonstration
returns this:

<!-- listing: extracted from `apps/labs/lab-media/demo.js` -->
```js
return { isError: true, content: [{ type: "text",
  text: "The index volume is full, so nothing was written. "
      + "Free space and retry." }] };
```

Three facts in nineteen words: what happened, what the consequence was
(nothing was written, so no partial state to worry about), and what to do.
Compare it with "Error: operation failed", which has none of them and is what
most tools return.

**Show it where the action was.** An error about an export belongs next to the
export button, not in a toast that vanishes and not in a banner at the top of
a view the user has scrolled past.

**Keep the last good state.** Recipe 1's table keeps its rows when a reload
fails and says the data is from the previous successful call. An empty table
with an error above it has thrown away information the user still needed.

## The four states of a long operation

Every operation in this chapter moves through the same small state machine,
and naming it is what stops each application inventing a different one.

**Idle.** No work in flight. The control that starts it is enabled, and
whatever the last run produced is still on screen.

**Running.** Determinate or indeterminate progress, a phase name, and a cancel
control that is enabled. The control that started it is disabled or idempotent.

**Settled.** Done, failed, or cancelled. All three are terminal, all three
leave something on screen, and the difference between them is what the
interface says rather than what it shows. Done keeps the new result. Failed
keeps the previous one and explains. Cancelled keeps the previous one and says
how far the work got.

**Retrying.** A distinct state, because it is not idle: the arguments are still
there, the failure is still visible, and the user is deciding.

Recipe 11 renders all four with a chip whose text is the state name, which is
unglamorous and turns out to be the most legible thing in the interface.

## Conformance checks

1. `notifications/progress` from a server reaches the view, or the view
   degrades to indeterminate progress.
2. `notifications/cancelled` from the view carries the id of the request being
   abandoned.
3. `ui/notifications/tool-cancelled` from the host leaves the last good state
   on screen.
4. A tool result with `isError: true` is rendered as a readable message rather
   than as a thrown exception.
5. A retry re-sends the same arguments without the user re-entering them.
6. `ui/request-display-mode` with `fullscreen` is the route a media view takes,
   and `requestFullscreen` is not called.
7. Media never autoplays.

## What to remember

Four obligations while the user waits. Progress says how far.
`notifications/cancelled` says where it stopped. `isError` says what happened
and what to do. Retry re-sends the same arguments.

Do all four and the application feels reliable when the server is not. Do none
and it feels broken when everything worked.
