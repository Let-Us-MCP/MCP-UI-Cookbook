Two shapes, repeated. Parts II and III are capability entries. Part V is
recipes.

Both templates are stated here so you can hold the rest of the book to them,
and notice when it falls short.

## What is in a capability entry?

Each entry answers eleven questions in the same order.

**Capability.** Identifier, level, tag, and ground. Generated from the
registry, so the prose cannot contradict it.

**Motivation.** Why an application needs this at all. If the honest answer is
"it does not, but people expect it", the entry says that.

**User experience.** What the person sees and does. Written from the outside.

**Application behaviour.** What your code does, including the part it does
before anybody clicks anything.

**Host behaviour.** What belongs to the host. This is the half most entries in
other documents leave out, and it is the half that determines whether your
application works in a host you have never tested against.

**Lifecycle.** Initialisation, execution, cancellation, completion,
destruction. Most capabilities are boring here. The ones that are not are the
ones that break.

**Security.** Which trust boundary this crosses and what the host is entitled
to do about it.

**Accessibility.** Keyboard, focus, name and role, scaling, motion. Not a
section at the end of the book. A section in every entry, because that is the
only way it survives contact with a deadline.

**Failure modes.** Unsupported, denied, cancelled, timeout, failed. Five of
them, always, in that order.

**Minimal example.** The smallest thing that demonstrates it, running on the
page.

**Conformance tests.** The automated checks that decide whether an
implementation has it.

Not every entry in this book spends a paragraph on all eleven. A capability
like `picker.color` has nothing interesting to say about lifecycle. The
template is a checklist for the author, not a quota for the reader, and where
a section is silent it is because the honest content was one sentence long.

## The five failure modes

This is the part worth internalising, because it is where the difference
between a demonstration and an application lives.

**Unsupported.** `hostCapabilities.downloadFile` was absent at
`ui/initialize`. Do not render the export button at all. Not disabled with a
tooltip, not showing an error when pressed: absent.

**Denied.** `ui/open-link` came back with a JSON-RPC error. Show the host's
message next to the control and leave the control enabled: "The host declined
to open that link" says what happened and what to try. "Error" says
neither.

**Cancelled.** Someone sent `notifications/cancelled`, or the host sent
`ui/notifications/tool-cancelled`. Report where it stopped. Recipe 11 writes
"Stopped after 3 of 5 steps. Completed steps were not rolled back." Resetting
the bar to zero claims nothing happened, and three steps happened.

**Timeout.** No answer at all. Give every request a deadline, 8 seconds is a
reasonable default, and treat expiry as a failure with a retry. Skip this and
you ship a spinner that runs until the user reloads the host.

**Failed.** The tool ran and returned `isError: true`. Its `content` carries
three facts: what failed, what state that leaves, and what to do. "The index
volume is full, so nothing was written. Free space and retry." is 14 words
carrying all three.

![The five failure modes, and the moment each one is discoverable](figures/diag-failures.png)

The value of naming all five is that they are discoverable at different times.
Unsupported is known before render. Denied and failed are known at the attempt.
Cancelled comes from the user or the host at any moment. Timeout is known only
by deciding it. An application that handles one of them and calls it error
handling has handled the least common one.

## What is in a recipe entry?

Part V uses a different template, because a recipe is an argument rather than
a reference.

**Goal.** The conventional application being reproduced, in one line.

**Capability delta.** Which primitives this recipe exercises that no earlier
recipe does. This is the load-bearing field. A recipe with an empty delta gets
merged or deleted, because it is not teaching anything and not testing
anything, and thirteen recipes that each cover the same twelve capabilities
would prove nothing about the model's sufficiency.

**Surface.** What it looks like and how much room it needs.

**Components.** Which Part IV components it composes.

**Atomic capabilities.** The full list, generated from the registry.

**Local interactions and agentic interactions.** The split from Chapter 3,
declared as a table before any code.

**Host dependencies.** What it needs by conformance level, so a reader can
tell whether it will run in their host.

**Failure cases.** What happens when each dependency is absent. The recipes in
this book are all built to run at Level 1 with reduced function, and the entry
says what "reduced" means.

**Accessibility.** The keyboard-only path through the whole application.

**Conformance checks.** The observable behaviours a host has to produce, in
the form the harness asserts them.

## Why every listing has a tag

One more convention, visible on every code block in the book. A tag above each
listing says where it came from:

*Extracted* means the lines are read out of a file the tests run. The file
name is given, and the demonstration on the same page is running it.

*Captured* means it is real output from a real run, quoted verbatim, including
the parts that are inconvenient.

*Illustrative* means it was written for the page and nothing executes it.
Message shapes quoted from the specification are illustrative. So are the
sketches of code you might write.

The reason for the convention is that books about protocols accumulate code
that used to work. A reader who cannot tell which listings are load-bearing
has to treat all of them as suspect. Chapter 29 describes the check that keeps
the tags honest.

## A worked failure table

Here is the same capability, `file.export`, written out as the template asks,
so that the shape is concrete before Part II starts using it eighty-five times.

| Mode | When you learn | What the interface does |
|---|---|---|
| Unsupported | Initialisation | No export control is rendered. Copy is offered instead. |
| Denied | The click | "The host declined to save that file." The control stays. |
| Cancelled | The click | Nothing. The user changed their mind and the interface is unchanged. |
| Timeout | Your deadline | "No answer from the host." The control returns to idle. |
| Failed | The click | The host's message, verbatim, next to the button. |

Five rows, and notice that three of them leave the interface in a different
state and two leave it identical. Cancelled and unsupported both produce no
error and no message, for opposite reasons: one because nothing was attempted,
the other because nothing was ever offered.

The row people skip is timeout, and skipping it is what produces the single
most common defect in embedded applications: a spinner with no end, in a frame
whose host stopped listening, that only a reload will clear.

## Where the templates came from

Both are adapted from how specification-anchored test suites describe web
platform features, and the borrowing is deliberate. A capability entry that
names its host behaviour and its failure modes can be turned into assertions
mechanically, which is what Appendix C does. An entry that describes only the
happy path cannot, which is why so much interface documentation is unfalsifiable
and therefore ages without anybody noticing.

## What to remember

If you take one thing from Part I into the rest of the book, take the failure
section. Every capability entry from here on has one, and in almost every case
it is longer than the section describing the happy path. That ratio is the
point. The happy path is a few lines of code you would have written anyway.
The rest is what makes an application survive a host that says no.

## Reading an entry critically

Two habits worth having, because not every entry in Parts II and III deserves
equal trust.

**Check the ground badge against your own experience.** A *platform* entry is
a claim about browsers, and browsers differ. A *wire* entry is a claim about a
specification that is still moving, and eight of them carry a draft badge. A
*gap* entry is the strongest claim in the book, because it asserts that
something does not exist, and absence is the hardest thing to verify.

**Ask what the failure section leaves out.** The template asks for five modes
and most entries have something to say about three. Where an entry is silent
on cancelled or timeout, it is usually because the capability is synchronous
and local, and that reasoning should be visible rather than assumed. Where it
is silent and the capability is neither, the entry is thin and you should
treat it as a starting point rather than as a specification.
