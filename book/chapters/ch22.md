Part IV is the middle layer. Capabilities are too small to build with;
applications are too large to reuse. Components are the pieces with names a
designer already uses, and every entry here answers three questions: which
capabilities it composes, which Authoring Practices Guide pattern governs its
keyboard behaviour, and what changes because it is inside somebody else's
window.

That third question is the only reason these chapters exist. There are
excellent references for building a combobox. There are none for building one
that is four hundred pixels wide, inside an opaque origin, next to a model
that may fill it in.

The component library the recipes are built from is one CSS file and one
helper file, `apps/lib/view.css` and `apps/lib/view.js`, about five hundred
lines together. Thirteen applications share it, which is why they look like
they came from the same place.

## Overlays

| Component | Composes | APG pattern |
|---|---|---|
| Alert | `dialog.alert`, `surface.focus` | Alert Dialog |
| Confirmation | `dialog.confirm`, `surface.focus`, `input.keyboard` | Alert Dialog |
| Modal | `surface.displayMode`, `surface.focus`, `input.keyboard` | Dialog (Modal) |
| Sheet, drawer | `surface.focus`, `input.pointer`, `env.reducedMotion` | Dialog (Modal) |
| Popover | `surface.focus`, `input.keyboard` | Disclosure |
| Tooltip | `input.pointer`, `env.inputMode` | Tooltip |
| Context menu | `input.contextmenu`, `input.longpress`, `surface.focus` | Menu |

**Use `<dialog>` and `showModal()`.** It gives you the focus trap, the inert
background, the Escape handling and the `aria-modal` semantics. A hand-rolled
overlay gives you none of them, and in a frame a keyboard user cannot escape
from, the difference is not cosmetic.

**Everything is clipped by the frame.** A popover that would overflow the
viewport in a page just overflows; here it is cut off by the iframe's edge and
there is no way to render outside it. Position with the frame's bounds, not
the screen's, and prefer flipping to a different side over letting the content
extend past the boundary. A dropdown that opens downward at the bottom of the
frame is a dropdown nobody can read.

**Tooltips need a second route.** They are hover-only by construction, and
`hostContext.deviceCapabilities.hover` tells you when hover does not exist.
On a touch device, move the content into the label, a popover triggered by
tap, or a description that is always visible.

**Context menus need a keyboard route.** Shift+F10, a visible button, or both.
Chapter 9 has the details.

## Controls

| Component | Composes | APG pattern |
|---|---|---|
| Button | `input.pointer`, `input.keyboard` | Button |
| Checkbox, radio | `input.keyboard`, `input.selection` | Checkbox, Radio Group |
| Toggle | `input.keyboard` | Switch |
| Slider | `input.pointer`, `input.keyboard` | Slider |
| Stepper | `input.keyboard` | Spinbutton |
| Segmented control | `input.keyboard`, `input.selection` | Radio Group |
| Filter chip | `input.selection`, `input.keyboard` | Checkbox |
| Dropdown | `input.keyboard`, `surface.focus` | Listbox |
| Combobox | `input.keyboard`, `input.selection`, `surface.focus` | Combobox |

**Start from the native element.** `<button>`, `<input type="checkbox">`,
`<input type="range">`, `<select>` all work, all come with keyboard and screen
reader support, and all are one CSS file away from matching your design. The
recipes use native elements everywhere except the combobox, which does not
exist natively.

**Target size is a host-dependent decision.** Forty-four pixels on touch,
smaller with a pointer, and `deviceCapabilities` is where you find out which.
A toolbar designed at 28 pixels is unusable on a phone, and you cannot detect
a phone by width when the same width is a side panel on a desktop.

**Disabled controls carry an obligation.** A disabled button is a promise that
something could enable it, and the user is entitled to know what. If the
reason is a missing host capability, do not disable, omit: Chapter 1's
argument. If the reason is state, say so.

**The combobox is the one worth buying rather than building.** It is the most
complex pattern in the APG, it involves a listbox that must be positioned
within the frame, and getting the `aria-activedescendant` and expanded state
right takes longer than any other component here. If a plain `<select>` or a
text input with a datalist will do, take it.

## Text input

| Component | Composes | APG pattern |
|---|---|---|
| Text field | `input.keyboard`, `surface.focus` | (native) |
| Search field | `input.keyboard`, `input.shortcut` | (native) |
| Multiline editor | `input.keyboard`, `history.transaction` | (native) |
| Autocomplete | `input.keyboard`, `input.selection` | Combobox |
| Token input | `input.keyboard`, `input.selection`, `clipboard.write` | Combobox |
| Rich text editor | `history.transaction`, `input.selection`, `ui.prefill` | (none) |
| Code editor | `input.keyboard`, `clipboard.write`, `input.selection` | (none) |

**Validate on blur and on submit, never on keystroke.** Telling somebody their
email is invalid while they are typing the at sign is the fastest way to make
a form feel hostile. Recipe 13 tracks a `touched` flag per field and only
shows an error after the field has been left once.

**Undo grouping is per pause, not per keystroke.** Chapter 15. In a rich text
editor this is the difference between an undo stack somebody can use and one
that steps back a character at a time.

**Search fields want a shortcut and cannot safely have one.** Cmd/Ctrl+F is
the convention and the host may own it. Bind it, expect to lose it sometimes,
and always provide the visible field.

**Rich text is where the agent shows up.** A text field can be prefilled and
the user sees the value change. A document cannot: the agent's rewrite has to
appear as a proposal, with the original still visible, and accepting it has to
be one undo transaction. Recipe 4 is the worked example, and the proposal card
is a component in its own right that Chapter 24 lists.

**Code editors are a decision about weight.** A real editor is a large
dependency inside a frame with a restrictive CSP and no CDN unless the server
declares one. A `<pre>` with syntax highlighting done server-side covers
reading, which is most of what a review interface does. Recipe 8 renders a
diff with no editor at all.

## The embedded rule that applies to all of them

Every component in this chapter is smaller than the version you have built
before, because the frame is smaller. A toolbar with nine buttons becomes a
toolbar with four and an overflow menu. A form with three columns becomes one
column. A modal that would be 600 pixels wide has to work at 380.

The useful discipline is to design at the narrowest width you will accept, and
to let `surface.resize` report the height rather than trying to fit a fixed
one. Everything in this book is built at 380 pixels first, and the recipes look
the same at 900 because the layout only ever had one column to lose.
