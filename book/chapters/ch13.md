Accessibility is a section in every entry of this book rather than a chapter
at the end, because that is the only arrangement that survives a deadline.
This chapter carries the four capabilities that do not belong to any other
group, and the specifically embedded problems that the rest of the entries
refer back to.

## What makes a frame harder than a page

Four things, and none of them are your fault.

**Your view is a document inside a document.** A screen reader user reaches it
by moving into the frame, and inside it your headings start again at whatever
level you chose. Use a sensible internal hierarchy and give the frame a
meaningful title, because the title is what the host can expose as the frame's
accessible name.

**You cannot see the host's landmarks.** You do not know whether the
conversation is a `main`, whether there is already an `h1`, or what else has
`role="status"`. Assume your announcements are competing with the host's.

**Focus cannot cross the boundary.** Chapter 7 is the whole story. The
practical consequence is that a keyboard user who enters your view must be
able to leave it by ordinary tabbing, which means no traps outside modals and
no infinite roving lists.

**The user's preferences reach you by a different route than the theme.** The
host sends colours. The operating system sends motion, contrast and text size,
through media queries. Those two can disagree, and the demonstration above has
a control that makes them disagree on purpose.

## Reduced motion

@cap env.reducedMotion

`prefers-reduced-motion: reduce` works inside the sandbox and reflects the
operating system.

**Application behaviour.** The blunt instrument is a stylesheet rule that
collapses every animation and transition, and it is the right default:

<!-- listing: extracted from `apps/lib/view.css` -->
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .001ms !important;
    transition-duration: .001ms !important;
  }
}
```

The finer instrument is to check the query in JavaScript where motion is
functional rather than decorative. A dashboard that repaints a sparkline every
1.4 seconds is not decorating; it is moving, continuously, in somebody's
peripheral vision. Recipe 2 slows its polling to four seconds under a reduced
motion preference, which is a different response from removing an animation
and a more honest one.

**What to keep.** Reduced motion does not mean no feedback. Replace slides
with crossfades, replace crossfades with instant changes, and keep the state
change legible. A toast that appears instantly is fine; a toast that never
appears is a regression.

## Contrast

@cap env.contrast

`prefers-contrast: more` and forced-colors mode are both real and both arrive
without the host's involvement.

**The embedded-specific trap.** In forced colours, the operating system
replaces the palette. Anything you drew with a background image, a gradient,
or a `box-shadow` to indicate state loses that indication entirely, because
those properties are not overridden and the colours around them are. State has
to be carried by something that survives: a border, an outline, text, or an
icon.

The same applies to your own custom properties. A view that indicates
selection only by `background: var(--color-background-info)` shows no
selection at all under forced colours. Recipe 1 sets both a background and an
`aria-selected` attribute, and the attribute is what makes it survive.

## Text scale

@cap env.textScale

Users enlarge text. In a page that means everything reflows; in a four hundred
pixel frame it means your two-column layout has three words per line.

**Application behaviour.** Size in relative units so the root scales
everything. Never set a fixed pixel height on anything that contains text.
Let the frame grow: `surface.resize` exists for precisely this, and a view
that reports its true height when text doubles is a view that stays usable.

WCAG 2.2 asks for usability at 200% zoom and reflow at 320 CSS pixels of
width. Both are testable with the browser's own zoom, and a four hundred pixel
card at 200% is roughly a phone, so testing one gets you most of the other.

## Announcements

@cap a11y.announce

This is the capability with no equivalent anywhere else in the book: telling
assistive technology that something changed, when the change was not caused by
the user moving focus.

Everything in an agentic application is that kind of change. A tool result
arrives. The agent highlights a row. A streaming log gains forty lines. A task
fails. A sighted user notices; nobody else does, unless you say so.

**Application behaviour.** One polite live region, created once, updated with
text. Politeness matters: `aria-live="assertive"` interrupts whatever is being
read, and in an application where results arrive continuously that is
unusable.

<!-- listing: extracted from `apps/lib/view.js` -->
```js
function announce(text) {
  let region = $("#live-region");
  if (!region) {
    region = h("div", { id: "live-region", class: "sr-only",
                        role: "status", "aria-live": "polite" });
    document.body.append(region);
  }
  region.textContent = "";
  setTimeout(() => { region.textContent = text; }, 30);
}
```

The clear-then-set with a small delay is not superstition. Screen readers
announce *changes* to a live region, and setting the same string twice is not
a change, so the second identical event is silent without it.

**Announce the outcome, not the event.** "Six of forty selected" rather than
one announcement per row. "Import failed. Row 812 has a malformed date."
rather than "error". The demonstration announces at phase boundaries only,
which is what a sighted user actually perceives from a progress bar.

**What not to announce.** Hover. Scroll position. Anything the user did
deliberately and can already feel. A live region that narrates the mouse is
worse than no live region.

## The checklist that fits on a card

Every recipe in Part V is built against this list, and Appendix C turns it
into assertions.

Every interactive element is reachable by Tab and operable by Enter or Space.
Every composite widget is one tab stop with arrow key navigation inside it.
Every control has a name, and the name is what a person would call it. State
changes that were not caused by focus are announced. Focus is visible, and the
ring is not clipped by an `overflow: hidden` ancestor. Nothing depends on
colour alone. Nothing depends on hover alone. Every spatial gesture has a
button or a key equivalent. Text stays usable at 200%. Motion respects the
preference.

Ten lines, and running `axe-core` against your view will confirm perhaps half
of them. The other half need a keyboard and five minutes, which is a cheaper
test than most of the automated ones in Part VI and catches more.
