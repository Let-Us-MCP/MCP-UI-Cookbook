@recipe r08

The recipe that makes the strongest case for structured escalation. A reviewer
looking at a diff has a precise question about a precise range, and the
difference between sending that range and sending a description of it is the
difference between a useful answer and a plausible one.

@demo r08-diff-reviewer

## What stays local, what crosses

| Normally local | Worth crossing |
|---|---|
| Select a line, extend a range | "Explain this change" |
| Add a comment | "Is this backoff correct?" |
| Scroll, navigate hunks | "What else depends on this constant?" |
| Copy the hunk | "Open the file on the server" |

## Selection as the unit

Click sets the anchor, shift-click extends, arrows move and shift-arrows
extend. The selected range is published as structured content, with line
numbers and kinds:

<!-- listing: illustrative -->
```json
{ "file": "src/transport/retry.ts",
  "lines": [ { "no": 44, "kind": "del", "text": "  return base * 2 ** attempt + jitter;" },
             { "no": 44, "kind": "add", "text": "  const capped = Math.min(base * 2 ** attempt, 30_000);" } ] }
```

The model receives line numbers, the file path, and whether each line was
added or removed. Compare that with a screenshot, or with "the user is looking
at the retry file", and the difference in what can be answered is large.

## Escalation carries the range

"Explain this change" sends the selected lines with their diff markers as a
`ui/message`. Not the whole file, not the whole hunk, and not a summary: the
lines the reviewer pointed at.

## Comments are local

A comment is attached to a line and rendered under it, and it never leaves the
view unless the reviewer escalates. That is the right default: a review comment
is a note to a colleague, not a prompt.

## Try this

**Click line 42, then shift-click line 45.** The published context is those
four lines with their numbers and their kinds, which is what makes "explain
this change" answerable precisely.

**Press "Explain this change".** The message carries the selected lines with
their diff markers, not a description of them.

**Press "Refuse to open links", then "Open on the server".** The refusal is
reported rather than swallowed, which is the correct handling for a capability
that was present at initialisation and declined at use.

## What it needs from the host

| Level | Needs | Without it |
|---|---|---|
| 1 | Render, resize, theme | Nothing works |
| 1 | `link.open` | The source button is omitted |
| 3 | `surface.displayMode` | Reviewing happens at inline width |
| 4 | `agent.escalate` | The explain button is omitted; copy remains |
| 4 | `agent.contextUpdate` | The model does not learn the selection |
| 4 | `tool.invoke` | No diff to review |

## What happens when things go wrong

**The host refuses to open links.** Press "Refuse to open links". The button
reports the refusal rather than failing silently, which is the right response
for a capability that was present at initialisation and declined at use.

**A very wide line.** The diff pane scrolls horizontally rather than wrapping,
because a wrapped diff line breaks the alignment between the number gutter and
the content. In a four hundred pixel frame this means horizontal scrolling,
which is the least bad option.

## Keyboard and screen reader

The diff is a labelled group with keyboard navigation by arrow keys, and shift
extends. Each line's kind is carried by a `+` or `-` character in the text
rather than by colour alone, so it survives forced colours. Comments are
announced when added. The selection count and range are available to a screen
reader through the live region.

## Conformance checks

1. `load_diff` returns eight lines and the stat chip reads `+3 -2`.
2. Clicking a line sends exactly one `ui/update-model-context`.
3. Shift-clicking extends the published range rather than replacing it.
4. Explain sends `ui/message` containing the selected lines with markers.
5. With `openLinks` withdrawn, `ui/open-link` is not sent and the refusal is
   reported.
