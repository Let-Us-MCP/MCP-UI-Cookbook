@recipe r07

The recipe where the agent is a first-class editor. Everything the mouse can
do to this graph, a tool can do, and everything a tool does is one undoable
transaction. The topology explorer some applications need is this same surface
in read-only mode.

@demo r07-workflow-builder

## What stays local, what crosses

| Normally local | Worth crossing |
|---|---|
| Drag nodes, pan, zoom | "Build me a triage workflow" |
| Connect two selected steps | "What is wrong with this graph?" |
| Add and delete steps | "Add error handling to this" |
| Undo | |

The second column is the interesting one. All three of those are the agent
calling the same operations the mouse calls, which is why they are safe.

## The agent's vocabulary

Four tools: `add_step`, `connect_steps`, `highlight_step`, and `get_workflow`.
Three of them mutate and are annotated `readOnlyHint: false`; the fourth
reads.

<!-- listing: illustrative -->
```js
bridge.registerTool({
  name: "connect_steps",
  description: "Connect two steps by name",
  inputSchema: { type: "object", properties: { from: { type: "string" },
    to: { type: "string" } }, required: ["from", "to"] },
  annotations: { readOnlyHint: false },
}, async ({ from, to }) => {
  const a = graph.nodes.find((n) => n.name === from);
  const b = graph.nodes.find((n) => n.name === to);
  if (!a || !b) {
    return { isError: true, content: [{ type: "text",
      text: `No step called ${a ? to : from}.` }] };
  }
  connect(a.id, b.id);
  return { content: [{ type: "text", text: `Connected ${from} to ${to}.` }] };
});
```

Two design decisions in that snippet. The tool takes names, because names are
what appear in the conversation. And it fails with a message naming the step
that does not exist, so the agent can correct itself. Press "Agent: connect to
a step that is not there" in the demonstration to see the failure path.

## Validation as a continuous state

The graph is validated on every change and the result is a chip: valid, or a
count of problems. Nodes with problems get a red border. The initial graph
loads with a disconnected Notify node, so the recipe starts invalid on
purpose.

`get_workflow` returns the problems as structured data, which is what makes
"what is wrong with this graph" answerable without the model reading pixels.

## Undo covers both parties

Every mutation goes through the same `apply()`, whether it came from a pointer
or from a tool. The agent adds a step; one Cmd+Z removes it. Chapter 21 argues
this is what makes agent editing acceptable, and this recipe is the clearest
case: a graph an agent can restructure and a human cannot un-restructure is a
graph nobody will let an agent near.

## The minimap

Eleven lines of canvas drawing, showing node positions and the current
viewport rectangle. It is the cheapest orientation aid available and the first
thing users miss on a pannable surface.

## Try this

**Press "Agent: what is wrong with this?".** The reply is a count of structural
problems, computed from the graph.

**Press "Agent: connect Assign owner to Notify".** An edge appears, the chip
goes from "2 problem(s)" to "valid", and one Cmd/Ctrl+Z removes it.

**Press "Agent: connect to a step that is not there".** The tool fails with the
missing name in the message, so the agent can correct itself.

**Drag a node, then press Undo.** One transaction for the whole drag, not sixty.

## What it needs from the host

| Level | Needs | Without it |
|---|---|---|
| 1 | Render, resize, theme | Nothing works |
| 3 | `input.zoompan` | Platform; always present |
| 4 | `tool.invoke` | No graph to load |
| 4 | `app.tools` | The agent cannot edit; the mouse still can |

## What happens when things go wrong

**The agent names a step that does not exist.** The tool returns
`isError: true` with the missing name, and the graph is unchanged.

**A node is dragged outside the world.** The world is 1200 by 800 and the
transform does not clamp, so a node can be dragged out of view. The minimap is
how the user finds it again, which is a mitigation.

## Keyboard and screen reader

Each node is a `role="button"` with `aria-pressed` carrying its selection
state and an accessible name of "name, kind". Enter selects, Shift+Enter adds
to the selection, and the arrow keys move the focused node by ten pixels or by
one with Shift. Connecting is then the ordinary Connect button, which enables
itself at two selected nodes.

A focusable `div` is silent about all of this by default. `tabindex` makes it
reachable and nothing more: Enter does not fire `click` the way it does on a
button, so a canvas whose nodes are divs with `onclick` is a canvas that
cannot be operated at all without a pointer, and it looks fine in every
screenshot. That was this recipe's defect until the render harness gained key
dispatch and could be pointed at it.

Arrow-key moves coalesce into one transaction per run, on the reasoning
Chapter 16 gives for typing: undo that steps back ten pixels at a time is undo
nobody uses. The tool interface remains, and it is still the better route for
an agent, because naming a step beats describing where it sits.

## Conformance checks

1. `load_workflow` returns four nodes and two edges.
2. The validation chip reports two problems on load.
3. `connect_steps` with valid names adds an edge and clears one problem.
4. `connect_steps` with an invalid name returns `isError: true`.
5. Undo removes an agent-created edge.
6. `get_workflow` returns the same problem count the chip shows.
7. Dragging a node produces exactly one undo transaction.
