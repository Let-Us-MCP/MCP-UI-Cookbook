@recipe r10

The recipe built on a capability that does not exist. There is no
`approval.request` message, so this recipe is an argument about where the
enforcement has to live and what the interface owes the person making the
decision.

@demo r10-approval-center

## What stays local, what crosses

| Normally local | Worth crossing |
|---|---|
| Read the queue, expand provenance | "What is this refund for?" |
| Approve or deny | "Has this customer been refunded before?" |
| Review the audit trail | "Explain the retention rule behind this" |

Approving is local. A person presses a button; the `approve` tool exists only
to refuse the agent.

## Provenance, or it is not an approval

Every card carries five fields: who asked, on whose behalf, which tool, which
arguments, and what has been approved before.

Chapter 22 argues that a card without them is a dialog with a lever attached,
and that people learn to pull levers. The version with them lets a reviewer
notice that this is the first refund ever approved for this customer, which is
the fact that changes the decision.

## Where the gate actually is

The view cannot enforce anything. It is untrusted HTML in a sandbox and its
Approve button is an ordinary button. The enforceable arrangement is:

The server queues. A refund tool returns a queue id and does
nothing else. A second tool performs the refund, requires the queue id, and is
`visibility: ["app"]` so the model cannot call it. The view calls it after a
human presses Approve.

That is a convention, and its weakness is that a
compromised view could call the second tool without a human. Closing that
needs `ui/request-approval`, which is in Appendix B.

## The tool that refuses

<!-- listing: illustrative -->
```js
bridge.registerTool({
  name: "approve",
  description: "Approve a queued action",
  inputSchema: { type: "object", properties: { title: { type: "string" } } },
  annotations: { readOnlyHint: false },
}, async () => ({
  isError: true,
  content: [{ type: "text", text:
    "Approval requires a person. This view does not accept approvals over "
    + "the tool interface." }],
}));
```

Registering a tool in order to refuse it looks strange until you consider the
alternative: an agent that finds no approval tool tries something else, and
what it tries may not have a gate. Press "Agent tries to approve it itself" in
the demonstration.

## What crosses the boundary

Decisions, and nothing else. Not which cards were expanded, not how long the
person took, not the order they read them in. The audit trail is local; the
context update carries the outcomes.

## Try this

**Read the provenance on the refund card before deciding.** Five fields, and
the one that changes the decision is "prior approvals: none for this customer".

**Press "Agent queues a deletion", then "Agent tries to approve it itself".**
The tool refuses and says why. Registering a tool in order to decline it is the
point of the recipe.

**Approve the deletion, then press "Show the audit trail".** The decision is
recorded locally and published to the model; how long you took and which cards
you expanded are not.

## What it needs from the host

| Level | Needs | Without it |
|---|---|---|
| 1 | Render, resize, theme | Nothing works |
| 2 | `dialog.confirm` | Yours to build; always available |
| 4 | `approval.request` | Gap; the queue-and-perform convention is the fallback |
| 4 | `elicit.request` | Gap; "Ask in the conversation" is the fallback |
| 4 | `agent.contextUpdate` | The model does not learn the decisions |
| 4 | `app.tools` | The agent cannot queue anything |

## What happens when things go wrong

**High-risk approval.** Requires a second confirmation naming the consequence,
because the card can be read quickly and the money cannot be recalled.

**A question mid-decision.** There is no view-side elicitation, so "Ask in the
conversation" sends `ui/message` and the reviewer waits for a turn. It works
and it takes them out of the flow, which is what the gap costs.

## Keyboard and screen reader

Each card is a region with a heading, and the provenance is a description list
so a screen reader reads label and value in pairs. New arrivals are announced.
The risk level is carried by text as well as by border colour. Confirmations
are `<dialog>` with focus trapped and returned.

## Conformance checks

1. `pending_approvals` returns two requests and both render with provenance.
2. Approving a high-risk request opens a confirmation.
3. Cancelling the confirmation leaves the request in the queue.
4. Approving sends exactly one `ui/update-model-context` carrying decisions.
5. `approve` called as a tool returns `isError: true` and changes nothing.
6. `queue_approval` adds a card and announces it.
