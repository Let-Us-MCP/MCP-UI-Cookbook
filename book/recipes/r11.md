@recipe r11

The recipe about watching work happen. Its delta is the whole of Chapter 17
under load: several operations in flight, each with its own progress, its own
cancellation, and its own failure.

@demo r11-agent-control

## What stays local, what crosses

| Normally local | Worth crossing |
|---|---|
| Cancel, retry, expand a task | "Why did shard 41 fail?" |
| Read progress and steps | "Run the reindex for every shard" |
| Cancel everything | "Should I retry this or escalate?" |

## A task that exists before it exists

The row appears while the model is still writing the arguments.

<!-- listing: illustrative -->
```js
bridge.on("toolinputpartial", ({ arguments: args }) => {
  const task = tasks.get("pending") ?? { id: "pending", name: "…", steps: [],
    percent: 0, done: 0, total: 5, state: "queued" };
  task.name = args?.name ?? task.name;
  task.steps = [`arguments arriving: ${JSON.stringify(args ?? {})}`];
  tasks.set("pending", task);
  draw();
});
```

Press "Agent streams a task in" and watch `"Reindex sh"` become
`"Reindex shard 9"` before the task starts. This is the difference between an
interface that feels immediate and one that shows a spinner for as long as the
model takes to write JSON.

The pending row is keyed separately and replaced when
`ui/notifications/tool-input` arrives, so a partial row never becomes a real
task by accident.

## Progress against the running request

`notifications/progress` carries a step count and a message, and each message
is appended to the task's step list. The bar moves; the last three step names
are visible. A phase name is worth more than a percentage, because it tells
the user whether the slow part is the part they expected to be slow.

## Cancellation that tells the truth

<!-- listing: illustrative -->
```js
task.error = `Stopped after ${task.done} of ${task.total} steps. `
  + "Completed steps were not rolled back.";
```

Resetting the bar to zero would say nothing happened, which is false. Leaving
it at sixty percent would suggest the work is still there, which is also
false. Saying where it stopped and what state that leaves is the only honest
option, and it is one sentence.

## Retry that keeps the arguments

The failed task keeps its name and its configuration, and Retry re-runs the
same call. The user does not rebuild anything. Chapter 17 argues that a
failure that clears the form is the same failure plus a punishment.

## Try this

**Press "Agent streams a task in".** The row appears while the name is still
`Reindex sh`, then fills in when `ui/notifications/tool-input` arrives.

**Start a task and cancel it halfway.** The task reports the step it reached
and says that completed steps were not rolled back, which is unglamorous and
true.

**Press "Make the next task fail", then start one.** The failure keeps its step
history, explains what state it left, and offers Retry with the same arguments.

## What it needs from the host

| Level | Needs | Without it |
|---|---|---|
| 1 | Render, resize, theme | Nothing works |
| 2 | `op.progress` | Bars are indeterminate; step names are absent |
| 3 | `notify.attention` | Gap; the banner-on-return is the fallback |
| 4 | `tool.invoke`, `tool.cancel` | Nothing to run and nothing to stop |
| 4 | `tool.partialInput` | Tasks appear only when fully specified |

## What happens when things go wrong

**A task fails midway.** Press "Make the next task fail". The task turns red,
keeps its step history, shows the server's explanation, and offers Retry. The
explanation is three facts: what failed, what state it left, what to do.

**Cancel everything.** Each running task is cancelled individually, each sends
`notifications/cancelled` with its own request id, and each reports where it
stopped.

**A failure while the view is hidden.** Raises a banner that survives until
the user returns, which is the same fallback Recipe 9 uses for the same
missing capability.

## Keyboard and screen reader

Each task is a region with a heading and a `role="progressbar"`. Completion
and failure are announced once; progress ticks are not, because a screen
reader narrating five steps a second for four tasks is unusable. The step log
is scrollable and reachable. Cancel and Retry are ordinary buttons in tab
order next to the task they belong to.

## Conformance checks

1. `ui/notifications/tool-input-partial` creates a pending row.
2. `ui/notifications/tool-input` replaces it with a running task.
3. Each `notifications/progress` advances the bar and appends a step.
4. Cancel sends `notifications/cancelled` with the right request id.
5. A cancelled task reports the step it reached.
6. A failed task offers Retry and Retry re-sends the same arguments.
