@recipe r01

The first recipe is the one most MCP applications actually are: structured
data from a tool, rendered as a table, with the interactions people expect
from a table. Everything after it adds something; this one establishes what
"working" means.

@demo r01-data-explorer

## The split

| Normally local | Worth crossing |
|---|---|
| Sort by any column | "Why is p95 high on these?" |
| Filter and search | "Investigate this anomalous value" |
| Page through results | "Verify these against the invoice system" |
| Select rows, extend with shift | "What changed in this deploy?" |
| Copy the selection | |
| Export CSV | |

Six local interactions, four crossings, and every crossing is a button the
user pressed on purpose. Nothing here consults a model about how to sort.

## Surface

One column at any width. A toolbar with a search field, an environment filter
and three actions; a scrolling table with six columns; a pager. It reports its
height and lets the host grow the frame, up to whatever maximum the host
allows.

## Components

Toolbar, search field, dropdown, table with selection, pagination, toast,
banner for the error state. All from `apps/lib/view.css`.

## How data arrives, twice

The view is rendered because `list_deployments` was called, so the rows arrive
in `ui/notifications/tool-result`. It also calls the same tool itself, on
mount and from the reload button, through `tools/call`. Both paths land in the
same render function.

That duality is worth designing for deliberately rather than discovering. The
first arrival is free and comes with the view; every later one costs a round
trip and needs a loading state. The demonstration's "Deliver the tool result"
control pushes a fresh result down the notification path so you can watch the
table update without a call.

## What the model is told

Selection, as structured data, and nothing else.

<!-- listing: illustrative -->
```json
{ "selected": [ { "id": "d5", "service": "billing", "env": "production",
                  "version": "9.2.4", "p95": 1290, "errors": 143 } ] }
```

Not the sort order, not the filter, not the page, not the hover. Press "Show
what the model was told" with nothing selected and the answer is that nothing
has been published. Select two rows and it fills in.

The server's side of the same discipline is in `summarise()`: the model gets
"8 deployments. Worst p95 is 1290ms on billing." and the eight full records go
to the view in `structuredContent`.

## Try this

**Select two rows, then press "Show what the model was told".** The payload is
the selection as structured data and nothing else. Select a third and press it
again: the payload was replaced, not appended to.

**Press "Break the server", then "Reload from the server".** The table keeps
its rows, a banner explains that the data is from the previous successful call,
and the reload button still works. Press "Fix the server" and reload again.

**Press "Switch to ja-JP / Tokyo".** Every timestamp and number re-renders. The
selection survives, because formatting is a render concern and selection is
state.

**Open the `server.js` tab and find `summarise`.** That one function is the
whole two-channel argument: the model gets its sentence, the view gets the
eight records.

## Host dependencies

| Level | Needs | Without it |
|---|---|---|
| 1 | Render, `surface.resize`, `env.theme`, `env.locale` | Nothing works |
| 2 | `clipboard.write`, `file.export` | Copy falls back to `execCommand`; export button is omitted |
| 4 | `tool.invoke` | No reload; the initial result is all there is |
| 4 | `agent.escalate` | The Ask button is omitted; the selection is still copyable |
| 4 | `agent.contextUpdate` | The model does not learn the selection |

Every row of that table is a real host. The recipe renders and remains useful
at Level 1 with none of the Level 4 capabilities, which is the test every
recipe in Part V has to pass.

## Failure cases

**The tool fails.** Press "Break the server". The table keeps the rows it had,
a banner explains that the data is from the previous successful call, and the
reload button still works. An empty table with an error above it would have
thrown away the information the user still needed.

**The host cannot save files.** The export button is not rendered. Copy is
offered instead, which puts CSV on the clipboard through whichever of the two
paths works.

**The locale changes mid-session.** Press "Switch to ja-JP / Tokyo". Numbers
and timestamps re-render; the underlying data does not change; the selection
survives.

## Accessibility

The table is a grid with `aria-selected` on each row and `tabindex="0"` for
keyboard activation. Space toggles selection, and the selected count is
announced once per change rather than once per row. Sortable headers carry
`aria-sort`. The error banner is a live region. Every column that is numeric
is right-aligned with tabular figures, which is a legibility rather than an
accessibility requirement and is the sort of thing that gets dropped first.

## Conformance checks

1. The view sends `ui/initialize` and `ui/notifications/initialized`.
2. It sends `ui/notifications/size-changed` with a positive height.
3. `tools/call` for `list_deployments` succeeds and the table has eight rows.
4. Sorting by a column changes row order and sends no message.
5. Selecting a row sends exactly one `ui/update-model-context`.
6. Selecting a second row replaces rather than appends the context.
7. With `downloadFile` withdrawn, the export control is absent.
8. With `serverTools` withdrawn, the view still renders the initial result.
